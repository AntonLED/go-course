# Урок 1. Интерфейсы

## Ключевые идеи

Интерфейс в Go — это просто **набор методов**. Тип реализует интерфейс **неявно**: если у него есть все нужные методы, он подходит, и никакого ключевого слова `implements` писать не нужно. Компилятор сам сверит сигнатуры в момент, когда вы попытаетесь положить значение в интерфейсную переменную.

```go
type Shape interface {
    Area() float64
}

type Rect struct{ W, H float64 }

func (r Rect) Area() float64 { return r.W * r.H } // Rect теперь Shape

var s Shape = Rect{2, 3}
fmt.Println(s.Area()) // 6
```

На первый взгляд это мелкое синтаксическое удобство, но из него вытекает целый стиль проектирования. Раз тип не обязан заранее знать, каким интерфейсам он соответствует, интерфейс можно объявить там, где он нужен, то есть у потребителя, а не у поставщика. Пакет `storage` ничего не знает о вашем `type Saver interface{ Save(...) error }`, и знать ему не нужно. По той же причине можно «подогнать» чужой тип под свой интерфейс, не трогая его код. А поскольку каждый потребитель описывает только то, чем реально пользуется, интерфейсы получаются маленькими — ровно под его нужды.

## Method set и получатели

У каждого типа есть **method set** — набор методов, которые можно на нём вызвать с точки зрения интерфейсов. Для значения и для указателя этот набор разный:

| Тип | Методы в method set |
|---|---|
| `T` | только с получателем `T` |
| `*T` | с получателями `T` и `*T` |

Именно поэтому следующий код компилируется только наполовину:

```go
type Scaler interface{ Scale(k float64) }
func (c *Circle) Scale(k float64) { c.R *= k }

var _ Scaler = &Circle{}  // ок
var _ Scaler = Circle{}   // ошибка компиляции: Scale has pointer receiver
```

Причина вполне практическая. Значение, положенное в интерфейс, — это копия, и адреса у неё нет. Метод с получателем-указателем существует ради того, чтобы менять исходный объект, а менять безымянную копию внутри интерфейса бессмысленно: изменения никто бы не увидел. Поэтому язык такой вызов просто запрещает.

## Как интерфейс устроен внутри

Чтобы понимать поведение интерфейсов, а не заучивать его, полезно заглянуть внутрь. Интерфейсное значение — это пара машинных слов:

```
iface (непустой интерфейс)         eface (interface{} / any)
+--------+--------+                +--------+--------+
|  tab   |  data  |                | _type  |  data  |
+--------+--------+                +--------+--------+
    |                                  |
    v                                  v
  itab: { inter, _type, hash, fun[] }  описание типа
```

Первое слово непустого интерфейса указывает на `itab` (структура описана в runtime/runtime2.go). В ней лежат указатель на описание интерфейса, указатель на динамический тип и **таблица методов** `fun`, через которую идёт динамический вызов. Когда преобразование «конкретный тип в интерфейс» известно при компиляции, компилятор генерирует `itab` статически. Если же `itab` приходится вычислять в рантайме, например при `x.(io.Reader)` из другого интерфейса, результат кэшируется в глобальной хэш-таблице, так что повторные такие проверки обходятся дёшево.

Второе слово, `data`, — указатель на данные. Если значение не помещается в указатель (или само не является указателем), его обычно копируют в кучу, а в `data` кладут адрес копии. Отсюда **аллокация** при `var x any = bigStruct`: escape analysis видит, что значение уходит в интерфейс, и переносит его в кучу. Для мелких значений рантайм умеет обходиться без аллокации — это числа от 0 до 255, пустые структуры и нулевые значения.

У пустого интерфейса `any` (он же `eface`) методов нет, поэтому и `itab` ему не нужен: в первом слове сразу лежит `_type`.

Отсюда же следует цена вызова. Метод через интерфейс вызывается косвенно, через `fun[i]`, и компилятору такой вызов гораздо труднее встроить (заинлайнить). Частично это компенсирует PGO-девиртуализация, когда профиль подсказывает, какой конкретный тип встречается чаще всего.

![Для `var s Shape = Rect{2, 3}` слово `tab` ведёт в `itab` (интерфейс, динамический тип, таблица методов `fun`), а `data` указывает на копию значения. У `any` вместо `tab` сразу лежит `_type`: методов нет, и `itab` не нужен](img/iface-layout.svg)

## nil-интерфейс vs интерфейс с nil-указателем

Теперь, зная про два слова, легко понять самую знаменитую ловушку Go. Интерфейс равен `nil`, только если nil оба слова: и тип, и значение.

```go
type MyErr struct{}
func (*MyErr) Error() string { return "boom" }

func do() error {
    var p *MyErr = nil
    return p // интерфейс (type=*MyErr, data=nil)
}

fmt.Println(do() == nil) // false!
```

Функция вроде бы «вернула nil», но при возврате указатель `p` был упакован в интерфейс `error`. Значение внутри действительно nil, а вот тип уже записан — `*MyErr`, и сравнение с `nil` даёт `false`.

![Слева nil-интерфейс, у которого оба слова nil. Справа результат `return p` при `p *MyErr = nil`: `data` равно nil, но `tab` уже указывает на `itab` с типом `*MyErr`, поэтому интерфейс не равен nil](img/iface-typed-nil.svg)

Это классический вопрос с собеседований, и на практике он встречается не реже. Правило простое: **возвращайте литерал `nil`**, а не типизированную переменную. Если ошибки нужно накапливать, держите их в `[]error` или в переменной типа `error`, но не в `*MyErr`.

Любопытная деталь: метод на nil-указателе, лежащем внутри интерфейса, вызвать можно, если сам метод к этому готов. А вот вызов метода на nil-интерфейсе всегда заканчивается паникой `nil pointer dereference`, потому что таблицы методов просто нет.

## Type assertion и type switch

Иногда из интерфейса нужно достать конкретный тип или выяснить, умеет ли значение что-то ещё. Для этого есть type assertion:

```go
var s Shape = &Circle{R: 1}

c := s.(*Circle)        // паника, если тип другой
c, ok := s.(*Circle)    // безопасная форма
sc, ok := s.(Scaler)    // проверка «умеет ли ещё что-то» — интерфейс в интерфейс
```

Под капотом эти формы работают по-разному. Assertion к конкретному типу сводится к сравнению динамического типа с одним-единственным типом. Assertion к интерфейсу сложнее: рантайм ищет `itab` для пары (интерфейс, тип) в кэше, а если не находит, собирает его, сверяя методы типа.

![Assertion к конкретному типу сравнивает динамический тип с одним типом, а assertion к интерфейсу ищет `itab` для пары (интерфейс, тип) в кэше или собирает его по методам типа](img/type-assertion.svg)

Когда вариантов несколько, удобнее type switch:

```go
switch v := s.(type) {
case nil:
    // s == nil
case *Circle:
    // v имеет тип *Circle
case Rect, *Rect:
    // несколько типов — v имеет тип Shape (интерфейс)!
default:
    // v имеет тип Shape
}
```

Обратите внимание на ветку с несколькими типами: в ней `v` не получает конкретный тип, а остаётся интерфейсом `Shape`. Компилятор не может выбрать между `Rect` и `*Rect`, поэтому оставляет исходный тип выражения.

Проверка «интерфейс в интерфейс» лежит в основе приёма, который называют upgrade interface. Стандартная библиотека постоянно им пользуется: `io.Copy` проверяет, не реализует ли переданный `io.Writer` ещё и `io.ReaderFrom`, обработчики HTTP проверяют, реализует ли `http.ResponseWriter` ещё и `http.Flusher`, и так далее. Если умеет, выбирается более эффективный путь.

## Пустой интерфейс и any

`any` — псевдоним для `interface{}`, появившийся в Go 1.18. Ему удовлетворяет любой тип, и это одновременно его сила и слабость. Он уместен, когда тип действительно произволен: так устроены `fmt.Println` или `json.Unmarshal` в `map[string]any`. Но если после получения `any` вы делаете type switch по десятку типов, скорее всего, вам нужен интерфейс с методом или дженерик.

С `any` связан ещё один сюрприз. Оператор `==` для интерфейсов сравнивает и типы, и значения, и компилируется всегда. Однако если динамический тип несравним (срез, map, функция), сравнение заканчивается **паникой в рантайме**:

```go
var a, b any = []int{1}, []int{1}
fmt.Println(a == b) // panic: comparing uncomparable type []int
```

## Маленькие интерфейсы стандартной библиотеки

Самые полезные интерфейсы Go состоят из одного метода:

```go
type Reader interface { Read(p []byte) (n int, err error) }
type Writer interface { Write(p []byte) (n int, err error) }
type Stringer interface { String() string }        // fmt
type error interface { Error() string }            // встроенный
```

Роб Пайк сформулировал это так: «The bigger the interface, the weaker the abstraction» — чем больше интерфейс, тем слабее абстракция. Из одного `io.Reader` вырастает целая экосистема: `bufio`, `gzip`, `io.TeeReader`, `io.LimitReader`, `http.Request.Body`… Всё это можно вкладывать друг в друга, потому что каждому участнику цепочки нужен только метод `Read`.

![Обёртки `io.Reader` вкладываются друг в друга: каждый `Read` уходит вглубь цепочки, байты возвращаются обратно, а `TeeReader` по пути копирует их в `Writer`](img/reader-chain.svg)

У такой простоты есть обратная сторона: контракт `io.Reader` тоньше, чем кажется по сигнатуре, и документацию к нему обязательно стоит прочитать. Вот три пункта, на которых спотыкаются чаще всего:

- `Read` может вернуть `n > 0` и `err != nil` одновременно, поэтому сначала обработайте `n` прочитанных байт и только потом смотрите на ошибку;
- возвращать `0, nil` не рекомендуется (кроме случая `len(p) == 0`), но вызывающий обязан это пережить: это не EOF, а «ничего не произошло»;
- после `io.EOF` все последующие вызовы тоже должны возвращать `0, io.EOF`.

Проверять собственные реализации удобно пакетом `testing/iotest`: в нём есть `TestReader`, `OneByteReader`, `DataErrReader` и `ErrReader`, которые воспроизводят неудобные, но законные сценарии.

## Встраивание интерфейсов

Большие интерфейсы в Go обычно собирают из маленьких встраиванием:

```go
type ReadWriter interface {
    Reader
    Writer
}
```

Начиная с Go 1.14 наборы методов встраиваемых интерфейсов могут пересекаться, и это не ошибка. Интерфейс можно встроить и в структуру. Тогда структура «получает» его методы и делегирует их вызов полю. Это частый приём в тестах: объявляют `struct{ io.Writer }` и переопределяют один метод, а остальные достаются от встроенного поля. Подвох в том, что если встроенное поле осталось nil, вызов любого непереопределённого метода приведёт к панике.

## «Accept interfaces, return structs»

Эта поговорка хорошо описывает, как интерфейсы распределяются по API. Параметры функций делайте интерфейсами, причём минимально необходимыми: такую функцию легко протестировать с подделкой и переиспользовать с другим источником данных. Возвращайте же конкретные типы. Потребитель получит всё их API и сам решит, к какому интерфейсу привести результат.

У правила есть исключения. Первое — `error`, который всегда возвращают интерфейсом. Второе — фабрики, намеренно скрывающие реализацию: `sha256.New()` возвращает интерфейс `hash.Hash`. Для контраста посмотрите на `strings.NewReader`: он возвращает конкретный `*strings.Reader`, и это правило в чистом виде.

И последнее: не создавайте интерфейс «на всякий случай» рядом с единственной реализацией. Объявляйте его там, где он **потребляется**.

## Проверка реализации на этапе компиляции

Поскольку реализация неявная, легко случайно разойтись с интерфейсом, поменяв сигнатуру метода. Защититься помогает такая идиома:

```go
var _ io.Writer = (*CountingWriter)(nil)
var _ fmt.Stringer = Rect{}
```

Она ничего не аллоцирует и в рантайме ничего не делает, зато сборка сломается, как только сигнатура метода перестанет совпадать с интерфейсом.

## Типичные ошибки

1. Возврат типизированного nil как `error`.
2. Методы с получателем-указателем и попытка положить в интерфейс само значение.
3. Огромные интерфейсы «репозиториев» на 20 методов, объявленные рядом с реализацией.
4. `interface{}` там, где подошёл бы конкретный тип или дженерик.
5. Сравнение интерфейсов с несравнимым динамическим типом. Это касается и ключей map типа `any`.
6. Указатель на интерфейс (`*io.Reader`), который почти всегда означает ошибку.
