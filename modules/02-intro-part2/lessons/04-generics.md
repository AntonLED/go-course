# Урок 4. Дженерики

Долгие годы в Go нельзя было написать одну функцию `Map`, которая работала бы и со срезом чисел, и со срезом строк. Приходилось либо копировать код, либо принимать `any` и терять проверку типов. Дженерики (type parameters) появились в Go 1.18 и закрыли этот пробел: теперь функции и типы можно параметризовать типами, а компилятор по-прежнему проверяет всё на этапе сборки.

## Синтаксис

Параметры типа пишутся в квадратных скобках перед обычными параметрами:

```go
func Map[T, U any](s []T, f func(T) U) []U {
    out := make([]U, 0, len(s))
    for _, v := range s {
        out = append(out, f(v))
    }
    return out
}

strs := Map([]int{1, 2}, strconv.Itoa) // T=int, U=string выведены
```

Указывать `T` и `U` при вызове не пришлось: компилятор вывел их сам. Он сопоставляет типы параметров функции с типами переданных аргументов, примерно как при решении уравнения.

![Инференс сопоставляет типы параметров с типами аргументов: из `[]T` и `[]int` следует `T = int`, из `func(T) U` и `func(int) string` — `U = string`](img/type-inference.svg)

Параметризовать можно и тип:

```go
type Stack[T any] struct{ items []T }

func (s *Stack[T]) Push(x T) { s.items = append(s.items, x) }

var s Stack[string]
```

У методов такого типа параметры типа могут быть только те, что объявлены у получателя (`[T]`). Добавить методу собственные параметры типа **нельзя**. К этому ограничению мы ещё вернёмся.

## Ограничения (constraints)

Параметр типа без ограничений почти бесполезен: с произвольным `T` ничего, кроме присваивания, не сделаешь. Поэтому каждому параметру назначают **ограничение** (constraint), и это ограничение — обычный интерфейс. Точнее, почти обычный: с Go 1.18 интерфейсы бывают двух видов.

**Базовые интерфейсы** содержат только методы. Их по-прежнему можно использовать как обычный тип переменной.

**Общие интерфейсы** описывают набор типов (type set), например `~int | ~string` или `comparable`. Такие интерфейсы можно использовать **только** как ограничения.

```go
type Number interface {
    ~int | ~int64 | ~float64
}

func Sum[T Number](s []T) T {
    var total T
    for _, v := range s {
        total += v
    }
    return total
}

type Celsius float64
Sum([]Celsius{1.5, 2}) // ок благодаря ~float64
```

Тильда здесь ключевая. Запись `~T` означает «любой тип, у которого базовый тип T». Без неё в набор попал бы только сам `float64`, и `Celsius` не подошёл бы.

Внутри дженерика разрешены лишь те операции, которые допустимы для **всех** типов из набора. Для чисел и строк это `+`, для `cmp.Ordered` — `<`, для `comparable` — `==`. Методы и типы в ограничении можно комбинировать: `interface{ ~int; String() string }` требует и базовый тип `int`, и наличие метода `String`.

![Ограничение `Number` — объединение множеств типов. `~float64` включает все типы с базовым `float64`, в том числе `Celsius`, а без тильды в множестве был бы только сам `float64`](img/type-set.svg)

### Встроенные и стандартные ограничения

Самые ходовые ограничения уже есть в языке и стандартной библиотеке:

| Ограничение | Что разрешает |
|---|---|
| `any` | ничего, кроме присваивания/передачи |
| `comparable` | `==`, `!=`, ключи map |
| `cmp.Ordered` | `<`, `<=`, `>`, `>=` (целые, float, string) |

С `comparable` связана тонкость. Начиная с Go 1.20 ему удовлетворяют и интерфейсы, хотя строго сравнимы они не все: значение типа `any` может запаниковать при сравнении в рантайме, если внутри лежит, например, срез.

Раньше за упорядоченными типами ходили в `golang.org/x/exp/constraints`, но теперь это не нужно: с Go 1.21 `cmp.Ordered` есть в стандартной библиотеке.

## Инференс типов

Чаще всего type arguments указывать не приходится. Компилятор выводит их из аргументов функции, а начиная с Go 1.21 — ещё и из типа, которому присваивается функция-значение:

```go
slices.Index(xs, 5)          // T выведен из xs
var f func([]int) int = Sum  // 1.21+: инстанцирование по целевому типу
NewSet[int]()                // нечего выводить — указываем явно
```

Если вывести тип не из чего, компилятор сообщит `cannot infer T`, и тогда тип указывают явно, как в `NewSet[int]()`.

## Generic-типы и их ограничения

Вернёмся к запрету на собственные параметры типа у методов. На практике он выглядит так:

```go
type Set[T comparable] struct{ m map[T]struct{} }

func (s *Set[T]) Has(x T) bool { _, ok := s.m[x]; return ok }

// Нельзя: у метода собственный параметр типа
// func (s *Set[T]) Map[U comparable](f func(T) U) *Set[U]

// Можно: функция
func SetMap[T, U comparable](s *Set[T], f func(T) U) *Set[U] { ... }

// Нельзя сузить ограничение для метода: Sorted требует cmp.Ordered,
// а у Set только comparable — значит, это функция.
func Sorted[T cmp.Ordered](s *Set[T]) []T { ... }
```

Всё, что требует нового параметра типа или более узкого ограничения, оформляют обычной функцией, принимающей `*Set[T]` первым аргументом.

У текущей реализации есть и другие ограничения, о которых полезно знать заранее. В Go нет специализации и перегрузки. Нельзя сделать type switch прямо по `T`: можно написать `switch any(v).(type)`, но обычно это признак того, что дженерик здесь не нужен. Нельзя встроить параметр типа в структуру, то есть `struct{ T }` не скомпилируется. Generic-псевдонимы типов в Go 1.23 объявлять нельзя без GOEXPERIMENT, полноценно они появились в Go 1.24. Нулевое значение параметра типа получают через `var zero T`. И наконец, у параметра типа нет полей: ограничение `func F[T interface{ X int }]` не работает, ограничения описывают только методы.

## Как это реализовано: GC shape stenciling

Реализовать дженерики можно по-разному. C++ генерирует отдельную копию кода на каждый тип, что быстро, но раздувает бинарник и время компиляции. Java стирает типы и работает со всеми значениями через ссылки. Go выбрал компромисс, который называется **GC shape stenciling со словарями**.

Типы группируются по «GC-форме»: размеру, выравниванию и расположению указателей. Все указатели при этом имеют одну и ту же форму. На каждую форму генерируется одна копия кода, и в неё скрытым параметром передаётся **словарь** с информацией о конкретном типе: его методы, реализация `==`, размеры для вложенных инстанцирований.

Поэтому `Sum[int]` и `Sum[MyInt]` делят один и тот же машинный код. А вызовы методов через параметр типа, который оказался указателем, идут косвенно через словарь, почти как через интерфейс. Отсюда практический вывод: дженерики с интерфейсными ограничениями **не всегда быстрее** обычных интерфейсов.

![Инстанцирования одной GC-формы делят машинный код, а конкретный тип приходит скрытым словарём. Все указатели имеют одну форму, поэтому метод `String` вызывается через словарь, косвенно](img/gcshape.svg)

## Когда использовать

Дженерики хорошо ложатся на контейнеры и алгоритмы над ними: `Set`, `Stack`, `LRU`, `slices.Sort`, `maps.Keys`. Так же естественно выглядят функции над срезами, map и каналами любого типа, например `Map`, `Filter`, `Merge` или `FanIn[T]`. Общий признак простой: если без дженериков пришлось бы писать `any` с type assertion и терять типобезопасность, дженерик почти наверняка уместен.

## Когда НЕ использовать

Столь же важно понимать, когда без них лучше обойтись. Если достаточно интерфейса с методом, берите интерфейс: `func Write(w io.Writer)` проще и понятнее, чем `func Write[W io.Writer](w W)`. Если реализация для разных типов **разная**, это задача для интерфейса и полиморфизма, а не для дженерика: дженерик нужен, когда код одинаков, а меняется только тип.

Не обобщайте «на будущее», пока тип всего один. Хорошее правило: сначала напишите конкретный код и обобщайте его, когда появится вторая или третья копия. И не переходите на дженерики ради производительности без замеров — как мы видели выше, выигрыш вовсе не гарантирован.

## Типичные ошибки

1. `func Max[T any](a, b T) T { if a > b ... }`: оператор `>` не определён для `any`, нужен `cmp.Ordered`.
2. Забытая `~`: вызов `Sum([]Celsius{})` падает с ошибкой `Celsius does not satisfy Number`.
3. Попытка объявить метод с собственным параметром типа.
4. `min`, `max` и `<` с NaN. Встроенные `min` и `max` возвращают NaN, если он есть среди аргументов, а `<` с NaN всегда даёт false. Для полного порядка используйте `cmp.Compare` или `cmp.Less`.
5. `var x T; x == nil` — это ошибка компиляции для `T any`.
6. Возврат `nil` там, где нужно нулевое значение `var zero T`.
