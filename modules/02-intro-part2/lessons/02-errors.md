# Урок 2. Обработка ошибок в Go

## Ошибка — это значение

В большинстве популярных языков неудача сообщает о себе исключением, которое летит вверх по стеку, пока его кто-нибудь не поймает. Go выбрал другой путь. Ошибка здесь — обычное значение, реализующее крошечный встроенный интерфейс:

```go
type error interface {
    Error() string
}
```

Для штатных ситуаций исключений в Go нет. Функция, которая может не справиться, возвращает `error` последним результатом, а вызывающий код **явно** решает, что с ним делать:

```go
f, err := os.Open(name)
if err != nil {
    return fmt.Errorf("load config: %w", err)
}
defer f.Close()
```

Да, это многословнее, чем `try`/`catch`. Зато поток управления виден прямо в коде: глядя на функцию, вы точно знаете, где она может прерваться. А раз ошибки — обычные значения, с ними можно делать всё то же, что и с любыми другими: хранить, сравнивать, агрегировать, передавать по каналам.

## Sentinel-ошибки

Самый простой способ дать вызывающему коду отличить одну ошибку от другой — заранее объявить значение, с которым можно сравнивать. Такие значения называют **sentinel-ошибками**:

```go
var ErrNotFound = errors.New("not found")   // в пакете

if errors.Is(err, ErrNotFound) { ... }      // у потребителя
```

В стандартной библиотеке их много: `io.EOF`, `sql.ErrNoRows`, `fs.ErrNotExist`, `context.Canceled`. Минус у подхода один, но существенный: sentinel становится частью публичного API пакета, и убрать или переименовать его потом нельзя, не сломав потребителей. И ещё одно предостережение: никогда не сравнивайте `err.Error()` со строкой. Текст сообщения может поменяться в любой момент, и такая проверка тихо перестанет работать.

## Свои типы ошибок

Sentinel говорит только «что случилось», но иногда вызывающему нужны подробности: какое поле не прошло валидацию, какой код вернул сервер. Тогда объявляют собственный тип ошибки:

```go
type ValidationError struct {
    Field, Msg string
}

func (e *ValidationError) Error() string { return e.Field + ": " + e.Msg }

var ve *ValidationError
if errors.As(err, &ve) {
    fmt.Println("плохое поле:", ve.Field)
}
```

Обычно метод `Error` объявляют с получателем-указателем и возвращают `&ValidationError{...}`. Обратите внимание на второй аргумент `errors.As`: это **указатель на переменную** целевого типа. Если целевой тип — интерфейс, передают указатель на интерфейсную переменную, например `var re runtime.Error; errors.As(err, &re)`.

## Wrapping: %w, Unwrap, Is, As

Ошибка, поднимаясь по стеку вызовов, обычно обрастает контекстом. При этом исходную причину терять не хочется: вызывающему может понадобиться узнать, что в самом низу был именно `ErrNotFound`. Для этого ошибки **оборачивают**:

```go
err := fmt.Errorf("find user %d: %w", id, ErrNotFound)
errors.Unwrap(err) == ErrNotFound // true
errors.Is(err, ErrNotFound)       // true — проходит по цепочке
```

Глагол `%w` в `fmt.Errorf` сохраняет исходную ошибку: результат получает метод `Unwrap() error`, который её возвращает. Глагол `%v` оставляет только текст, и цепочка рвётся. Иногда так делают намеренно, чтобы не раскрывать детали реализации.

![`errors.Is` идёт по цепочке `Unwrap()`: на каждом звене сравнивает ошибку с целью и пробует метод `Is`, пока не найдёт совпадение или пока цепочка не кончится](img/errors-is-chain.svg)

Цепочка — не единственная возможная форма. Начиная с Go 1.20 `fmt.Errorf` принимает **несколько `%w`**, и тогда результат реализует `Unwrap() []error`. Той же версии принадлежит `errors.Join(e1, e2, ...)`, который объединяет несколько ошибок в одну. Nil-аргументы он отбрасывает, а если nil оказались все, возвращает `nil`. Текст объединённой ошибки — сообщения исходных, разделённые `\n`.

Получается уже не цепочка, а дерево. `errors.Is` и `errors.As` обходят его в глубину, в прямом порядке (pre-order), и умеют спускаться как по `Unwrap() error`, так и по `Unwrap() []error`.

![`errors.Join` и несколько `%w` превращают цепочку в дерево (`Unwrap() []error`), а `errors.Is` и `errors.As` обходят его в глубину: сначала узел, потом детей слева направо](img/errors-tree.svg)

Тип ошибки может и сам решать, чему он «равен». Для этого у него объявляют методы `Is(target error) bool` или `As(target any) bool`:

```go
func (e *ConflictError) Is(target error) bool { return target == ErrConflict }
```

На каждом узле `errors.Is` действует в строгом порядке. Сначала сравнивает ошибку с целью через `==`, если тип сравним. Затем вызывает метод `Is`, если он есть. И только потом идёт дальше через `Unwrap`.

## Typed nil — самая частая ловушка

В уроке про интерфейсы мы уже встречали эту ловушку, но в обработке ошибок она попадается особенно часто:

```go
func validate(u User) error {
    var verr *ValidationError
    if u.Name == "" {
        verr = &ValidationError{"name", "required"}
    }
    return verr // при отсутствии ошибок вернёт НЕ nil!
}
```

Интерфейс хранит пару (тип, значение), и пара `(*ValidationError, nil)` не равна `nil`. Поэтому даже при корректном пользователе вызывающий получит «ошибку». Лечится это просто: в успешной ветке пишите `return nil` явно, а если ошибок может быть несколько, копите их в `[]error` и объединяйте через `errors.Join`.

## Как оформлять сообщения

У сообщений об ошибках в Go есть устоявшиеся соглашения. Пишут их строчными буквами, без точки в конце и без слов вроде «failed to» или «error:», например `open config: permission denied`. Причина практическая: сообщения склеиваются друг с другом, и заглавная буква или точка посреди итоговой строки выглядели бы странно.

Каждый слой добавляет **свой** контекст, и в итоге получается читаемый путь: `profile: find user 42: not found`. Добавлять стоит то, чего вызывающий не знает. Он и так в курсе, что вызвал `LoadProfile`, поэтому писать «LoadProfile failed» бесполезно, а вот идентификатор пользователя, которого не нашли, пригодится.

## Стратегии обработки

Получив ошибку, функция может поступить одним из четырёх способов:

1. **Вернуть наверх с контекстом.** Это поведение по умолчанию.
2. **Обработать на месте**: повторить попытку (retry с backoff для временных ошибок), подставить значение по умолчанию или деградировать.
3. **Залогировать и продолжить работу.** Так поступают на границе системы: в HTTP-хендлере, в воркере очереди, в `main`.
4. **Прервать программу.** Это допустимо только в `main` или при инициализации (`log.Fatal`).

Главное здесь — **не логировать и не возвращать ошибку одновременно**. Если каждый уровень стека пишет ошибку в лог и тут же возвращает её выше, одна и та же ошибка попадёт в лог $N$ раз, по разу на каждом уровне. Решение о логировании принимает тот, кто ошибку окончательно обрабатывает.

Иногда вместо конкретного типа удобнее проверять поведение, то есть спросить ошибку, умеет ли она что-то:

```go
type temporary interface{ Temporary() bool }
var t temporary
if errors.As(err, &t) && t.Temporary() { retry() }
```

## panic и recover

Раз для штатных ситуаций есть `error`, зачем нужна паника? Она предназначена для **программных ошибок** и невозможных состояний: выхода за границы, nil-разыменования, нарушения инварианта. Ещё одно законное применение — «Must»-функции при инициализации, такие как `regexp.MustCompile` и `template.Must`: если регулярное выражение в исходнике некорректно, продолжать работу всё равно бессмысленно. Использовать панику как исключение для обычных ситуаций не стоит, и уж точно не стоит выпускать её за пределы своего пакета.

Если паника всё же может случиться в коде, который вы не контролируете, её превращают обратно в ошибку:

```go
func SafeCall(f func()) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("panic: %v", r)
        }
    }()
    f()
    return nil
}
```

Этот короткий пример опирается на несколько правил, и каждое из них важно.

Когда происходит паника, текущая горутина начинает раскручивать стек и выполнять отложенные функции в порядке LIFO. `recover()` останавливает раскрутку, **только** если вызван непосредственно в отложенной функции. Вызов из функции, вложенной в отложенную, или из другой горутины вернёт `nil` и ничего не остановит.

Чтобы после восстановления вернуть ошибку, нужен **именованный результат**. Отложенная функция выполняется уже после `return` и может изменить только то, у чего есть имя.

Паника в чужой горутине вашим `recover` не ловится и роняет весь процесс. Поэтому у каждой горутины должен быть свой `recover`, если он нужен. Именно так поступает `net/http`: он восстанавливается после паники в каждом хендлере отдельно.

Ещё несколько фактов, которые полезно помнить. Паники, порождённые рантаймом, реализуют интерфейс `runtime.Error`. Начиная с Go 1.21 вызов `panic(nil)` превращается в панику со значением `*runtime.PanicNilError`, так что проверка `recover() != nil` теперь надёжно отличает случай «паника была». Наконец, `os.Exit` и `log.Fatal` **не** выполняют отложенные функции вообще.

![Паника в `f` раскручивает стек: сначала выполняются defer'ы самой `f`, затем отложенная функция `SafeCall`, где `recover()` останавливает панику. После этого `SafeCall` возвращается обычным образом с заполненным `err`](img/panic-recover.svg)

## Типичные ошибки

1. `if err != nil { log.Println(err); return err }` — двойное логирование.
2. `return err` без контекста на каждом уровне. В логе остаётся одинокое «not found», и непонятно, что именно не нашлось.
3. Проверка `err == ErrX`, когда ошибку где-то по дороге обернули. Здесь нужен `errors.Is`.
4. `errors.As(err, ve)` вместо `errors.As(err, &ve)`. В рантайме это паника, а `go vet` ловит её заранее с сообщением «second argument to errors.As must be a non-nil pointer to either a type that implements error, or to any interface type».
5. Игнорирование ошибки `Close()` у файла, в который писали: данные могли так и не сброситься на диск.
6. `%w` для ошибок чужой реализации, которые вы не хотите делать частью своего API.
7. `defer` с `recover` в функции, которая сама не вызывается через `defer`.
