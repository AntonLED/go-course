# Урок 5. Итераторы

До Go 1.23 цикл `for ... range` умел обходить только встроенные коллекции: срезы, массивы, строки, map и каналы. Если же у вас было своё дерево или поток записей из базы, каждый автор изобретал собственный способ обхода: коллбэки, методы `Next()`, каналы. Go 1.23 добавил **range-over-func**: теперь `for ... range` умеет обходить функции особого вида, а новый пакет `iter` дал этим функциям имена.

## Типы итераторов

```go
package iter

type Seq[V any]     func(yield func(V) bool)
type Seq2[K, V any] func(yield func(K, V) bool)
```

Итератор — это функция, которая вызывает `yield` для каждого элемента. Сам `yield` возвращает `false`, когда потребитель больше не хочет данных, то есть сделал `break`, `return` или `goto` за пределы цикла. Если тело цикла паникует, `yield` не возвращается вовсе: паника проходит сквозь итератор, и его `defer` при этом выполняются.

```go
func Count(n int) iter.Seq[int] {
    return func(yield func(int) bool) {
        for i := range n {
            if !yield(i) {
                return // обязательно прекратить
            }
        }
    }
}

for v := range Count(5) {
    if v == 3 { break }
    fmt.Println(v)
}
```

## Как компилятор переписывает цикл

Чтобы понять, откуда берутся правила игры, посмотрим, во что компилятор превращает такой цикл. Тело цикла становится замыканием, и именно оно передаётся итератору в качестве `yield`:

```go
Count(5)(func(v int) bool {
    if v == 3 {
        return false // break
    }
    fmt.Println(v)
    return true      // следующая итерация
})
```

Получается, что управление перевёрнуто: не цикл запрашивает элементы, а итератор сам вызывает тело цикла для каждого из них. `break` превращается в `return false`, а переход к следующей итерации — в `return true`.

![Цикл `for v := range Count(5)` с `break` на 3: итератор сам вызывает тело цикла как `yield`, `break` превращается в `return false`, и итератор обязан выйти](img/range-func-seq.svg)

Более сложные конструкции тоже работают корректно. `return` из внешней функции, `break` по метке, `defer` внутри тела цикла — всё это поддержано: компилятор запоминает, каким образом тело хочет выйти, и после возврата из итератора выполняет нужное действие. `defer` в теле цикла при этом относится к **внешней** функции, точно так же, как в обычном цикле.

## Главное правило: yield после false

Раз итератор получает сигнал об остановке через возвращаемое значение `yield`, он обязан этот сигнал уважать. Если итератор вызовет `yield` после того, как тот вернул `false`, рантайм запаникует:

```
panic: runtime error: range function continued iteration after function for loop body returned false
```

С простыми циклами всё понятно, а вот в рекурсивных обходах, например по дереву, легко забыть пробросить `false` наверх. Каждый уровень рекурсии должен сообщать вызывающему, стоит ли продолжать:

```go
func (n *node) walk(yield func(int) bool) bool {
    if n == nil {
        return true
    }
    return n.left.walk(yield) && yield(n.val) && n.right.walk(yield)
}
```

Оператор `&&` здесь делает всю работу: как только какое-то звено вернуло `false`, остальные уже не вычисляются, и `false` поднимается до самого верха.

![После `break` на 3 `yield` возвращает false, и `&&` пробрасывает его вверх по рекурсии: `walk(3)`, `walk(2)` и `walk(4)` сразу возвращают false, а правое поддерево не обходится](img/tree-walk-false.svg)

Если итератору нужно освободить ресурс (закрыть файл, отпустить соединение), делайте это через `defer` внутри функции-итератора. Она завершится и при раннем выходе, так что очистка выполнится в любом случае.

## Стандартная библиотека (1.23)

Вместе с `iter` в Go 1.23 пакеты `slices` и `maps` получили функции, которые возвращают и принимают итераторы:

| Функция | Что делает |
|---|---|
| `slices.All(s)` | `Seq2[int, E]` — индекс и значение |
| `slices.Values(s)` | `Seq[E]` |
| `slices.Backward(s)` | `Seq2[int, E]` с конца |
| `slices.Collect(seq)` | собрать в срез |
| `slices.AppendSeq(s, seq)` | дописать в срез |
| `slices.Sorted(seq)`, `SortedFunc` | собрать и отсортировать |
| `slices.Chunk(s, n)` | `Seq[[]E]` — подсрезы (разделяют память с s!) |
| `maps.Keys(m)`, `maps.Values(m)`, `maps.All(m)` | итераторы по map (порядок случайный) |
| `maps.Collect(seq2)`, `maps.Insert(m, seq2)` | собрать в map |

Из этих кирпичиков складывается, например, идиома получения отсортированных ключей map: `slices.Sorted(maps.Keys(m))`.

## Pull-итераторы

Все итераторы, которые мы видели до сих пор, работают по модели **push**: источник управляет циклом и «проталкивает» элементы потребителю. Чаще всего это удобно, но не всегда. Попробуйте, например, пройти по двум последовательностям одновременно, чтобы слить их. С двумя push-итераторами это неудобно: каждый из них хочет сам управлять циклом, а вложенный `range` дал бы не слияние, а перебор всех пар. Здесь нужна модель **pull**, в которой потребитель сам запрашивает следующий элемент:

```go
next, stop := iter.Pull(seq)
defer stop()
for {
    v, ok := next()
    if !ok { break }
    ...
}
```

Под капотом `iter.Pull` запускает итератор как **корутину**. Это особый вид горутины с прямой передачей управления, и он дешевле, чем связка из горутины и канала. Вызов `next()` передаёт управление корутине до ближайшего `yield` и возвращает полученный элемент.

С `stop()` нужно обращаться аккуратно. Если вы не дочитали последовательность до конца, вызвать его обязательно: иначе итератор так и останется «висеть» на `yield`, и его `defer` не выполнятся. Вызывать `stop` повторно или после исчерпания последовательности безопасно. А вот вызывать `next` и `stop` конкурентно из разных горутин нельзя. Для `Seq2` существует парная функция `iter.Pull2`.

![В push-итераторе `seq` сам вызывает тело цикла. `iter.Pull` запускает `seq` в корутине: `next()` передаёт ей управление до ближайшего `yield`, а `stop()` заставляет `yield` вернуть false, и `seq` завершается, выполнив свои defer'ы](img/push-pull.svg)

Слияние двух отсортированных последовательностей через `iter.Pull` вам предстоит написать в задаче 08.

## Композиция

Итераторы легко комбинировать: функция может принять итератор и вернуть новый.

```go
func Filter[T any](s iter.Seq[T], keep func(T) bool) iter.Seq[T] {
    return func(yield func(T) bool) {
        for v := range s {
            if keep(v) && !yield(v) {
                return
            }
        }
    }
}

evens := Filter(Fibonacci(), func(x int) bool { return x%2 == 0 })
first5 := slices.Collect(Take(evens, 5))
```

![Конвейер ленивый: каждое число Фибоначчи проходит всю цепочку, прежде чем вычисляется следующее. После пятого чётного `Take` возвращается, и 233 уже не считается](img/iter-pipeline.svg)

Важное свойство таких конвейеров — они **ленивые**. Ничего не вычисляется, пока кто-нибудь не начнёт `range`, и каждый элемент проходит всю цепочку, прежде чем вычисляется следующий. Благодаря этому можно работать с бесконечными последовательностями, как `Fibonacci()` выше. Цена у этого тоже есть: каждая ступень конвейера — косвенный вызов замыкания. Компилятор часто инлайнит простые итераторы, но для горячих циклов по срезу обычный `for` всё ещё быстрее.

## Однократные и многократные итераторы

Большинство итераторов можно запускать сколько угодно раз: `slices.Values` каждый раз заново пройдёт по срезу. Но некоторые итераторы однократные — например, те, что читают из `bufio.Scanner` или из сети. Повторный `range` по ним ничего не даст, потому что данные уже прочитаны. Если ваш итератор такой, обязательно напишите об этом в документации.

## Ошибки в итераторах

Сигнатура `Seq` не предусматривает возврата ошибки. Как же быть, если при обходе что-то может сломаться? Устоявшихся вариантов три:

- `iter.Seq2[T, error]`, где на каждом шаге вместе с элементом приходит ошибка;
- отдельный метод `Err()`, который вызывают после цикла, как у `bufio.Scanner`;
- проверка ошибок до создания итератора, когда функция возвращает пару `Find(index) (iter.Seq[E], error)`.

## Итераторы и блокировки

Если коллекция защищена мьютексом, возникает соблазн держать блокировку на протяжении всего обхода. Не делайте этого: во время `yield` выполняется тело цикла, то есть чужой код. Если оно попытается захватить тот же `sync.RWMutex` на запись, получится дедлок, ведь мьютексы в Go не реентерабельны. Надёжнее сделать снимок данных под блокировкой, отпустить её и обходить уже снимок.

## Типичные ошибки

1. Игнорирование результата `yield`, которое приводит к панике при `break`.
2. Рекурсивный обход, не пробрасывающий `false` наверх.
3. `iter.Pull` без `stop()`: корутина утекает, а её `defer` не выполняются.
4. Переиспользование одного буфера при выдаче срезов (например, в собственной реализации `Chunk`): потребитель, сохраняющий срезы, раз за разом сохраняет одну и ту же память.
5. Ожидание определённого порядка от `maps.Keys`.
6. `Take(s, n)`, который запрашивает $(n+1)$-й элемент, хотя тот уже не нужен. У дорогого источника это лишняя работа.
