# Урок 6. Указатели, структуры, методы

## Указатели

Указатели в Go выглядят так же, как в C: `&` берёт адрес, `*` разыменовывает.

```go
x := 10
p := &x      // *int
*p = 20      // x == 20
var q *int   // nil; *q → panic: invalid memory address or nil pointer dereference
```

На этом сходство с C во многом заканчивается. Арифметики указателей в Go нет, и сдвинуть указатель на соседний элемент можно только через пакет `unsafe`. Зато можно спокойно вернуть из функции указатель на локальную переменную: это безопасно, переменная переживёт функцию, а где её разместить, компилятор решит сам.

Полезно держать в голове и общее правило: в Go **всё передаётся по значению**. Указатель не исключение, он тоже значение, просто это значение — адрес. Функция получает копию адреса, и эта копия указывает на тот же объект, поэтому изменения через неё видны снаружи.

### new vs &T{}

Получить указатель на новый объект можно двумя способами:

```go
p1 := new(int)          // *int на нулевое значение
p2 := &Point{X: 1}      // составной литерал + взятие адреса
p3 := new(Point)        // то же, что &Point{}
```

`new(T)` выделяет память под нулевое значение типа `T` и возвращает указатель на неё. `&T{...}` делает то же самое, но позволяет сразу задать поля, поэтому на практике встречается гораздо чаще. Учтите, что `&` нельзя применить к литералу базового типа: `&5` не скомпилируется, здесь понадобится `new` или промежуточная переменная.

## Escape analysis кратко

Мы уже упоминали, что компилятор сам решает, где разместить переменную. Делает он это с помощью escape analysis. Если переменная не переживает функцию, она остаётся на **стеке**, а это практически бесплатно и не нагружает сборщик мусора. Если же переменная «убегает», её приходится размещать в **куче**. Убегает она в нескольких типичных случаях: когда из функции возвращается указатель на неё, когда она сохраняется в глобальной переменной или в замыкании, когда её передают как интерфейс (часто, но не всегда), когда она слишком велика или её размер неизвестен при компиляции.

Решения компилятора можно увидеть своими глазами:

```bash
go build -gcflags=-m ./...
# ./main.go:5:2: moved to heap: x
# ./main.go:9:13: ... argument does not escape
```

Из этого вытекает неочевидный вывод. Возвращать структуру по значению нередко **дешевле**, чем возвращать указатель на неё: копирование небольшой структуры стоит меньше, чем аллокация в куче и последующая работа GC.

## Структуры

Структура объединяет несколько именованных полей. Поля с маленькой буквы не экспортируются и видны только внутри пакета:

```go
type User struct {
	ID    int64
	Name  string
	email string // неэкспортируемое поле
	Tags  []string
}

u := User{ID: 1, Name: "Ann"}   // именованные поля — рекомендуется
v := User{1, "Bob", "b@x", nil} // все поля по порядку — хрупко
anon := struct{ X, Y int }{1, 2} // анонимная структура (удобно в тестах)
```

Литерал с именами полей устойчив к изменениям типа, а позиционный ломается, стоит кому-то добавить или переставить поле. Поэтому почти всегда пишут первый вариант.

Присваивание структуры копирует **все её поля**, но копирование поверхностное. Если в структуре есть срез, map или указатель, копия будет ссылаться на те же данные, что и оригинал. Обращаться к полям через указатель можно без явного разыменования: Go сам превратит `p.Name` в `(*p).Name`. Пустая структура `struct{}` занимает 0 байт, и мы уже видели, как это используется для множеств.

Менее очевидно, что на размер структуры влияет порядок полей. Процессору удобнее читать поле, когда его адрес кратен размеру поля, поэтому компилятор вставляет между полями выравнивающие байты. Структура `struct{a bool; b int64; c bool}` занимает 24 байта:

$$
\underbrace{1}_{a} + \underbrace{7}_{\text{выравнивание}} + \underbrace{8}_{b} + \underbrace{1}_{c} + \underbrace{7}_{\text{хвост}} = 24
$$

А если поставить `int64` первым, `struct{b int64; a, c bool}` уложится в $8 + 1 + 1 + 6 = 16$ байт.

![Раскладка на amd64: перед `int64` нужно 7 байт выравнивания, и хвост добивается до кратного 8, итого 24 байта; если поставить `int64` первым, `bool`-поля ложатся подряд, и выходит 16 байт](img/struct-padding.svg)

### Сравнение структур

Структуры можно сравнивать через `==`, если сравнимы **все их поля**. Достаточно одного поля-среза, map или функции, и сравнение станет ошибкой компиляции. Структуры двух разных именованных типов сравнить не получится без явной конвертации. А сравнимые структуры, как мы видели в уроке про map, могут служить ключами map.

### Теги

К полю структуры можно приписать тег — строку с метаданными для библиотек:

```go
type Item struct {
	ID    int    `json:"id" db:"item_id"`
	Price int    `json:"price,omitempty"`
	Note  string `json:"-"`
}
```

Сам язык тег никак не интерпретирует, это просто строковый литерал. Читают его через `reflect`, например так: `reflect.TypeOf(Item{}).Field(0).Tag.Get("json")`. Этим пользуются `encoding/json`, ORM и библиотеки валидации. По соглашению тег состоит из пар `key:"value"`, разделённых пробелом, а `go vet` проверяет, что синтаксис не нарушен.

## Методы

Метод — это функция с **получателем** (receiver), который записывается в скобках перед именем:

```go
type Counter struct{ n int }

func (c Counter) Value() int { return c.n } // value receiver — копия
func (c *Counter) Inc()      { c.n++ }      // pointer receiver — оригинал
```

![Value receiver получает копию всей структуры, pointer receiver только адрес, поэтому `c.n++` в `Inc` меняет оригинал](img/receivers.svg)

Методы можно объявлять не только для структур, а для любого **именованного типа из того же пакета**, например для `type Celsius float64`. Ограничение одно: базовый тип получателя не может быть указателем или интерфейсом.

### Value vs pointer receiver

Какой получатель выбрать? Указатель нужен, если метод **меняет** получателя. Он же предпочтителен, если структура большая и копировать её при каждом вызове накладно. Обязателен указатель и тогда, когда в структуре есть `sync.Mutex` или что-то подобное: такие поля копировать нельзя, и `go vet` на это ругается. Наконец, если у типа уже есть методы с получателем-указателем, остальные тоже делают на указателе ради единообразия.

Получатель по значению хорош для маленьких неизменяемых типов, таких как `time.Time` или `type Celsius float64`.

Go немного помогает с вызовами. Если переменная `c` **адресуема**, запись `c.Inc()` автоматически превращается в `(&c).Inc()`. Но для неадресуемых значений это не работает:

```go
Counter{}.Inc()           // ошибка: cannot call pointer method Inc on Counter
m := map[string]Counter{}
m["a"].Inc()              // ошибка: элемент map неадресуем
```

Любопытная особенность Go: метод можно вызвать на nil-указателе. Ничего не упадёт, пока метод не обратится к полям, а значит, метод может сам обработать этот случай:

```go
func (l *List) Len() int { if l == nil { return 0 }; return l.n }
```

### Method sets

У каждого типа есть **набор методов** (method set), и от получателя зависит, в какие наборы метод попадёт:

| Тип | Method set |
|---|---|
| `T` | методы с получателем `T` |
| `*T` | методы с получателем `T` **и** `*T` |

Это различие становится критичным, когда в игру вступают интерфейсы (о них в модуле 2). Допустим, метод `String()` объявлен на `*T`. Тогда `fmt.Println(t)` для значения `t T` его **не вызовет**, потому что у типа `T` такого метода нет, а `fmt.Println(&t)` вызовет.

### Method value и method expression

Метод можно превратить в обычное значение-функцию двумя способами:

```go
f := c.Inc          // method value: получатель зафиксирован (для value receiver — копия сейчас)
g := (*Counter).Inc // method expression: func(*Counter)
g(&c)
```

Method value `c.Inc` запоминает получатель в момент вычисления выражения. Для получателя по значению это означает, что сохраняется копия, и последующие изменения `c` метод уже не увидит. Method expression `(*Counter).Inc`, напротив, ничего не запоминает: получается функция, которая принимает получатель первым аргументом.

## Встраивание (embedding)

Если объявить поле структуры без имени, указав только тип, получится встроенное поле. Его поля и методы «продвигаются» наверх, и к ним можно обращаться так, будто они принадлежат внешней структуре:

```go
type Animal struct{ Name string }
func (a *Animal) Describe() string { return "I am " + a.Name }
func (a *Animal) Sound() string    { return "..." }

type Dog struct {
	Animal        // встроенное поле: имя поля = имя типа, Animal
	Breed string
}
func (d *Dog) Sound() string { return "Woof" } // затеняет Animal.Sound

d := &Dog{Animal: Animal{Name: "Rex"}}
d.Name          // продвинутое поле, = d.Animal.Name
d.Describe()    // продвинутый метод: "I am Rex"
d.Sound()       // "Woof"
d.Animal.Sound() // "..." — явный вызов
```

![`Dog` содержит `Animal` целиком: `d.Name` и `d.Describe()` продвигаются и работают с `d.Animal`, а собственный `Dog.Sound` затеняет `Animal.Sound`](img/embedding.svg)

Выглядит похоже на наследование, но **это не наследование**, и разница проявляется быстро. Внутри `Animal.Describe` получатель имеет тип `*Animal` и ничего не знает о `Dog`. Если `Describe` вызовет `a.Sound()`, выполнится `Animal.Sound`, а не `Dog.Sound`, потому что виртуальных методов в Go нет. Точно так же `Dog` нельзя передать туда, где ожидается `Animal`, можно передать только `d.Animal`. Полиморфизм в Go достигается через интерфейсы.

Встраивание влияет и на наборы методов. Встраивание `T` продвигает методы с получателем `T`, а методы с получателем `*T` попадают только в method set `*Dog`. Если же встроить `*T`, оба вида методов окажутся в наборах и `Dog`, и `*Dog`.

Если на одной глубине встраивания оказались одноимённые поля или методы, это не ошибка сама по себе. Компилятор пожалуется (ambiguous selector) **только при обращении** к такому имени. И наконец, в структуры можно встраивать интерфейсы. Это используют для частичной реализации интерфейса и для декораторов, подробнее об этом в модуле 2.

## Конструкторы

Специального синтаксиса конструкторов в Go нет. По соглашению роль конструктора играет обычная функция с именем `NewT`, которая может проверить аргументы и вернуть ошибку:

```go
func NewServer(addr string, opts ...Option) (*Server, error) {
	if addr == "" {
		return nil, errors.New("empty addr")
	}
	return &Server{addr: addr, handlers: make(map[string]Handler)}, nil
}
```

Но ещё лучше, если конструктор вообще не нужен и нулевое значение типа уже рабочее, как у `var mu sync.Mutex` или `var b bytes.Buffer`.

## Stringer

Если тип реализует интерфейс `fmt.Stringer`, то есть имеет метод `String() string`, пакет `fmt` использует этот метод при печати:

```go
func (a *Account) String() string { return fmt.Sprintf("%s: %d", a.id, a.balance) }
```

Здесь есть известная ловушка — бесконечная рекурсия. Если внутри `String()` написать `fmt.Sprintf("%v", a)` для значения того же типа, `fmt` снова вызовет `String()`, и так до переполнения стека. Выхода два: форматировать отдельные поля, как в примере выше, или сконвертировать значение в тип без этого метода, например объявив `type plain Account`.
