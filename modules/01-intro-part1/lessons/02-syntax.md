# Урок 2. Основы синтаксиса

## Переменные

Объявить переменную в Go можно несколькими способами, и все они встречаются в реальном коде:

```go
var a int          // нулевое значение: 0
var b, c = 1, "x"  // тип выводится
d := 3.14          // короткое объявление — только внутри функций
```

У короткого объявления `:=` есть тонкость, о которую спотыкаются даже опытные люди. Оно требует, чтобы слева была **хотя бы одна новая** переменная, а остальные просто получают новые значения. Но переприсваиваются они только в том случае, если объявлены в той же области видимости. Во вложенном блоке `:=` создаст новую переменную с тем же именем; к этому мы вернёмся в разделе про shadowing.

### Нулевые значения (zero values)

Неинициализированных переменных в Go не бывает. Всё, что вы объявили без значения, получает **нулевое значение** своего типа: `0` для чисел, `0.0` для вещественных, `false` для `bool`, `""` для строк и `nil` для указателей, срезов, map, каналов, функций и интерфейсов. У структуры нулевыми становятся все поля.

Из этого вытекает важный принцип проектирования: хороший тип устроен так, чтобы его нулевое значение сразу было полезным. Именно так сделаны `sync.Mutex`, `bytes.Buffer` и `strings.Builder`: их можно объявить через `var` и сразу пользоваться, никакой инициализации не требуется.

## Базовые типы

| Группа | Типы |
|---|---|
| целые | `int8..int64`, `uint8..uint64`, `int`, `uint` (32/64 бит по платформе), `uintptr` |
| алиасы | `byte = uint8`, `rune = int32` |
| вещественные | `float32`, `float64`; `complex64`, `complex128` |
| прочие | `bool`, `string` |

Главное, что нужно запомнить про типы в Go: **неявных преобразований нет**. Сложить `int32` и `int64` не получится, как не получится и написать `var x float64 = i`, если `i` имеет тип `int`. Всякое преобразование пишется явно, например `float64(i)`.

Сами преобразования тоже таят несколько сюрпризов. Если привести к `int8` переменную со значением 200, произойдёт переполнение по модулю $2^8$, и получится $200 - 256 = -56$. С константой тот же `int8(200)` вообще не скомпилируется. Похожая история с дробными числами: для переменной `f := 3.99; int(f)` даст `3`, потому что дробная часть просто отбрасывается, а константное выражение `int(3.99)` снова окажется ошибкой компиляции, так как константу нельзя представить в `int` без потери точности.

Коварнее всего `string(65)`. Результатом будет `"A"`, а не `"65"`: целое число интерпретируется как руна, то есть как код символа. `go vet` предупреждает о такой конструкции, а для перевода числа в десятичную запись нужен `strconv.Itoa`.

Целочисленное деление отбрасывает дробную часть в сторону нуля, поэтому `7/2 == 3` и `-7/2 == -3`. Остаток берёт знак делимого: `-7%2 == -1`. И последнее: переполнение целых чисел не вызывает панику, значение просто «заворачивается».

## Константы и iota

Константы в Go вычисляются во время компиляции, и у них есть особенность, которой нет у переменных. Они бывают **нетипизированными**: такая константа хранится с «идеальной» точностью и получает конкретный тип только в том месте, где её используют.

```go
const big = 1 << 100        // ок, пока не используется как int
const f = big >> 98         // 4
var x float64 = 1 << 3      // ок: константа станет float64
```

Константа `big` равна $2^{100}$ и не помещается ни в один целый тип, но это не ошибка, пока её не попытаются положить в `int`. А `big >> 98` даёт вполне обычное $2^{2} = 4$.

Для перечислений в Go есть `iota`. Это счётчик внутри блока `const`: он начинается с 0 и увеличивается на единицу на каждой **строке** блока (в терминах спецификации, на каждом ConstSpec). Если у строки не указано выражение, повторяется выражение предыдущей строки, но уже с новым значением `iota`:

```go
type Weekday int
const (
	Sunday Weekday = iota // 0
	Monday                // 1 — выражение повторяется
	Tuesday               // 2
)

const (
	_  = iota             // пропуск 0
	KB = 1 << (10 * iota) // 1 << 10
	MB                    // 1 << 20
)

const (
	A, B = iota, iota * 10 // 0, 0
	C, D                   // 1, 10 — iota одна на строку
)
```

Во втором блоке `KB` получает $2^{10} = 1024$, а `MB` — $2^{20}$. Третий блок показывает, что `iota` считает именно строки, а не отдельные константы: `A` и `B` стоят в одной строке, и для обеих `iota` равна нулю.

## Управляющие конструкции

### if

В `if` можно написать короткую инструкцию перед условием. Объявленные в ней переменные видны во всех ветках, включая `else`:

```go
if v, err := strconv.Atoi(s); err != nil { // v и err видны и в else
	return err
} else if v > 10 {
	...
}
```

### for — единственный цикл

В Go нет `while` и `do-while`: все циклы записываются через `for`, просто в разных формах.

```go
for i := 0; i < n; i++ {}
for cond {}              // while
for {}                   // бесконечный
for i, v := range slice {}
for i := range 10 {}     // Go 1.22: range по целому
```

### switch

`switch` в Go ведёт себя спокойнее, чем в C. Писать `break` в конце каждого `case` не нужно, выполнение само останавливается. Если же нужно провалиться в следующую ветку, используют `fallthrough`, причём переход происходит безусловно, условие следующего `case` уже не проверяется. В одном `case` можно перечислить несколько значений через запятую, например `case 1, 2, 3:`, а `switch` без выражения (`switch { case x > 0: ... }`) заменяет длинную цепочку `if`-`else`.

Есть и ловушка. `break` внутри `switch` или `select` выходит **из самого switch, а не из окружающего цикла**. Чтобы прервать цикл, понадобится метка.

### Метки

Метка ставится перед циклом, и `break` или `continue` с её именем действуют на этот внешний цикл:

```go
outer:
	for _, row := range grid {
		for _, v := range row {
			if v < 0 {
				continue outer
			}
			if v == 0 {
				break outer
			}
		}
	}
```

## Функции

Функция может возвращать несколько значений и давать им имена. Именованные результаты на входе в функцию уже равны нулевым значениям, а «голый» `return` без аргументов возвращает их текущие значения. В коротких функциях это удобно, в длинных только запутывает читателя.

```go
func divmod(a, b int) (q, r int) { // именованные результаты — нулевые на входе
	q, r = a/b, a%b
	return // «голый» return — ок в коротких функциях
}

func sum(nums ...int) int { // variadic: nums — это []int
	total := 0
	for _, n := range nums {
		total += n
	}
	return total
}

sum(1, 2, 3)
s := []int{1, 2}
sum(s...)        // передаётся сам срез, без копирования — общий backing array!
```

Обратите внимание на последнюю строку. Когда срез передают в variadic-функцию через `s...`, копия не создаётся: функция получает тот же срез, и если она изменит его элементы, изменения увидит вызывающий код.

Функции в Go — значения первого класса. Их можно хранить в переменных, передавать как аргументы и возвращать из других функций. Сравнивать функции между собой нельзя, допустимо только сравнение с `nil`.

## Замыкания

Функциональный литерал может обращаться к переменным из окружающей функции. Важно понимать, что он захватывает **саму переменную, а не её значение** на момент создания: замыкание и внешняя функция работают с одной и той же ячейкой памяти.

```go
func counter() func() int {
	c := 0
	return func() int { c++; return c } // c «убегает» в кучу
}
```

Функция `counter` уже вернула управление, её кадр стека снят, но переменная `c` продолжает жить. Компилятор заметил, что на неё ссылается замыкание, и разместил её в куче.

![`next := counter()`: кадр `counter` уже снят, а `c` живёт в куче; объект замыкания хранит код и ссылку `&c`, поэтому после двух вызовов `next()` в `c` лежит 2](img/closure-counter.svg)

### Переменная цикла: до и после Go 1.22

Захват по ссылке долго был источником одной из самых известных ошибок в Go. До версии 1.22 переменная цикла `for i := ...` существовала в **единственном экземпляре на весь цикл**, и все замыкания, созданные внутри, ссылались на неё одну:

```go
var fs []func()
for i := 0; i < 3; i++ {
	fs = append(fs, func() { fmt.Print(i) })
}
for _, f := range fs { f() } // go ≤1.21: 333; go ≥1.22: 012
```

К моменту вызова цикл уже закончился, `i` равна 3, и старый Go печатал `333`. Начиная с Go 1.22 (если в `go.mod` указана версия `go 1.22` или новее) **каждая итерация получает собственную копию** переменной, причём и в трёхкомпонентном `for`, и в `range`. Теперь программа печатает `012`, а старый приём `i := i` в начале тела цикла больше не нужен. Изменение касается и горутин, запускаемых в цикле, и взятия адреса `&v` от переменной цикла.

![До Go 1.22 все три замыкания ссылаются на одну `i`, которая после цикла равна 3; с Go 1.22 у каждой итерации своя `i`](img/loopvar.svg)

## Область видимости и shadowing

Области видимости в Go вложены друг в друга: снаружи universe-блок со встроенными именами, внутри него пакет, затем файл (там живут импорты), затем функция и, наконец, блоки `if`, `for`, `switch` и просто `{}`. Имя, объявленное во внутреннем блоке, закрывает одноимённое внешнее. Это называется затенением, или shadowing:

```go
x := 1
if true {
	x := 2       // новая переменная, затеняет внешнюю
	x++
}
fmt.Println(x)   // 1
```

В таком игрушечном примере всё очевидно, но в жизни затенение чаще всего бьёт по переменной `err`. Посмотрите на классический случай:

```go
var err error
if cond {
	v, err := f() // err — новая, внешняя останется nil
	_ = v
}
return err       // всегда nil
```

Внутри `if` оператор `:=` видит новую переменную `v`, поэтому спокойно объявляет заодно и новую `err`. Ошибка из `f()` попадает во внутреннюю переменную и пропадает вместе с блоком, а функция всегда возвращает `nil`.

Найти такие места помогает анализатор `shadow`: `go vet -vettool=$(which shadow)`. В стандартный `go vet` он не входит, его устанавливают отдельно из `golang.org/x/tools/go/analysis/passes/shadow/cmd/shadow`. И для полноты картины: затенить можно даже встроенные имена. Строки `len := 3` или `true := false` компилируются без единой жалобы.

## defer

`defer` откладывает вызов функции до момента выхода из окружающей функции. Если отложенных вызовов несколько, они выполняются в порядке **LIFO**: последний отложенный срабатывает первым.

Здесь легко ошибиться в одном месте. Аргументы отложенного вызова **вычисляются сразу**, в момент выполнения инструкции `defer`, а не в момент вызова:

```go
x := 1
defer fmt.Println(x) // напечатает 1
x = 2
```

При этом отложенная функция-замыкание видит переменные «вживую» и может даже менять **именованные результаты** функции уже после `return`:

```go
func f() (n int) {
	defer func() { n *= 2 }()
	return 3 // n = 3, затем defer → 6
}
```

Здесь `return 3` сначала записывает 3 в `n`, затем выполняется отложенная функция и удваивает его, так что `f` вернёт 6.

Две оговорки напоследок. `os.Exit` завершает процесс немедленно и отложенные вызовы не выполняет. А `defer` внутри цикла не срабатывает в конце каждой итерации: вызовы копятся до выхода из функции, что легко приводит, например, к тысячам открытых файлов.

![`defer` в цикле: каждый вызов кладётся на вершину стека с уже вычисленным аргументом, а при выходе вызовы снимаются с вершины, поэтому вывод будет `2 1 0`](img/defer-lifo.svg)

## panic и recover

`panic` прерывает обычное выполнение и начинает раскручивать стек, по дороге выполняя все отложенные вызовы. Если паника так никем и не остановлена, программа падает и печатает трассировку стека. Остановить её можно функцией `recover`:

```go
func safe(f func()) (err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("recovered: %v", r)
		}
	}()
	f()
	return nil
}
```

![`safe(f)`, где `f` паникует: стек раскручивается до `safe`, её отложенная функция вызывает `recover`, пишет `err` в именованный результат, и `safe` возвращается обычным образом, а `return nil` так и не выполняется](img/panic-recover.svg)

У `recover` строгие правила. Он работает, только если вызван **непосредственно** в отложенной функции; вызов из функции, которую отложенная функция в свою очередь вызвала, ничего не поймает. Паника в другой горутине тоже не перехватывается `recover`-ом в текущей: если горутина запаниковала и сама себя не спасла, падает весь процесс.

С Go 1.21 вызов `panic(nil)` превращается в панику со значением `*runtime.PanicNilError`, так что `recover()` в этом случае возвращает не `nil`, и паника не остаётся незамеченной. Кроме того, некоторые аварии перехватить нельзя в принципе: `fatal error: concurrent map writes`, взаимная блокировка всех горутин (deadlock), нехватка памяти. Это не паники, а фатальные ошибки рантайма.

И главное про стиль. Паника в Go предназначена для программных ошибок, для ситуаций «этого не может быть». Всё, что может случиться при нормальной работе (файл не найден, сеть недоступна), возвращается как значение типа `error`.
