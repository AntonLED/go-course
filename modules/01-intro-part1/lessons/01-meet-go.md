# Урок 1. Осознанное знакомство с Go

## Зачем появился Go

Go придумали в Google в 2007 году трое инженеров: Роберт Гризмер, Роб Пайк и Кен Томпсон. В 2009-м язык открыли, а версия 1.0 вышла в марте 2012 года. Появился он не из академического интереса, а из вполне бытовой боли, знакомой любому, кто работал с большими кодовыми базами на C++ или Java.

Крупные проекты собирались десятки минут, и разработчики проводили заметную часть дня в ожидании компилятора. Языки были настолько богатыми, что внутри одной компании разные команды фактически писали на разных «диалектах», и чужой код приходилось сначала расшифровывать. А железо тем временем изменилось: серверы стали многоядерными, почти любая программа общалась по сети, тогда как языки предлагали для этого неудобные потоки и callback-и.

Из этих проблем и выросли цели Go: быстрая компиляция, код, который легко читать, встроенная конкурентность и единственный принятый способ оформления кода.

### Обещание совместимости Go 1

Код, написанный для Go 1.0, как правило, компилируется и работает до сих пор. Исключения оговорены в документе [go.dev/doc/go1compat](https://go.dev/doc/go1compat): это исправления ошибок и дыр в безопасности, а также программы, которые опирались на неспецифицированное поведение. Если поведение всё же нужно поменять, это делают осторожно и привязывают к директиве `go` в `go.mod`. Так, например, в 1.22 изменилась семантика переменной цикла (подробнее в уроке 2): старые модули её не замечают, пока вы не поднимете версию в `go.mod`. Отдельные настройки обратной совместимости переключаются через `GODEBUG`.

## Философия

Go намеренно беден. В нём всего 25 ключевых слов, нет наследования, перегрузки функций и операторов, исключений и неявных преобразований типов. Авторы сознательно поставили **простоту выше выразительности**: код пишут один раз, а читают десятки раз, и читать его должен любой человек в команде.

Вместо наследования язык предлагает композицию. Структуры встраиваются друг в друга, а интерфейсы реализуются неявно: типу достаточно иметь нужные методы, объявлять «implements» не нужно. Ошибки обрабатываются явно, потому что ошибка в Go — обычное значение, и отсюда знаменитое `if err != nil`. Для конкурентности есть горутины и каналы, а их идея сформулирована в девизе «Don't communicate by sharing memory; share memory by communicating»: не делите память ради общения, а общайтесь, чтобы делить память.

Отдельно стоит сказать про gofmt. Эта утилита задаёт единый стиль форматирования, и споры о пробелах и скобках в Go-сообществе просто закрыты. Как говорит Пайк, «Gofmt's style is no one's favorite, yet gofmt is everyone's favorite»: стиль gofmt никому не нравится полностью, но сам gofmt любят все.

Та же строгость проявляется в мелочах. Неиспользуемый импорт или неиспользуемая локальная переменная в Go считаются ошибкой компиляции, а не предупреждением.

## Toolchain: команда `go`

Почти всё, что нужно для работы, умеет одна команда `go`. Вот подкоманды, которыми вы будете пользоваться каждый день:

| Команда | Что делает |
|---|---|
| `go run main.go` / `go run .` | компилирует во временный каталог и запускает |
| `go build` | собирает бинарник (для `package main`) или просто проверяет компиляцию пакета |
| `go build -o app ./cmd/app` | собрать в указанный файл |
| `go test ./...` | запускает тесты (`*_test.go`) во всех пакетах модуля |
| `go test -race -count=1 -run TestX ./pkg` | с детектором гонок, без кеша, только нужный тест |
| `go vet ./...` | статический анализ: `Printf` с неверными аргументами, копирование `sync.Mutex`, недостижимый код и т.д. |
| `gofmt -l -w .` / `go fmt ./...` | форматирование |
| `go mod init`, `go mod tidy` | создание модуля, синхронизация зависимостей |
| `go get pkg@v1.2.3` | добавить/обновить зависимость |
| `go install pkg@latest` | установить утилиту в `$GOBIN` (по умолчанию `$GOPATH/bin`) |
| `go env` | переменные окружения toolchain |
| `go doc strings.Builder` | документация в терминале |

Запись `./...` встречается постоянно и означает «этот каталог и все вложенные пакеты».

### Build-теги

Иногда файл должен попадать в сборку только при определённых условиях: скажем, только на Linux или только в особой конфигурации. Для этого первой строкой файла пишут ограничение сборки, например `//go:build linux && amd64` или `//go:build solution`, и компилятор возьмёт файл, лишь когда условие выполнено.

В этом курсе теги используются для задач. Заготовки помечены `!solution`, эталонные решения помечены `solution`, поэтому обычный `go test` проверяет ваш код, а `go test -tags solution ./...` проверяет эталон.

## GOPATH и модули

До Go 1.11 весь код обязан был жить внутри рабочего пространства, по пути вида `$GOPATH/src/github.com/user/repo`, а понятия версии зависимости не существовало вовсе. Сейчас код организуют в **модули**, и типичный проект выглядит так:

```
myapp/
  go.mod      // module github.com/me/myapp; go 1.23; require ...
  go.sum      // криптографические хеши зависимостей
  main.go
```

В `go.mod` записаны путь модуля, минимальная версия Go и зависимости, а `go.sum` хранит криптографические хеши, по которым проверяется, что скачанный код не подменили.

Самое интересное здесь — то, как Go выбирает версии зависимостей. Алгоритм называется **MVS (minimal version selection)**. Каждый модуль в графе зависимостей говорит в `require`, какая минимальная версия библиотеки ему нужна, и Go берёт наименьшую версию, которая устраивает всех. На практике это максимум из указанных минимумов:

$$
v_\text{итог} = \max(v_1, v_2, \dots, v_k)
$$

Обратите внимание: выбирается не «самая свежая» версия из опубликованных. Новая версия библиотеки не попадёт в вашу сборку сама по себе, пока кто-то в графе явно её не потребует, и благодаря этому сборки воспроизводимы.

![MVS: `A` требует `C v1.3`, `B` требует `C v1.4`, и в сборку идёт максимальная из минимальных версий, `C v1.4`, хотя уже вышла `v1.5`](img/mvs.svg)

Скачанные зависимости складываются в кеш `$GOPATH/pkg/mod`. Так что GOPATH никуда не делся, но теперь это просто место для кеша модулей и каталога `bin`. Откуда качать модули, решает `GOPROXY` (по умолчанию `proxy.golang.org`); `GOSUMDB` сверяет хеши из `go.sum` с публичной базой, а в `GOPRIVATE` перечисляют приватные репозитории, которые не нужно отправлять ни в прокси, ни в базу хешей. Начиная с Go 1.21 директива `toolchain` и переменная `GOTOOLCHAIN` позволяют автоматически скачать нужную версию компилятора, если установленная слишком старая.

Подробно модули разбираются в модуле 2.

## Компиляция

Go компилируется в **нативный машинный код**, никакой виртуальной машины между программой и процессором нет. По умолчанию бинарь статически слинкован со всем Go-кодом и рантаймом: вы копируете один файл, и он работает. Именно поэтому Go-сервисы так удобно упаковывать в Docker-образ `FROM scratch`, где нет вообще ничего, кроме вашего бинаря.

Есть оговорка. Если программа использует пакеты `net` или `os/user`, на Linux может подключиться cgo, а вместе с ним динамическая зависимость от libc. Сборка с `CGO_ENABLED=0 go build` заставляет Go взять чистые Go-реализации, и бинарь получается полностью статическим.

Кросс-компиляция работает из коробки: `GOOS=linux GOARCH=arm64 go build` соберёт бинарь для Linux на ARM с любой машины, никаких дополнительных тулчейнов ставить не нужно.

За удобство приходится платить размером. Рантайм с планировщиком и сборщиком мусора едет внутри каждого бинаря, поэтому даже «hello world» с `fmt` весит около 2 МБ. Флаги `-ldflags="-s -w"` выбрасывают таблицу символов и отладочную информацию DWARF, и размер падает примерно до 1,5 МБ.

Почему же Go собирается так быстро, ведь это и была одна из главных целей? Во-первых, циклические импорты запрещены, так что пакеты компилируются строго по порядку зависимостей. Во-вторых, объектный файл пакета содержит всю информацию об экспорте, и компилятору, собирающему зависимый пакет, не нужно заглядывать дальше непосредственных импортов.

![`go build`: каждый пакет компилируется отдельно в объектный файл с export data (он кешируется), линковщик собирает их вместе с `runtime` в один файл, а `-ldflags="-s -w"` выкидывает таблицу символов и DWARF](img/go-build.svg)

## Рантайм и сборщик мусора

В каждом Go-бинаре живёт **runtime**: планировщик горутин (модель G-M-P, о ней в модуле 3), аллокатор памяти и сборщик мусора.

Сборщик мусора в Go конкурентный: он работает параллельно с вашей программой по алгоритму трёхцветной разметки (mark-and-sweep). В отличие от JVM, он **не делит кучу на поколения и не перемещает объекты**. Паузы, когда программа полностью останавливается (stop-the-world), обычно укладываются в доли миллисекунды.

Главная ручка настройки — переменная `GOGC`, по умолчанию равная 100. Она говорит, насколько куча может вырасти относительно живых данных, оставшихся после прошлой сборки, прежде чем начнётся новый цикл. Цель для следующей сборки считается так:

$$
H_\text{goal} = H_\text{live} \cdot \left(1 + \frac{\mathrm{GOGC}}{100}\right)
$$

При `GOGC=100` куча может вырасти на 100%, то есть вдвое. Вторая ручка, `GOMEMLIMIT` (Go 1.19+), задаёт мягкий лимит памяти: приближаясь к нему, сборщик начинает работать чаще, чем требует `GOGC`.

![«Пила» кучи при `GOGC=100`: после сборки осталось 4 МБ живых данных, поэтому следующий цикл GC нацелен на момент, когда куча дорастёт до 8 МБ](img/gc-gogc.svg)

Не каждая переменная вообще попадает в кучу. Компилятор с помощью **escape analysis** решает, где её разместить: на стеке, что дёшево и не нагружает GC, или в куче. Поэтому в Go совершенно законно вернуть из функции указатель на локальную переменную: компилятор заметит, что она «убегает» из функции, и просто разместит её в куче.

Стек горутины стартует с размера около 2 КБ. Когда его не хватает, рантайм выделяет новый участок памяти побольше и копирует стек туда.

## Где Go хорош

Лучше всего Go чувствует себя в сетевых сервисах: API, микросервисах, прокси. Неслучайно на нём написаны Docker, Kubernetes, etcd, Prometheus, Terraform и CockroachDB. Второе естественное применение — CLI-утилиты и DevOps-инструменты, где один статический бинарь и кросс-компиляция избавляют от множества проблем с установкой.

Язык хорошо справляется с высоконагруженным вводом-выводом: горутины намного дешевле потоков ОС, а сетевой poller встроен прямо в рантайм. И наконец, Go удобен большим командам. Код разных людей выглядит и читается одинаково, так что новый человек быстро начинает приносить пользу.

## Где Go не лучший выбор

Есть и области, где Go уступает. Системы жёсткого реального времени и всё, где сборщик мусора недопустим (ядро ОС, прошивки), остаются за C, C++ и Rust. Для тяжёлой численной математики и машинного обучения экосистема Python и C++ заметно богаче, к тому же в языке нет SIMD-интринсиков. GUI и мобильные приложения на Go писать можно, решения существуют, но это далеко не мейнстрим. А если задача требует богатой системы типов с алгебраическими типами данных и pattern matching, Go покажется слишком аскетичным.

## Hello, world

Теперь, когда понятно, откуда Go взялся и чем он живёт, напишем первую программу:

```go
package main // исполняемая программа — всегда пакет main

import "fmt"

func main() { // точка входа
	fmt.Println("Привет, Go!")
}
```

Чтобы её запустить, создайте модуль и воспользуйтесь `go run`, а если нужен бинарь, соберите его через `go build`:

```bash
go mod init example.com/hello
go run .
go build -o hello && ./hello
```

## Типичные ошибки новичков

Первое, обо что спотыкается почти каждый, — неиспользуемая переменная или импорт. Программа просто не скомпилируется. Пока код в работе, временно выручает заглушка `_ = x`.

Второе — перенос открывающей фигурной скобки на новую строку. В Go `{` обязана стоять на той же строке, что и `if`, `for` или `func`. Причина в лексере: он автоматически вставляет `;` в конце строки, и оторванная скобка оказывается уже после «конца» инструкции.

Третье — `go run main.go` в пакете из нескольких файлов. Команда увидит только перечисленные файлы и пожалуется на неизвестные имена из остальных, поэтому используйте `go run .`.

Наконец, путаница между старым GOPATH-режимом и модулями. Если запустить `go build` вне модуля, вы получите ошибку `go.mod file not found`, а лечится это созданием модуля через `go mod init`.
