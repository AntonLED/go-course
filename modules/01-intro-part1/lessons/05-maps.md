# Урок 5. Работа с картами (map): создание, доступ, операции

## Создание

Map — встроенная в Go хеш-таблица, и создать её можно несколькими способами:

```go
var m map[string]int            // nil map
m1 := map[string]int{}          // пустая, готова к записи
m2 := make(map[string]int, 100) // с подсказкой размера — меньше перераспределений
m3 := map[string][]int{"a": {1, 2}}
```

Если вы заранее примерно знаете, сколько элементов будет в map, передайте это число в `make`: таблица сразу выделит место, и по мере наполнения её не придётся перестраивать.

Переменная типа map — это, по сути, **указатель** на структуру рантайма (`*hmap`). Поэтому передача map в функцию не копирует данные, и все изменения, сделанные функцией, видны вызывающему. Но если внутри функции присвоить параметру новую map (`m = make(...)`), изменится лишь локальная копия указателя, а у вызывающего останется старая map.

## Нулевая (nil) map

Нулевое значение map — это `nil`, и с такой map можно делать почти всё, кроме записи:

```go
var m map[string]int
fmt.Println(m["x"], len(m)) // 0 0 — чтение ок
for range m {}              // ок, 0 итераций
delete(m, "x")              // ок, no-op
m["x"] = 1                  // panic: assignment to entry in nil map
```

На практике эта паника чаще всего возникает, когда map лежит полем внутри структуры, а конструктор забыл её инициализировать. Читать из такого поля можно сколько угодно, и ошибка проявится только при первой записи.

## Доступ и comma-ok

При обращении к отсутствующему ключу map не паникует, а возвращает нулевое значение типа. Чтобы узнать, был ли ключ на самом деле, используют вторую форму с флагом `ok`:

```go
v := m["k"]      // если ключа нет — нулевое значение
v, ok := m["k"]  // ok == false, если ключа нет
if _, ok := seen[x]; !ok { ... }
```

Без `ok` невозможно отличить ситуацию «ключа нет» от ситуации «ключ есть, и значение равно 0».

С другой стороны, то же самое поведение делает многие операции очень лаконичными: нулевое значение работает как значение по умолчанию.

```go
counts[w]++                         // для нового ключа начнёт с 0
groups[k] = append(groups[k], v)    // append к nil-срезу работает
```

## Удаление

Удалить один ключ можно через `delete`, а все сразу, начиная с Go 1.21, через `clear`:

```go
delete(m, k) // нет ключа — не ошибка
clear(m)     // Go 1.21: удалить все ключи
```

Удалять элементы прямо во время обхода `range` **безопасно**, это гарантирует спецификация: если удалённый элемент ещё не был пройден, цикл его уже не выдаст. С добавлением ситуация менее определённая. Элементы, добавленные во время обхода, могут попасть в него, а могут и не попасть.

## Порядок обхода

Порядок, в котором `range` выдаёт элементы map, **не определён**. Более того, рантайм специально его **рандомизирует**, выбирая случайный стартовый бакет и смещение внутри него, чтобы ни один программист не начал на этот порядок полагаться. Если нужен детерминированный вывод, ключи сортируют явно:

```go
keys := slices.Sorted(maps.Keys(m)) // Go 1.23: итераторы
for _, k := range keys { fmt.Println(k, m[k]) }
```

Приятное исключение — `fmt.Println(m)`. Начиная с Go 1.12 он печатает map **с отсортированными ключами**, и это очень удобно в тестах и примерах.

## Требования к ключам

Ключом map может быть только **сравнимый** тип, то есть такой, для которого определён оператор `==`. Сюда входят числа, строки, `bool`, указатели, каналы, интерфейсы, а также массивы и структуры, все поля которых сравнимы. Срезы, map и функции ключами быть не могут.

```go
type Point struct{ X, Y int }
visited := map[Point]bool{{1, 2}: true}
grid := map[[2]int]rune{}
```

С ключами связано несколько ловушек. Первая касается интерфейсов. Тип `any` сравним, поэтому компилятор такой ключ пропустит, но если в интерфейсе лежит несравнимое значение, случится **паника во время выполнения**: `m[any([]int{1})] = 1`.

Вторая ловушка — NaN. Поскольку $\mathrm{NaN} \ne \mathrm{NaN}$, каждая запись `m[math.NaN()] = 1` создаёт **новый** элемент, который потом невозможно прочитать по ключу. Такие элементы видны только при обходе через `range`, а удалить их можно лишь целиком, через `clear`.

Третья ловушка скорее концептуальная: если ключ — указатель, сравниваются адреса, а не содержимое. Две разные структуры с одинаковыми полями дадут два разных ключа.

## Элемент map неадресуем

Попробуйте изменить поле структуры, лежащей в map, и компилятор вас остановит:

```go
m := map[string]Point{"a": {1, 2}}
m["a"].X = 10   // ошибка компиляции: cannot assign to struct field m["a"].X in map
p := &m["a"]    // ошибка компиляции: invalid operation: cannot take address of m["a"]
```

Почему так строго? Когда таблица растёт, элементы переезжают в новую память. Если бы можно было взять адрес элемента, после переезда указатель стал бы висячим. Поэтому элементы map неадресуемы, и обходить это ограничение приходится одним из двух способов: прочитать значение, изменить его и записать обратно, либо с самого начала хранить в map указатели.

```go
p := m["a"]; p.X = 10; m["a"] = p // прочитать — изменить — записать
mp := map[string]*Point{}         // хранить указатели
mp["a"].X = 10                    // ок (если значение не nil!)
```

## Как устроено внутри

### Классическая реализация (до Go 1.23 включительно)

Вплоть до Go 1.23 map была устроена как хеш-таблица с бакетами. Главная структура `hmap` хранит число элементов `count`, параметр $B$, от которого зависит количество бакетов (их $2^B$), указатель на массив бакетов и `hash0` — сид хеш-функции, свой у каждой map.

Каждый **бакет** вмещает 8 пар ключ-значение. Кроме них в бакете лежит массив `tophash`, где для каждого ключа записаны старшие 8 бит его хеша, и указатель на overflow-бакет на случай, если восьми слотов не хватит.

Поиск ключа идёт так. Младшие $B$ бит хеша выбирают бакет. Внутри бакета слоты просматриваются по очереди, и для каждого сначала сравнивается `tophash`. Это быстрая проверка по одному байту, и полный ключ сравнивается только тогда, когда `tophash` совпал.

![Классическая map с `B = 2`: младшие B бит хеша выбирают один из 4 бакетов, старшие 8 бит сравниваются с `tophash`; бакет хранит по 8 tophash, ключей и значений и указатель на overflow-бакет](img/map-buckets.svg)

Когда в среднем на бакет приходится больше $6{,}5$ элемента, таблица удваивается. Если же накопилось слишком много overflow-бакетов, запускается «рост того же размера», то есть уплотнение без увеличения. В обоих случаях элементы переносятся в новые бакеты не разом, а **инкрементально**: понемногу при каждой записи и удалении. Так одна операция не превращается в долгую паузу.

![Рост с `B = 2` до `B = 3`: старый бакет `i` делится на новые `i` и `i+4` по следующему биту хеша, и переезд идёт понемногу при записях и удалениях, поэтому брать адрес элемента map нельзя](img/map-evacuation.svg)

И ещё одно свойство, о котором полезно помнить: map **никогда не уменьшается**. Если положить в неё миллион ключей, а потом их все удалить, память бакетов так и останется занятой. Единственное лекарство — создать новую map и переложить в неё оставшиеся элементы.

### Swiss tables (Go 1.24+)

С Go 1.24 map реализована по-новому, как **Swiss table** — идея пришла из библиотеки Abseil от Google. Это таблица с открытой адресацией, где слоты сгруппированы по 8. У каждой группы есть контрольное слово из 8 байт, по байту на слот: в нём 7 бит хеша и состояние слота. При поиске сравнивается сразу вся группа с помощью побитовых операций, почти как в SIMD.

Вся таблица разбита на независимые под-таблицы размером до 1024 слотов, и при росте перестраивается только одна из них. Благодаря этому пиковые задержки стали меньше. В итоге поиск и вставка ускорились, а памяти требуется меньше.

![Swiss table: старшие биты хеша выбирают таблицу в директории, `H1` — группу, с которой начинается поиск, а 7-битный `H2` сравнивается сразу со всеми 8 контрольными байтами группы](img/map-swiss.svg)

При этом **семантика языка не изменилась**. Порядок обхода по-прежнему случаен, элементы неадресуемы, а конкурентная запись фатальна. Для программиста смена реализации заметна только по производительности.

## Конкурентный доступ

Map **не потокобезопасна**. Если рантайм замечает, что одна горутина пишет в map, пока другая в неё пишет или читает, он завершает процесс с одной из таких ошибок:

```
fatal error: concurrent map writes
fatal error: concurrent map read and map write
```

Обратите внимание: это **fatal error, а не panic**, и `recover` здесь не поможет. Защищать map нужно заранее. Обычно её оборачивают в `sync.Mutex` или `sync.RWMutex`. Для сценариев, где пишут редко, а читают часто, или где горутины работают с непересекающимися ключами, подходит `sync.Map`. При очень высокой нагрузке map шардируют. Одновременное **чтение** из нескольких горутин безопасно и без блокировок, а найти ошибки конкурентного доступа поможет `go test -race`.

## Пакет maps (Go 1.21+, итераторы — 1.23)

Пакет `maps` появился в Go 1.21, а функции, работающие с итераторами, добавились в 1.23:

```go
maps.Clone(m)              // поверхностная копия; Clone(nil) == nil
maps.Copy(dst, src)        // dst[k] = v для всех k из src
maps.Equal(m1, m2)         // nil и пустая — равны
maps.DeleteFunc(m, func(k string, v int) bool { return v == 0 })
maps.Keys(m), maps.Values(m) // iter.Seq — не срезы!
maps.All(m)                // iter.Seq2[K, V]
maps.Collect(seq)          // map из iter.Seq2
slices.Sorted(maps.Keys(m))
```

Будьте внимательны с `maps.Keys` и `maps.Values`: они возвращают итераторы, а не срезы. Чтобы получить отсортированный срез ключей, итератор передают в `slices.Sorted`.

## Множество

Отдельного типа «множество» в Go нет, его делают из map. Классический вариант использует в качестве значения пустую структуру, которая занимает 0 байт:

```go
set := map[string]struct{}{} // struct{} занимает 0 байт
set["a"] = struct{}{}
_, ok := set["a"]
// или map[string]bool — проще читать: if set["a"] {...}
```

Вариант с `map[string]bool` тратит лишний байт на элемент, зато проверка принадлежности читается естественнее.

## Сравнение map

Map можно сравнивать через `==` **только с nil**. Чтобы сравнить содержимое двух map, используйте `maps.Equal` или `reflect.DeepEqual`.
