# Урок 3. Работа с массивами и срезами

## Массивы

Начнём с массивов. В повседневном Go-коде они встречаются нечасто, но без них невозможно понять срезы, которые построены поверх массивов.

```go
var a [3]int              // [0 0 0]
b := [...]string{"x", "y"} // длина выводится: [2]string
c := [5]int{1: 10, 4: 40}  // [0 10 0 0 40]
```

Длина массива — **часть его типа**. `[3]int` и `[4]int` — это разные типы, и передать один туда, где ожидается другой, нельзя. Поэтому `len` массива известна уже при компиляции и является константой.

Второе отличие от многих языков: массив в Go — это значение, а не ссылка. Присваивание и передача в функцию копируют все его элементы. Зато массивы можно сравнивать через `==`, если сравнимы их элементы, а значит, их можно использовать и как ключи map.

## Срез: устройство

Срез выглядит как «массив без длины», но на деле это маленькая структура, заголовок среза (slice header). На amd64 он занимает 24 байта:

```go
type slice struct {
	array unsafe.Pointer // указатель на первый элемент backing array
	len   int            // сколько элементов видно
	cap   int            // сколько есть от array до конца выделенной памяти
}
```

Сами элементы хранятся в отдельном массиве, который называют backing array. Когда вы передаёте срез в функцию, он передаётся **по значению**: копируется заголовок, но копия указывает на тот же самый массив. Отсюда следствие, которое важно прочувствовать. Функция может изменить элементы среза, и вызывающий это увидит. А вот изменить длину среза вызывающего она не может, потому что длина хранится в заголовке, а заголовок у функции свой. Именно поэтому в Go принята идиома `s = append(s, ...)`: новый заголовок нужно явно забрать.

```go
func set(s []int)  { s[0] = 100 }       // видно снаружи
func grow(s []int) { s = append(s, 1) } // не видно снаружи
```

![Массив при передаче копируется целиком, у среза копируется только заголовок: обе копии смотрят в один backing array, поэтому `s[0] = 100` видно вызывающему](img/array-vs-slice-arg.svg)

## Создание

Срез можно получить несколькими способами, и они дают немного разные результаты:

```go
var s []int            // nil-срез: len 0, cap 0, s == nil
e := []int{}           // пустой, НЕ nil
m := make([]int, 3)    // [0 0 0], cap 3
k := make([]int, 0, 10) // len 0, cap 10
```

### nil vs пустой

Разница между nil-срезом и пустым срезом в большинстве случаев не видна. У обоих `len == 0`, с обоими работают `range`, `append` и `len`. Но кое-где она всплывает. Условие `s == nil` истинно только для nil-среза. `json.Marshal` превращает nil-срез в `null`, а пустой в `[]`, и клиент вашего API вполне может это заметить. `reflect.DeepEqual` считает nil-срез и пустой срез разными и вернёт `false`.

Поэтому проверять срез на пустоту идиоматично через `len(s) == 0`: такая проверка одинаково работает в обоих случаях.

![У nil-среза указатель пуст; у `[]int{}` он ненулевой (указывает на объект нулевого размера), поэтому `e != nil`; `make([]int, 0, 10)` сразу выделяет место на 10 элементов при `len 0`](img/nil-vs-empty.svg)

## Срезание (slicing)

Выражение `s[low:high]` выбирает элементы с индексами от `low` до `high-1`. У результата длина равна `high-low`, а ёмкость равна `cap(s)-low`, то есть тянется до конца исходного массива. И главное: новый срез **разделяет память** с исходным, ничего не копируется.

```go
a := []int{1, 2, 3, 4, 5}
b := a[1:3]       // [2 3], len 2, cap 4
b[0] = 20         // a = [1 20 3 4 5]
b = append(b, 99) // места хватает → a = [1 20 3 99 5] !
```

Последняя строка обычно удивляет. У `b` длина 2, но ёмкость 4, поэтому `append` не выделяет новую память, а пишет 99 прямо в следующую ячейку общего массива. Эта ячейка — `a[3]`, и исходный срез молча меняется.

![`b := a[1:3]` — новый заголовок над тем же массивом: запись в `b[0]` видна как `a[1]`, а `append(b, x)` перезапишет `a[3]`, пока хватает `cap`](img/slice-sharing.svg)


Кстати, срезать можно и **за пределы `len`, если не выходить за `cap`**. Продолжая пример, `b[:4]` даст `[20 3 99 5]`.

### Full slice expression

Как защититься от такой перезаписи? Для этого есть полная форма выражения среза с третьим индексом: `s[low:high:max]`. Она ограничивает ёмкость результата значением `max-low`. Если ёмкость равна длине, `append` уже не сможет залезть в «чужие» элементы и будет вынужден выделить новый массив:

```go
b := a[1:3:3] // len 2, cap 2
b = append(b, 99) // новый массив, a не изменился
```

![`a[1:3:3]` даёт `cap 2`, и `append` уже не может писать в `a[3]`: выделяется новый массив, куда копируются 2 и 3, а исходный `a` остаётся нетронутым](img/full-slice-expr.svg)

Пользуйтесь этим приёмом, когда отдаёте наружу подсрез собственного буфера: так вызывающий код не испортит данные, которые ему не принадлежат.

## append и рост

`append` добавляет в конец среза один или несколько элементов, а с многоточием может дописать целый срез:

```go
s = append(s, x)
s = append(s, other...)
```

Что происходит внутри, зависит от запаса ёмкости. Если $\mathit{len} + n \le \mathit{cap}$, новые элементы записываются в тот же массив, и `append` возвращает срез с увеличенной длиной. Если места не хватает, выделяется новый массив побольше, старые элементы копируются туда, и только потом дописываются новые.

Насколько больше? С Go 1.18 стратегия такая: у маленьких срезов, до 256 элементов, ёмкость **удваивается**, а дальше коэффициент роста плавно снижается и стремится примерно к $1{,}25$. Полученное число ещё округляется вверх до ближайшего size class аллокатора памяти. Точные значения `cap` после роста — деталь реализации, и полагаться на них не стоит.

Из всего этого следует правило без исключений: **результат `append` всегда нужно присваивать**. Вы не можете знать заранее, выделит ли конкретный вызов новый массив, и старый заголовок может оказаться указывающим на устаревшие данные.

![`append` к полному срезу: создаётся новый массив удвоенной ёмкости, старые элементы копируются, затем дописывается 5, а `s` по-прежнему указывает на старый массив](img/append-grow.svg)

### Главный подвох: общий backing array

Теперь соберём всё вместе и посмотрим на ошибку, которую очень любят на собеседованиях:

```go
x := make([]int, 3, 10)
y := append(x, 1) // пишет в x[3]
z := append(x, 2) // пишет в x[3] — затирает!
fmt.Println(y[3], z[3]) // 2 2
```

![`x`, `y` и `z` делят один массив с `cap 10`: оба `append` пишут в элемент `[3]`, и второй затирает первый](img/append-alias.svg)

У `x` длина 3 и ёмкость 10, так что оба `append` работают без новой аллокации и пишут в одну и ту же ячейку с индексом 3. Второй вызов затирает результат первого, и `y` с `z` видят одно и то же значение. Когда от одного «родительского» среза с запасом ёмкости делают несколько `append`, они мешают друг другу. Разорвать эту связь можно тремя способами: ограничить ёмкость через full slice expression, скопировать срез через `slices.Clone` или сделать копию вручную с помощью `make` и `copy`.

Общий массив создаёт и ещё одну проблему, на этот раз с памятью. Если написать `small := big[:10]`, маленький срез будет держать в памяти весь огромный массив `big`, и сборщик мусора не сможет его освободить. Когда нужен только кусочек, скопируйте его: `small := slices.Clone(big[:10])`.

## copy

Встроенная функция `copy` копирует элементы из одного среза в другой и возвращает количество скопированных элементов:

```go
n := copy(dst, src) // копирует min(len(dst), len(src)), возвращает n
```

Она корректно обрабатывает перекрывающиеся области, как `memmove` в C, и умеет копировать байты из строки в `[]byte`: `copy(dst, "string")`.

Классическая ошибка с `copy` связана с тем, что она смотрит на длину приёмника, а не на ёмкость. Код `dst := make([]int, 0, len(src)); copy(dst, src)` не скопирует ни одного элемента, потому что у `dst` длина равна нулю.

## Идиомы

Несколько приёмов встречаются настолько часто, что их стоит просто запомнить:

```go
// удаление i-го с сохранением порядка
s = append(s[:i], s[i+1:]...)
// фильтрация на месте без аллокаций
out := s[:0]
for _, v := range s {
	if keep(v) { out = append(out, v) }
}
clear(s[len(out):]) // обнулить хвост, если элементы — указатели
// разворот
for i, j := 0, len(s)-1; i < j; i, j = i+1, j-1 { s[i], s[j] = s[j], s[i] }
// стек
s = append(s, v); top := s[len(s)-1]; s = s[:len(s)-1]
```

Фильтрация на месте заслуживает пояснения. Срез `out` начинается с нулевой длиной, но смотрит в тот же массив, что и `s`, поэтому оставленные элементы переписываются в его начало без единой аллокации. Хвост после фильтрации лучше обнулить через `clear`, если элементы содержат указатели: иначе объекты, на которые они ссылаются, так и останутся достижимыми для сборщика мусора.

## range по срезу

У цикла `range` по срезу есть два поведения, которые полезно знать заранее:

```go
for _, v := range s { v *= 2 }          // v — копия, s не меняется
for i := range s { s[i] *= 2 }          // так меняем
for _, v := range s { s = append(s, v) } // бесконечно? Нет: range вычисляет s один раз
```

Переменная `v` — это копия элемента, поэтому изменение `v` на срез никак не влияет; менять элементы нужно по индексу. А выражение справа от `range` вычисляется **один раз**, до начала цикла, и длина обхода фиксируется в этот момент. Поэтому третий цикл не станет бесконечным, хотя срез внутри него растёт.

## Пакет slices (Go 1.21+)

С Go 1.21 в стандартной библиотеке есть обобщённый пакет `slices`, который избавляет от множества самописных циклов:

```go
slices.Sort(s)                         // по возрастанию, для cmp.Ordered
slices.SortFunc(s, func(a, b T) int {...}) // cmp.Compare, cmp.Or
slices.SortStableFunc(...)
idx, found := slices.BinarySearch(s, x)
slices.Contains(s, x); slices.Index(s, x)
slices.Equal(a, b)                     // nil и пустой — равны
slices.Reverse(s); slices.Max(s); slices.Min(s)
slices.Clone(s)                        // Clone(nil) == nil
slices.Compact(s)                      // убрать соседние дубли
slices.Insert(s, i, v...); slices.Delete(s, i, j)
slices.Grow(s, n)                      // гарантировать запас cap
slices.Chunk(s, n)                     // Go 1.23: итератор кусков
```

Начиная с Go 1.22 `slices.Delete` и `slices.Compact` обнуляют освободившийся хвост среза, так что утечки через оставшиеся указатели там больше не бывает.

В том же Go 1.21 появились встроенные функции `min`, `max` и `clear`. Для среза `clear` обнуляет все элементы, но длину не меняет.

## Многомерные срезы

Двумерную сетку в Go обычно строят как срез срезов:

```go
grid := make([][]int, rows)
for i := range grid {
	grid[i] = make([]int, cols)
}
```

Каждая строка здесь — самостоятельный срез, поэтому строки независимы и могут иметь разную длину. Для плотных матриц, где все строки одинаковые, эффективнее завести один срез длиной `rows*cols` и обращаться к элементу по индексу `i*cols+j`: данные лежат в памяти подряд, а аллокация одна вместо `rows` штук.
