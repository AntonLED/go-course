# Задача 06. Атомарная запись файла: temp + rename

Представьте, что сервис хранит состояние в JSON-файле и перезаписывает его после каждого изменения. Однажды процесс падает посреди записи, и после рестарта файл оказывается пустым. Такое случается на практике, и защищаются от этого одним и тем же приёмом: пишут во временный файл рядом с целевым, а затем атомарно подменяют его через `rename`. Этот приём мы и реализуем.

Пакет `atomicfile`. Реализуйте в `atomicfile.go`:

```go
func Write(name string, perm fs.FileMode, fn func(w io.Writer) error) error
func WriteFile(name string, data []byte, perm fs.FileMode) error // через Write
```

Почему не подходит обычный `os.WriteFile`? Он открывает файл с `O_TRUNC` и пишет данные. Если процесс упадёт посередине или кто-то параллельно читает файл, тот увидит его пустым или записанным наполовину. Правильная последовательность шагов такая:

1. Создать временный файл через `os.CreateTemp(dir, "."+base+".tmp-*")` в том же каталоге, что и целевой.
2. Записать данные. Функция `fn` получает `bufio.Writer` поверх файла, так что не забудьте про `Flush`.
3. Вызвать `f.Chmod(perm)`. `CreateTemp` всегда создаёт файл с правами `0600`, а umask к `Chmod` не применяется, поэтому права получатся ровно `perm` (в отличие от `os.WriteFile`, где действует umask). Делаем это до `Sync`, чтобы на диск попали и данные, и права.
4. Вызвать `f.Sync()`, затем `f.Close()`, и обязательно проверить ошибку `Close`.
5. Выполнить `os.Rename(tmp, name)`: на POSIX это атомарно заменяет целевой файл.

При любой ошибке, и даже если `fn` запаникует, временный файл должен быть удалён, а исходный файл — остаться прежним. Паника при этом должна пролететь наружу: не глотайте её через `recover`.

## Что проверяют тесты

- создание и перезапись файла, пустые данные, относительное имя (`"rel.txt"`);
- точные права `0640`, `0600`, `0755`;
- если `fn` вернула ошибку, исходный файл не изменился и в каталоге не осталось мусора;
- если `fn` запаниковала, мусора тоже нет;
- несуществующий каталог и случай, когда целевой путь — каталог;
- 8 параллельных писателей и параллельный читатель: читатель никогда не должен увидеть смешанный или неполный файл.

## Подвохи

`defer f.Close()` без проверки ошибки — классическая ошибка именно при записи: отложенный сброс данных на диск может провалиться как раз в `Close`.

Временный файл в `os.TempDir()` не годится: `rename` между разными файловыми системами не атомарен или просто вернёт `EXDEV`.

Обратите внимание, что `filepath.Split("rel.txt")` даёт `dir == ""`, а `CreateTemp("")` создаст файл в системном temp-каталоге, а не рядом с целевым.

Для настоящей устойчивости к выключению питания после `rename` делают ещё `fsync` каталога.
