# Урок 3. Работа с файлами

С файлами работает почти любая программа, и почти любая делает это немного неправильно. Типичные истории выглядят так: конфиг оказался пустым после того, как процесс упал посреди записи; файл создался с правами `0644`, хотя в коде стояло `0666`; сервис упёрся в `too many open files`. Ни одна из этих проблем не связана с Go напрямую — все они про то, как устроены файловые системы. В этом уроке мы разберём API пакетов `os`, `io/fs` и `path/filepath` и заодно те места, где файловая система ведёт себя не так, как ожидаешь.

## Открытие: `os.Open`, `os.Create`, `os.OpenFile`

Файл открывают тремя функциями, и на самом деле это одна функция в трёх обличьях:

```go
f, err := os.Open("in.txt")        // = OpenFile(name, O_RDONLY, 0)
f, err := os.Create("out.txt")     // = OpenFile(name, O_RDWR|O_CREATE|O_TRUNC, 0666)
f, err := os.OpenFile("app.log", os.O_WRONLY|os.O_CREATE|os.O_APPEND, 0o644)
```

`os.Open` и `os.Create` покрывают самые частые случаи, а для всего остального есть `os.OpenFile` с явными флагами. Флаги складываются так: ровно один из режимов доступа `O_RDONLY`, `O_WRONLY`, `O_RDWR` плюс любые модификаторы из таблицы.

| Флаг | Смысл |
|---|---|
| `O_CREATE` | создать, если нет |
| `O_EXCL` | вместе с `O_CREATE` — ошибка, если файл уже есть (атомарная «блокировка»/уникальное имя) |
| `O_TRUNC` | обрезать до нуля при открытии |
| `O_APPEND` | каждая запись — в конец (атомарно для небольших записей на локальной ФС: удобно для логов из нескольких процессов) |
| `O_SYNC` | каждая запись ждёт физического сохранения |

Последний аргумент, `perm` (например, `0o644`), вызывает больше всего недоумения. Он используется только при создании файла и **урезается umask** процесса. Обычно umask равна `022`, поэтому вместо `0666` вы получите `0644`: биты, установленные в umask, просто снимаются. Если права нужны точно, вызовите после создания `os.Chmod` — к нему umask не применяется.

![umask снимает биты: `0666 &^ 022 = 0644`, и группа с остальными пользователями теряют право записи](img/umask.svg)

Ошибки открытия проверяют через `errors.Is` с сигнальными значениями `fs.ErrNotExist`, `fs.ErrExist` и `fs.ErrPermission`. Если нужны подробности, конкретный тип ошибки — `*fs.PathError{Op, Path, Err}`: в нём есть и операция, и путь, и исходная ошибка ОС.

## Закрытие и ошибки `Close`

Каждый открытый файл нужно закрыть, и для чтения стандартная идиома с `defer` работает без оговорок:

```go
f, err := os.Open(name)
if err != nil { return err }
defer f.Close() // для чтения — нормально
```

С записью всё интереснее. Игнорировать ошибку `Close` при записи нельзя, потому что ядро может отложить сообщение об ошибке записи до `close(2)`. Особенно этим грешат сетевые и пользовательские файловые системы вроде NFS и FUSE: `Write` отработал успешно, данные легли в буфер, а о том, что их некуда девать, вы узнаете только при закрытии. Если эту ошибку проглотить, программа сообщит об успехе, оставив на диске испорченный файл. Надёжный шаблон использует именованный результат:

```go
func writeReport(name string, data []byte) (err error) {
    f, err := os.Create(name)
    if err != nil { return err }
    defer func() {
        if cerr := f.Close(); cerr != nil && err == nil {
            err = cerr                      // именованный результат
        }
    }()
    _, err = f.Write(data)
    return err
}
```

Если такая конструкция кажется громоздкой, есть вариант проще: явный `return f.Close()` в конце функции плюс `defer f.Close()` как страховка на случай раннего выхода. Повторный `Close` вернёт ошибку, но её проигнорирует отложенный вызов, так что вреда от него нет.

Но даже успешный `Close` ещё не гарантирует, что данные физически на диске: скорее всего, они пока лежат в page cache ядра. Если вам нужна такая гарантия, например перед тем как ответить клиенту «сохранено», вызовите `f.Sync()`, то есть `fsync`.

## Атомарная запись: temp + rename

Теперь история про пустой конфиг. `os.WriteFile` открывает файл с `O_TRUNC` и пишет в него. Если процесс упадёт или выключится питание посередине, на диске останется пустой или обрезанный файл, а старое содержимое будет уже потеряно. Для важных файлов применяют другой приём: пишут во временный файл рядом и затем подменяют им оригинал.

```go
tmp, err := os.CreateTemp(filepath.Dir(name), ".tmp-*") // та же директория = та же ФС
// ... пишем в tmp ...
tmp.Chmod(perm)             // CreateTemp создаёт 0600; до Sync — чтобы права тоже попали на диск
tmp.Sync()                  // данные на диске
tmp.Close()                 // проверить ошибку!
os.Rename(tmp.Name(), name) // атомарная замена (POSIX rename(2))
// + fsync каталога, чтобы пережить отключение питания
```

Весь трюк держится на том, что `rename(2)` в POSIX атомарен. Читатели, открывающие `name`, видят либо старый файл, либо новый целиком, но никогда не промежуточное состояние. Если на любом шаге случилась ошибка, временный файл нужно удалить через `os.Remove(tmp.Name())`, чтобы не оставлять мусор.

Почему временный файл создают в той же директории, а не в `/tmp`? Потому что переименование между разными файловыми системами не работает и возвращает `EXDEV`, а `/tmp` часто смонтирован отдельно. На Windows `os.Rename` поверх существующего файла работает с Go 1.5 (через `MoveFileEx`), но гарантии атомарности там слабее.

![Все шаги до `Rename` меняют только временный файл, поэтому читатели `name` видят либо старую версию целиком, либо новую целиком](img/atomic-write.svg)

## Чтение и запись целиком

Для небольших файлов удобнее всего прочитать или записать их одним вызовом:

```go
data, err := os.ReadFile("config.json") // размер заранее берётся из Stat — обычно одна аллокация
err = os.WriteFile("out.txt", data, 0o644)
```

С большими файлами так делать не стоит: весь файл окажется в памяти. Их обрабатывают потоково, через `bufio` и `io.Copy`, как мы делали в первом уроке.

## Каталоги

Функции для работы с каталогами почти дословно повторяют привычные команды shell:

```go
os.Mkdir("a", 0o755)                 // ошибка, если родителя нет
os.MkdirAll("a/b/c", 0o755)          // как mkdir -p; нет ошибки, если уже есть
entries, err := os.ReadDir(".")      // []fs.DirEntry, отсортированы по имени
os.Remove(name)                      // файл или пустой каталог
os.RemoveAll(path)                   // рекурсивно; nil, если пути нет
dir, err := os.MkdirTemp("", "myapp-*") // уникальный временный каталог
defer os.RemoveAll(dir)
```

В тестах вместо `os.MkdirTemp` лучше использовать `t.TempDir()`: такой каталог удалится автоматически, когда тест завершится.

Обратите внимание, что `os.ReadDir` возвращает `fs.DirEntry`, а не `os.FileInfo`. Это сделано ради скорости: имя и тип файла приходят прямо из `readdir`, без отдельного `stat` для каждого файла. Метод `e.Info()` этот `stat` всё-таки делает, поэтому вызывайте его только тогда, когда действительно нужны размер или время изменения.

## Обход дерева: `filepath.WalkDir`

Чтобы обойти дерево каталогов, используют `filepath.WalkDir`. Он вызывает ваш колбэк для каждого файла и каталога, а колбэк возвращаемым значением управляет обходом:

```go
err := filepath.WalkDir(root, func(path string, d fs.DirEntry, err error) error {
    if err != nil {
        return err                    // ошибка доступа к path; можно вернуть nil и продолжить
    }
    if d.IsDir() && d.Name() == ".git" {
        return fs.SkipDir             // не заходить внутрь
    }
    if !d.IsDir() && filepath.Ext(path) == ".go" {
        fmt.Println(path)
    }
    return nil
})
```

`WalkDir` появился в Go 1.16 и работает быстрее старого `filepath.Walk`, который делал `lstat` для каждого файла. Внутри каталога элементы обходятся в лексикографическом порядке. Символические ссылки на каталоги не разыменовываются, так что зациклиться на них обход не может.

Тонкость с `fs.SkipDir`: если вернуть его для каталога, обход не зайдёт внутрь, а вот если вернуть его для файла, будет пропущен весь остаток родительского каталога. Чтобы пропустить один файл, достаточно вернуть `nil`. А чтобы остановить весь обход целиком, есть `fs.SkipAll`.

![Порядок вызовов колбэка `WalkDir` для дерева из примера: обход в глубину, имена сравниваются по байтам; для `.git` колбэк вернул `fs.SkipDir`, и его содержимое не посещается](img/walkdir-order.svg)

## `filepath` и `path`

В Go два пакета для работы с путями, и путать их нельзя. Пакет `path` всегда использует `/` как разделитель; он нужен для URL и путей внутри `fs.FS`, `embed` и zip-архивов. Пакет `path/filepath` использует разделитель текущей ОС (`\` на Windows) и предназначен для настоящих путей на диске. В нём есть всё необходимое: `filepath.Join`, `Base`, `Dir`, `Ext`, `Abs`, `Rel`, `Clean`, `Glob`, `Match`, `ToSlash`/`FromSlash`.

Никогда не склеивайте пути через `+ "/" +` — для этого есть `Join`. Но и `Join` не спасает от path traversal: `filepath.Join(base, userInput)` с `userInput = "../../etc/passwd"` спокойно выйдет за пределы `base`. Если путь приходит от пользователя, проверяйте его через `filepath.IsLocal(userInput)` (появилась в Go 1.20) или работайте через `fs.FS`, где `..` запрещён в принципе.

## Абстракция `fs.FS`

Функция, которая принимает имя каталога и сама открывает файлы, намертво привязана к диску. Тестировать её приходится с настоящими временными файлами, а переиспользовать для zip-архива или вшитых ресурсов не получится. Пакет `io/fs` предлагает интерфейс-абстракцию файловой системы, и он предельно прост:

```go
type FS interface { Open(name string) (fs.File, error) }
```

Пути в `fs.FS` устроены строже, чем на диске: только прямой слэш, без ведущего и завершающего `/`, без элементов `.` и `..`, а корень обозначается самой точкой `.`. Проверить путь можно функцией `fs.ValidPath`.

Базовый интерфейс умеет только открывать файлы, а дополнительные возможности реализация объявляет через расширенные интерфейсы: `fs.ReadFileFS`, `fs.ReadDirFS`, `fs.StatFS`, `fs.GlobFS`, `fs.SubFS`. Вам не нужно проверять их вручную: функции-помощники `fs.ReadFile`, `fs.ReadDir`, `fs.WalkDir`, `fs.Glob`, `fs.Sub` и `fs.Stat` работают с любой FS и сами используют быстрый путь, если реализация его предлагает.

Реализаций в стандартной библиотеке несколько:

- `os.DirFS("/srv/data")` — каталог на диске (защищает от `..`, но не от симлинков, ведущих наружу);
- `embed.FS` — файлы, вшитые в бинарник;
- `*zip.Reader` — содержимое zip-архива;
- `fstest.MapFS` — FS из `map` для тестов;
- `http.FS(fsys)` и `http.FileServerFS(fsys)` (Go 1.22) — раздача по HTTP.

Главный выигрыш от этой абстракции — тесты. Функция, принимающая `fs.FS`, а не имя каталога, тестируется вообще без диска:

```go
fsys := fstest.MapFS{
    "a.txt":     {Data: []byte("hello")},
    "dir/b.go":  {Data: []byte("package b"), Mode: 0o644},
    "empty":     {Mode: fs.ModeDir},
}
files, err := Find(fsys, ".", Options{Pattern: "*.go"})
```

![Код зависит только от интерфейса `fs.FS`, поэтому в продакшене работает с диском или `embed`, а в тестах — с `fstest.MapFS`](img/fs-abstraction.svg)

Если вы пишете собственную реализацию `fs.FS`, проверьте её через `fstest.TestFS(fsys, "a.txt")`: эта функция прогоняет набор проверок на соответствие контракту.

## `embed`: файлы внутри бинарника

Одна из самых приятных особенностей Go — деплой одного бинарного файла. Пакет `embed` позволяет сохранить это свойство, даже когда программе нужны шаблоны, статика или SQL-миграции: файлы вшиваются в бинарник на этапе компиляции.

```go
import "embed"

//go:embed templates/*.html static
var assets embed.FS

//go:embed version.txt
var version string
```

У директивы `//go:embed` есть несколько правил. Она ставится прямо над переменной уровня пакета типа `string`, `[]byte` или `embed.FS`. Пути отсчитываются от каталога пакета, и выйти за его пределы через `..` или за пределы модуля нельзя. Файлы, имена которых начинаются с `.` или `_`, пропускаются, если не указаны явно или не использован префикс `all:`. Сам `embed.FS` доступен только для чтения и реализует `fs.FS`, `ReadDirFS` и `ReadFileFS`, так что с ним работают все помощники из `io/fs`.

## Как устроено внутри

`*os.File` хранит дескриптор ОС. У него есть финализатор, который закроет дескриптор при сборке мусора, но полагаться на это нельзя: дескрипторы закончатся раньше, чем сработает GC, и вы получите `too many open files`.

Операции с обычными файлами выполняются блокирующими системными вызовами. Пока горутина ждёт диск, планировщик отдаёт P другому потоку ОС. Поэтому тысячи горутин, одновременно читающих файлы, порождают много потоков ОС — в отличие от сетевого ввода-вывода, который обслуживает netpoller.

## Типичные ошибки

1. Писать `defer f.Close()` в цикле по тысячам файлов: закрытие произойдёт только в конце функции. Тело цикла выносят в отдельную функцию.
2. Игнорировать ошибку `Close` при записи.
3. Ожидать, что `perm` в `OpenFile` задаёт права точно, и забыть про umask.
4. Сохранять важные конфиги через `os.WriteFile` вместо схемы temp + rename.
5. Использовать `filepath` для путей внутри `embed` и `fs.FS`: на Windows это сломается.
6. Не проверять `err` в колбэке `WalkDir`.
