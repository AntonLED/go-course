# Урок 1. Работа с потоками ввода/вывода

Откройте любой пакет стандартной библиотеки, который имеет дело с данными, — `os`, `net`, `net/http`, `compress/gzip`, `crypto`, `hash`, `bytes`, — и вы увидите одни и те же два интерфейса: `io.Reader` и `io.Writer`. Файл, сетевое соединение, тело HTTP-ответа, распаковщик gzip, шифр и хэш-функция выглядят для остального кода одинаково: из них можно читать или в них можно писать. Поэтому стоит один раз как следует разобраться в `io.Reader` и `io.Writer` — и половина стандартной библиотеки становится понятной без документации.

## Базовые интерфейсы

Интерфейсы в пакете `io` крошечные, по одному методу. Большие типы получаются из них встраиванием:

```go
type Reader interface { Read(p []byte) (n int, err error) }
type Writer interface { Write(p []byte) (n int, err error) }
type Closer interface { Close() error }
type Seeker interface { Seek(offset int64, whence int) (int64, error) }

type ReadCloser interface { Reader; Closer }   // http.Response.Body
type ReadSeeker interface { Reader; Seeker }   // *os.File, *strings.Reader, *bytes.Reader
```

Сигнатура `Read` выглядит непривычно: функция не возвращает прочитанные данные, а принимает буфер `p` от вызывающего и заполняет его. Так читатель не выделяет память на каждый вызов, и один и тот же буфер можно гонять по кругу сколько угодно раз.

### Контракт `Read`

Документацию к `io.Reader` стоит прочитать целиком: в ней описан контракт, и большинство ошибок при работе с потоками — это его нарушения.

Во-первых, `Read` вправе вернуть меньше байт, чем `len(p)`, даже если данные в потоке ещё есть. Сетевое соединение отдаст столько, сколько успело прийти, и один вызов вовсе не обязан прочитать «всё».

Во-вторых, `Read` может одновременно вернуть `n > 0` и `err != nil` — например, последние байты вместе с `io.EOF`. Отсюда правильный порядок действий: сначала обработать `p[:n]` и только потом смотреть на ошибку. Если сделать наоборот, хвост данных тихо потеряется.

В-третьих, `io.EOF` — это не ошибка, а сигнал о том, что поток закончился. Сравнивать его можно и через `errors.Is(err, io.EOF)`, и через `==`: по контракту `Read` возвращает сам `io.EOF`, а не обёрнутую ошибку. Но ваши собственные функции-обёртки вокруг чтения вполне могут его обернуть, и тогда поможет только `errors.Is`.

Наконец, результат `(0, nil)` допустим. Документация не рекомендует так делать, кроме случая `len(p) == 0`, но если такое пришло, это значит «ничего не произошло», а вовсе не конец потока.

Всё это складывается в канонический цикл чтения:

```go
buf := make([]byte, 4096)
for {
    n, err := r.Read(buf)
    process(buf[:n])            // сначала данные!
    if errors.Is(err, io.EOF) { break }
    if err != nil { return err }
}
```

Писать такой цикл руками приходится нечасто, потому что для типовых задач есть готовые функции. Если нужно прочитать ровно N байт (заголовок фиксированной длины, например), берите `io.ReadFull(r, buf)`: она вызывает `Read` столько раз, сколько потребуется, и возвращает `io.ErrUnexpectedEOF`, если поток закончился на середине, и `io.EOF`, если не удалось прочитать ни байта. А `io.ReadAll` читает поток целиком в память — удобно, но осторожно с размером: на недоверенных данных это прямой путь к исчерпанию памяти.

### Контракт `Write`

С записью проще. `Write` обязан вернуть ошибку, если записал `n < len(p)`, поэтому циклы «дописывания остатка», знакомые по C, в Go не нужны. А вот проверять ошибку нужно всегда.

## `io.Copy` и оптимизации `WriterTo`/`ReaderFrom`

Самая частая операция с потоками — переложить всё из одного в другой. Для этого есть `io.Copy`:

```go
n, err := io.Copy(dst, src) // до EOF; EOF ошибкой не считается
```

Внутри `io.Copy` устроен хитрее, чем цикл с буфером. Сначала он проверяет, не реализует ли `src` интерфейс `io.WriterTo`, и если да, просто вызывает `src.WriteTo(dst)`. Если нет, смотрит, не реализует ли `dst` интерфейс `io.ReaderFrom`, и тогда вызывает `dst.ReadFrom(src)`. И только когда ни то ни другое не подошло, копирует сам, циклом через буфер в 32 КиБ.

Зачем такие сложности? Источник или приёмник часто знает способ скопировать данные эффективнее, чем общий цикл. Благодаря этому `io.Copy(tcpConn, file)` на Linux превращается в системный вызов `sendfile(2)`, и данные вообще не копируются в пространство пользователя, а `bytes.Buffer.ReadFrom` сам растит свой буфер по мере чтения.

![Как `io.Copy` выбирает путь: сначала `WriterTo` у источника, потом `ReaderFrom` у приёмника, и только если их нет — цикл через буфер 32 КиБ](img/io-copy-fastpath.svg)

У `io.Copy` есть два родственника. `io.CopyBuffer(dst, src, buf)` использует ваш буфер вместо своего, что полезно, когда буферы берутся из пула. `io.CopyN(dst, src, n)` копирует ровно n байт.

## Композиция: обёртки над Reader и Writer

Настоящая сила маленьких интерфейсов проявляется в композиции. Все обёртки в `io` принимают интерфейс и возвращают интерфейс, поэтому их можно собирать в конвейер, как трубы в shell:

| Функция | Что делает |
|---|---|
| `io.LimitReader(r, n)` | отдаёт не больше n байт (защита от гигантских тел запросов) |
| `io.TeeReader(r, w)` | всё прочитанное из r параллельно пишет в w (хэш «на лету») |
| `io.MultiReader(r1, r2...)` | склеивает потоки последовательно |
| `io.MultiWriter(w1, w2...)` | пишет в несколько приёмников (файл + stdout) |
| `io.NewSectionReader(ra, off, n)` | окно $[\mathit{off}, \mathit{off}+n)$ поверх `io.ReaderAt` |
| `io.Pipe()` | синхронная труба: запись блокируется, пока кто-то не прочитает |
| `io.NopCloser(r)` | добавить пустой `Close` |
| `io.Discard` | Writer-«чёрная дыра» |

Вот как это выглядит в деле. Допустим, нужно скачать сжатый файл, проверить его SHA-256 и распаковать — и не хочется ни держать его целиком в памяти, ни сохранять во временный файл:

```go
// Скачать, посчитать SHA-256 и распаковать — за один проход, без временных файлов.
h := sha256.New()
zr, err := gzip.NewReader(io.TeeReader(io.LimitReader(resp.Body, 100<<20), h))
if err != nil { return err }
defer zr.Close()
if _, err := io.Copy(dst, zr); err != nil { return err }
sum := h.Sum(nil)
```

Читать такой код лучше изнутри наружу. `LimitReader` не даёт телу ответа оказаться больше 100 МиБ, `TeeReader` отдаёт каждый прочитанный сжатый байт в хэш, а `gzip.NewReader` распаковывает. Двигателем служит `io.Copy`: он тянет данные вызовами `Read`, и каждый такой вызов проходит через всю цепочку.

![Конвейер из примера: `io.Copy` тянет данные вызовами `Read` через всю цепочку, а `TeeReader` по дороге отдаёт сжатые байты в хэш — один проход, без временных файлов](img/io-pipeline.svg)

Обратите внимание, что `gzip.NewReader` сам является `io.Reader`, так что распаковка — просто ещё одно звено конвейера. Симметрично устроен и `gzip.NewWriter(w)`, но с ним есть ловушка: его обязательно нужно закрыть через `Close()`, иначе хвост архива так и не допишется, и файл получится битым.

### Своя обёртка

Написать собственное звено конвейера несложно: достаточно одного метода `Read`, который вызывает `Read` у внутреннего потока и что-то делает с результатом.

```go
type upperReader struct{ r io.Reader }

func (u upperReader) Read(p []byte) (int, error) {
    n, err := u.r.Read(p)
    for i := range p[:n] {                     // работаем только с p[:n]
        if 'a' <= p[i] && p[i] <= 'z' { p[i] -= 'a' - 'A' }
    }
    return n, err                              // ошибку пробрасываем как есть
}
```

Здесь соблюдены оба правила контракта: обрабатываются только `p[:n]`, а ошибка пробрасывается без изменений, в том числе вместе с данными.

Но у побайтовой обработки есть подвох. Она ломает многобайтовые руны UTF-8, если преобразование зависит от руны целиком, как `unicode.ToUpper` для кириллицы. Руна запросто окажется разрезанной между двумя вызовами `Read`, и тогда понадобится буфер для недочитанного «хвоста» или чтение через `bufio.Reader.ReadRune`.

## `io.Pipe`: соединить писателя и читателя

Бывает, что один код умеет только писать в `io.Writer`, а другой — только читать из `io.Reader`. Классический пример: вы генерируете JSON энкодером, а `http.Post` хочет тело запроса в виде `io.Reader`. Можно сначала записать всё в `bytes.Buffer`, но тогда всё тело окажется в памяти. `io.Pipe` соединяет их напрямую:

```go
pr, pw := io.Pipe()
go func() {
    enc := json.NewEncoder(pw)
    for _, item := range items {
        if err := enc.Encode(item); err != nil { pw.CloseWithError(err); return }
    }
    pw.Close()
}()
http.Post(url, "application/x-ndjson", pr) // тело генерируется на лету
```

Труба ничего не буферизует: каждый `Write` ждёт, пока соответствующие вызовы `Read` на другом конце не заберут данные. Поэтому писатель и читатель должны жить в разных горутинах.

Из этого же вытекает главное правило: писатель обязан закрыть трубу. Вызов `Close` даёт читателю `io.EOF`, а `CloseWithError(err)` передаёт ему `err`. Если писатель забудет это сделать, читатель зависнет навсегда. Верно и обратное: если читатель ушёл раньше времени, он должен закрыть свой конец через `pr.Close()`, и тогда очередной `Write` вернёт `io.ErrClosedPipe`, а не будет ждать вечно.

![`io.Pipe` без буфера: `Write` ждёт, пока `Read` на другой стороне заберёт байты; закрытие одного конца сообщает о нём другому](img/io-pipe.svg)

## `bufio`: буферизация

Каждый вызов `Read` или `Write` у файла — это системный вызов, а системный вызов ради десяти байт обходится дорого. Пакет `bufio` решает эту проблему: `bufio.Reader` и `bufio.Writer` держат в памяти буфер (по умолчанию 4 КиБ) и обращаются к нижележащему потоку крупными кусками.

С `bufio.Writer` связана самая частая ошибка при работе с потоками — забытый `Flush`. Пока буфер не заполнен, данные лежат в памяти, и если их не сбросить явно, последние килобайты вывода просто не дойдут до файла. Причём даже `defer` не спасает полностью:

```go
bw := bufio.NewWriter(f)
defer bw.Flush() // ошибка-ловушка: ошибку Flush так теряем
...
if err := bw.Flush(); err != nil { return err } // правильно — явно в конце
```

Отложенный `Flush` выполнится, но его ошибку (например, «диск переполнен») никто не увидит. Поэтому `Flush` вызывают явно в конце и проверяют результат.

![`bufio.Writer` копит мелкие записи и делает один `write(2)` на полный буфер; хвост меньше буфера остаётся в памяти, пока не вызван `Flush`](img/bufio-writer-flush.svg)

`bufio.Reader` полезен не только скоростью, но и удобными методами. `ReadString('\n')` и `ReadBytes` читают до разделителя, `ReadRune` — одну руну UTF-8. `Peek(n)` позволяет посмотреть на следующие байты, не потребляя их: так, например, определяют, что поток сжат gzip, по магическим байтам `1f 8b`. Есть ещё `ReadLine`, но это низкоуровневый метод, и пользоваться им лучше не стоит.

![Внутри `bufio.Reader`: непрочитанное лежит в `buf[r:w]`, чтения сдвигают `r`, `fill()` дочитывает из источника крупным куском, а `Peek` смотрит без сдвига](img/bufio-reader.svg)

### `bufio.Scanner` и лимит токена

Для построчного чтения чаще всего используют `bufio.Scanner`:

```go
sc := bufio.NewScanner(r)
for sc.Scan() {
    line := sc.Text() // без '\n' (и без '\r' перед ним)
}
if err := sc.Err(); err != nil { ... } // обязательно! Scan()==false бывает и при ошибке
```

Цикл выглядит безобидно, но в нём прячется главный подвох сканера. Максимальный размер токена по умолчанию равен `bufio.MaxScanTokenSize`, то есть **64 КиБ**. Если строка длиннее, `Scan()` вернёт `false` — ровно так же, как в конце файла, — а `Err()` вернёт `bufio.ErrTooLong`. Если ошибку после цикла не проверить, программа молча обработает половину файла и сочтёт работу выполненной. Минифицированный JSON, записанный в одну строку, превышает этот лимит очень легко. Лимит поднимают методом `Buffer`:

```go
sc.Buffer(make([]byte, 0, 64*1024), 10<<20) // до 10 МиБ на строку
```

По умолчанию сканер режет поток на строки, но режим разбиения можно поменять: `sc.Split(bufio.ScanWords)`, `ScanRunes`, `ScanBytes` или своя `SplitFunc`. И ещё одна тонкость: `Text()` копирует байты в новую строку, а `Bytes()` возвращает срез внутреннего буфера, который перезапишется на следующем `Scan`. Если сохраняете результат `Bytes()` на потом, скопируйте его.

## Ошибки

В пакете `io` определено несколько ошибок-сигналов, и каждая означает вполне определённую ситуацию:

- `io.EOF` — нормальный конец потока;
- `io.ErrUnexpectedEOF` — поток кончился посреди структуры (так отвечают `ReadFull`, `binary.Read`, gzip с обрезанным хвостом);
- `io.ErrShortWrite` — Writer записал меньше, чем просили, и не сообщил об ошибке, то есть это баг в самом Writer;
- `io.ErrClosedPipe` — запись в закрытую трубу.

## `Seek` и `ReaderAt`

Не все потоки читаются строго от начала к концу. Метод `Seek(off, whence)` перемещает текущую позицию, а `whence` говорит, откуда отсчитывать смещение: `io.SeekStart`, `io.SeekCurrent` или `io.SeekEnd`. Маленький полезный трюк: `rs.Seek(0, io.SeekEnd)` возвращает размер потока.

У `Seek` есть недостаток: позиция одна на весь поток, поэтому читать с разных мест из нескольких горутин через него нельзя. Для этого существует `io.ReaderAt` с методом `ReadAt(p, off)`, который не меняет текущую позицию и безопасен для параллельного чтения. `*os.File` реализует оба интерфейса. На произвольном доступе построены `tail`, чтение zip-архивов (их каталог лежит в конце файла) и HTTP Range-запросы.

## Как устроено внутри

`os.File.Read` в конечном счёте выполняет системный вызов `read(2)`, но по-разному для разных дескрипторов. Сокеты и трубы работают через netpoller, а обычные файлы читаются блокирующим syscall: горутина уходит в системный вызов вместе со своим потоком M, а планировщик передаёт освободившийся P другому M, чтобы остальные горутины не простаивали.

Потоки в памяти устроены куда проще. `strings.Reader` и `bytes.Reader` читают из готовой строки или среза без аллокаций, а `bytes.Buffer` — растущий буфер, который одновременно является и Reader, и Writer.

Может показаться, что за гибкость интерфейсов приходится платить скоростью. Интерфейсное значение `io.Reader` — это пара (тип, указатель), и вызов `Read` через него действительно косвенный, но его стоимость ничтожна по сравнению с любым системным вызовом.

## Типичные ошибки

Почти все ошибки ниже мы уже разобрали по ходу урока; здесь они собраны вместе, чтобы по списку было удобно проверять свой код:

1. Игнорировать `n` и обрабатывать весь буфер `p`.
2. Проверять `err` до обработки `p[:n]`.
3. Вызывать `io.ReadAll` на недоверенных данных без `LimitReader` и получить OOM.
4. Читать длинные строки через `bufio.Scanner` без `Buffer` и не проверять `sc.Err()`.
5. Забыть `Flush` у `bufio.Writer` или `Close` у `gzip.Writer`.
6. Не закрыть `io.Pipe` на стороне писателя, из-за чего читатель блокируется навсегда.
7. Создать два `bufio.Reader` поверх одного потока: первый «съест» данные в свой буфер, и второй их уже не увидит.
