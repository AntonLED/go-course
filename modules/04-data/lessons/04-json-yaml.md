# Урок 4. Работа с JSON, YAML

JSON — основной язык, на котором современные сервисы разговаривают друг с другом, а YAML — язык, на котором люди пишут конфиги. Пакет `encoding/json` устроен так, что простые случаи решаются одной строкой, и поэтому легко не заметить его тонкости: числа, которые молча теряют точность, поля, которые не обнуляются, методы, которые не вызываются. С YAML ещё интереснее: там строка `NO` может оказаться булевым значением. Разберём по порядку.

## `encoding/json`: основы

Сериализация управляется тегами полей структуры. Вот пример, в котором собраны почти все варианты:

```go
type User struct {
    ID        int64     `json:"id"`
    Name      string    `json:"name"`
    Email     string    `json:"email,omitempty"` // не выводить нулевое значение
    Password  string    `json:"-"`               // никогда не сериализовать
    Balance   int64     `json:"balance,string"`  // число в кавычках: "balance":"100"
    CreatedAt time.Time `json:"created_at"`      // RFC 3339
    internal  int                               // неэкспортируемые поля игнорируются
}

b, err := json.Marshal(u)             // []byte
b, err = json.MarshalIndent(u, "", "  ")
err = json.Unmarshal(b, &u)           // обязательно указатель
```

Пакет работает через рефлексию и поэтому видит только экспортируемые поля. Поле `internal` для него не существует ни при кодировании, ни при декодировании. А в `Unmarshal` нужно передавать указатель: иначе функции некуда записать результат.

Теперь о самих тегах. Имя поля в JSON задаётся как `json:"name"`, а без тега используется имя поля как есть (`Name`). При декодировании имена сопоставляются без учёта регистра: ключ `"NAME"` попадёт в поле `Name`, хотя точному совпадению отдаётся предпочтение.

Опция `omitempty` пропускает «пустые» значения: `false`, `0`, `""`, nil-указатель или nil-интерфейс, пустые слайс и map. Но пустую структуру и `time.Time{}` она не пропускает, потому что структура для неё никогда не бывает пустой. Опция `omitzero`, которая решает эту проблему, появилась только в Go 1.24.

Тег `"-"` полностью исключает поле из сериализации. Если же вам по какой-то причине нужно поле с именем `-`, пишите `"-,"`.

Наконец, `,string` для чисел и bool кладёт значение внутрь JSON-строки. Это полезно для `int64` больше $2^{53}$: JavaScript хранит все числа как float64 и такие значения теряет, а строку передаст без изменений.

![Что делает `json.Marshal` с каждым полем `User` из примера: имя берётся из тега, `omitempty` и `"-"` убирают поле, `,string` кладёт число в кавычки](img/json-tags.svg)

Отдельная история — декодирование в `any`, когда структура данных заранее неизвестна. Объект превращается в `map[string]any`, массив — в `[]any`, строка — в `string`, bool — в `bool`, null — в `nil`, а **любое число становится `float64`**. Отсюда два классических бага: `id: 12345678901234567890` теряет точность, а `m["count"].(int)` паникует, потому что там лежит `float64`, а не `int`. Если числа нужны без потерь, включите `UseNumber` у декодера:

```go
dec := json.NewDecoder(r)
dec.UseNumber()          // числа в any станут json.Number (строка), без потерь
var v map[string]any
dec.Decode(&v)
n, _ := v["id"].(json.Number).Int64()
```

У пакета есть и другие особенности, о которых полезно знать заранее.

`[]byte` кодируется не массивом чисел, а base64-строкой. Ключи map при кодировании сортируются, поэтому вывод детерминирован и его можно сравнивать в тестах. Ключами при этом могут быть строки, целые числа или типы, реализующие `encoding.TextMarshaler`.

nil-слайс кодируется как `null`, а пустой слайс — как `[]`. Если API обещает клиентам массив, инициализируйте поле как `[]T{}`, иначе фронтенд однажды получит `null` и упадёт.

HTML-символы `<>&` внутри строк экранируются (`<` превращается в `<`, `&` — в `&`). Это защита на случай, если JSON вставят в HTML-страницу. Отключить экранирование можно только у `Encoder`, вызовом `enc.SetEscapeHTML(false)`.

Встроенная (anonymous) структура «поднимает» свои поля на верхний уровень JSON-объекта. Встроенный интерфейс так не делает: он становится обычным полем с именем типа.

И последнее, самое коварное. Неизвестные поля при декодировании молча игнорируются, а поля, которых нет во входном JSON, остаются такими, какими были: `Unmarshal` не обнуляет структуру. Если переиспользовать одну переменную в цикле, данные из прошлой итерации «протекут» в следующую.

## Свой формат: `Marshaler` и `Unmarshaler`

Стандартное представление подходит не всегда. Например, `time.Duration` кодируется числом наносекунд, а в конфиге хочется видеть `"1m30s"`. Для этого тип реализует `json.Marshaler` и `json.Unmarshaler`:

```go
type Duration time.Duration

func (d Duration) MarshalJSON() ([]byte, error) {           // на значении
    return json.Marshal(time.Duration(d).String())         // "1m30s"
}

func (d *Duration) UnmarshalJSON(b []byte) error {         // на указателе
    var s string
    if err := json.Unmarshal(b, &s); err != nil { return err }
    v, err := time.ParseDuration(s)
    *d = Duration(v)
    return err
}
```

Почему методы объявлены на разных получателях? `UnmarshalJSON` обязан менять получателя, поэтому ему нужен указатель. С `MarshalJSON` наоборот: если объявить его на указателе, он не вызовется для поля-значения внутри структуры, которую передали в `Marshal` по значению, — такое поле неадресуемо, и взять на него указатель пакет не может. Вместо строки вы получите число наносекунд, причём без всякой ошибки. Поэтому `MarshalJSON` объявляют на значении.

Вторая ловушка — бесконечная рекурсия. Если внутри `(t T) MarshalJSON` вызвать `json.Marshal(t)`, пакет снова увидит метод `MarshalJSON` и вызовет его, и так до переполнения стека. Лечится это локальным типом с теми же полями, но без методов:

```go
func (u User) MarshalJSON() ([]byte, error) {
    type plain User                                     // те же поля, нет методов
    return json.Marshal(struct {
        plain
        Kind string `json:"kind"`
    }{plain(u), "user"})
}
```

Если значение представляется обычной строкой, есть способ проще: реализовать `encoding.TextMarshaler` (методы `MarshalText` и `UnmarshalText`). Пакет json использует его и для значений, и для ключей map.

## `json.RawMessage` и полиморфный JSON

Часто в одном потоке приходят события разных типов, а какой именно тип перед нами, говорит поле-дискриминатор. Разобрать такое в одну структуру нельзя, потому что форма поля `data` зависит от `type`. На помощь приходит `json.RawMessage` — это `[]byte`, который пакет не разбирает, а копирует как есть. Разбор идёт в два прохода:

```go
type Envelope struct {
    Type string          `json:"type"`
    Data json.RawMessage `json:"data"`
}

var env Envelope
json.Unmarshal(b, &env)
switch env.Type {
case "login":
    var e Login
    err = json.Unmarshal(env.Data, &e)
case "purchase":
    ...
default:
    err = fmt.Errorf("неизвестный тип %q", env.Type)
}
```

![Полиморфный JSON в два прохода: `Envelope` читает `type`, а `data` сохраняет сырыми байтами `RawMessage`, которые потом разбираются в нужный тип](img/json-polymorphic.svg)

Бывает, что `type` лежит на одном уровне с остальными полями: `{"type":"login","user":"ann"}`. Тогда сначала декодируют только `struct{ Type string }`, а потом весь объект целиком в конкретный тип. Если при этом включён `DisallowUnknownFields`, поле `type` окажется для типа `Login` «неизвестным», и декодирование упадёт. Выход — обёртка ``struct{ Type string `json:"type"`; *Login }``, в которой для `type` есть своё место.

## Потоковая обработка: `Decoder` и `Encoder`

`json.Unmarshal` работает с готовым срезом байт, а `json.Decoder` читает из `io.Reader` и умеет больше:

```go
dec := json.NewDecoder(r)
dec.DisallowUnknownFields()     // опечатка в конфиге → ошибка, а не тихое игнорирование
for {
    var ev Event
    if err := dec.Decode(&ev); err == io.EOF { break } else if err != nil { return err }
    handle(ev)
}
```

Этот цикл читает поток значений, идущих подряд, — именно так выглядит формат JSON Lines (он же NDJSON). Заодно включён `DisallowUnknownFields`: опечатка в имени поля конфига станет ошибкой, а не будет тихо проигнорирована.

А что делать, если на входе один огромный массив на несколько гигабайт? Читать его через `Unmarshal` целиком нельзя, но декодер позволяет пройти по нему токенами:

```go
tok, _ := dec.Token()            // json.Delim('[')
for dec.More() {
    var item Item
    if err := dec.Decode(&item); err != nil { return err }
}
dec.Token()                      // json.Delim(']')
```

Расход памяти здесь $O(\text{размер одного элемента})$, а не всего массива.

Есть и тонкое различие между двумя способами. `json.Unmarshal` требует, чтобы во входе было ровно одно значение, и считает ошибкой мусор после него. `Decoder.Decode` читает первое значение и оставляет всё остальное в буфере. Поэтому, если нужно убедиться, что после значения ничего нет, придётся вызвать ещё один `Token()` и ожидать от него `io.EOF`.

![Разбор большого массива токенами: `Token` читает скобки, `More` и `Decode` берут по одному элементу, так что в памяти только текущий](img/json-token-stream.svg)

Симметрично устроен и `Encoder`. Вызов `json.NewEncoder(w).Encode(v)` пишет значение и символ `\n` после него, что как раз удобно для NDJSON. Для красивого вывода с отступами есть `SetIndent`.

## Как устроено внутри

`encoding/json` построен на рефлексии. Для каждого типа пакет один раз строит «кодировщик» — список полей с разобранными тегами — и кэширует его в `sync.Map`. Поэтому первый `Marshal` значения нового типа заметно дороже последующих. Декодер работает в два этапа: сначала сканирует ввод конечным автоматом, проверяя, что это корректный JSON, и только потом заполняет значения.

Такой подход медленнее кодогенерации (easyjson, ffjson) и специализированных библиотек вроде `goccy/go-json` и `bytedance/sonic`. В Go 1.25 экспериментально появился пакет `encoding/json/v2`.

## YAML

YAML — надмножество JSON, в которое добавлены отступы вместо скобок, комментарии и якоря. Стандартной библиотеки для YAML в Go нет; стандартом де-факто стал `gopkg.in/yaml.v3`. В курсе он недоступен, поэтому API приводим для справки:

```go
import "gopkg.in/yaml.v3"

type Config struct {
    Name    string            `yaml:"name"`
    Port    int               `yaml:"port,omitempty"`
    DB      DBConfig          `yaml:"db"`
    Extra   map[string]string `yaml:",inline"`   // «поднять» поля
    Secret  string            `yaml:"-"`
}

err := yaml.Unmarshal(data, &cfg)
out, err := yaml.Marshal(cfg)

dec := yaml.NewDecoder(r)
dec.KnownFields(true)   // аналог DisallowUnknownFields
```

Как видите, API почти повторяет `encoding/json`, только теги называются `yaml`. Собственную логику разбора тип задаёт методом `UnmarshalYAML(value *yaml.Node) error`. Тип `yaml.Node` открывает доступ к самому дереву документа, с номерами строк и комментариями, так что через него можно даже программно менять конфиг, сохраняя комментарии.

### Подводные камни YAML

YAML удобен для человека, но у его удобства есть обратная сторона: парсер угадывает тип значения по его виду, и угадывает не всегда так, как вы ожидаете. Посмотрите на этот файл:

```yaml
defaults: &defaults        # якорь
  timeout: 5s
  retries: 3
prod:
  <<: *defaults            # merge key: подмешать поля
  retries: 10

country: NO                # YAML 1.1 (yaml.v2, PyYAML): false! «норвежская проблема»
                           # yaml.v3 в any/string даёт строку "NO" (bool по 1.2 — только
                           # true/false), но в поле типа bool по-прежнему примет NO как false
version: 1.10              # float 1.1, а не строка "1.10"
zip: 01234                 # в YAML 1.1 — восьмеричное число 668 (yaml.v3 ради совместимости тоже)
time: 12:30:00             # в YAML 1.1 — шестидесятеричное число 45000
empty:                     # null, а не ""
port: "8080"               # строка
```

Первые строки показывают полезную возможность: якорь `&defaults` и ключ слияния `<<: *defaults` подмешивают общие настройки в секцию `prod`, а явно заданное там `retries: 10` их перекрывает.

Дальше начинаются сюрпризы. Код страны Норвегии `NO` парсеры YAML 1.1 (yaml.v2, PyYAML) читают как булево `false` — это знаменитая «норвежская проблема». yaml.v3 при разборе в `any` или в строку уже вернёт строку `"NO"`, потому что по YAML 1.2 булевы значения — только `true` и `false`, но в поле типа `bool` по-прежнему примет `NO` как `false`. Номер версии `1.10` превращается в число с плавающей точкой `1.1`, и хвостовой ноль теряется. Почтовый индекс `01234` с ведущим нулём в YAML 1.1 читается как восьмеричное число $1234_8 = 668$, и yaml.v3 ради совместимости поступает так же. Время `12:30:00` в YAML 1.1 оказывается шестидесятеричным числом: $12 \cdot 3600 + 30 \cdot 60 = 45000$. А пустое значение — это `null`, а не пустая строка.

Отсюда простое правило: всё, что должно быть строкой, берите в кавычки. Кроме того, табуляция в отступах запрещена, а сами отступы значимы, поэтому «съехавший» на один пробел ключ молча меняет структуру документа. Для конфигов с жёсткой схемой многие по этим причинам выбирают JSON, TOML или HCL.

![Отступы задают вложенность отображений; якорь `&defaults` и `<<: *defaults` подмешивают поля в `prod`, а явное `retries: 10` их перекрывает](img/yaml-merge.svg)

Ещё одна особенность касается разбора в `map[string]any`. yaml.v3 кладёт туда `int`, `float64`, `bool`, `string`, `nil`, `[]any` и `map[string]any`. В yaml.v2 вложенные отображения были `map[any]any`, а такие map не сериализуются в JSON. Из-за этого распространился приём «YAML в `map[string]any`, затем в JSON, затем в структуру»: так работает `sigs.k8s.io/yaml`, и так поступает Kubernetes.

## Типичные ошибки

1. Вызвать `json.Unmarshal(b, v)` без `&` и получить `InvalidUnmarshalError`.
2. Удивляться, что неэкспортируемые поля «пропадают»: json их просто не видит.
3. Писать `m["n"].(int)` после декодирования в `any` и получать панику, потому что там `float64`.
4. Ставить `omitempty` на структуру или `time.Time` и ждать, что поле исчезнет.
5. Объявить `MarshalJSON` на указателе, а в `Marshal` передать значение.
6. Отдавать клиентам `null` вместо `[]` из-за nil-слайса.
7. Читать огромный массив через `Unmarshal` целиком.
