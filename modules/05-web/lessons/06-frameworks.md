# Урок 6. Популярные фреймворки для HTTP

Внешние модули в курсе недоступны, поэтому код в этом уроке предназначен для чтения, а не для запуска. Зато в задаче вы соберёте собственный мини-фреймворк и на своём опыте увидите, что именно дают эти библиотеки и где заканчивается их магия.

## Карта экосистемы

Фреймворков для Go много, но на собеседованиях и в реальных проектах чаще всего встречаются пять. Главное, чем они различаются, — насколько они совместимы со стандартным `net/http`.

| | Совместим с `net/http` | Роутер | Контекст | Особенности |
|---|---|---|---|---|
| **chi** | полностью (`http.Handler`) | radix-дерево | `context.Context` + `chi.URLParam` | лёгкий, идиоматичный, богатый набор middleware |
| **gorilla/mux** | полностью | регулярки, host/header-матчеры | `mux.Vars(r)` | классика; проект архивировался в 2022, затем был возрождён; медленнее |
| **gin** | частично (`gin.WrapH`) | httprouter (radix) | `*gin.Context` | самый популярный, биндинг/валидация (validator), быстрый |
| **echo** | частично | radix | `echo.Context` | хендлеры возвращают `error`, централизованный `HTTPErrorHandler` |
| **fiber** | **нет** (fasthttp) | radix | `*fiber.Ctx` | API как у Express.js, очень быстрый на микробенчмарках |

![Граница совместимости — интерфейс `http.Handler`: ServeMux, chi и gorilla/mux живут на нём целиком, gin и echo реализуют его снаружи, но внутри у них свой контекст, а fiber стоит на отдельном сервере fasthttp](img/frameworks-stack.svg)

### chi

chi ближе всех к стандартной библиотеке. По сути, это роутер с удобными группами и набором готовых middleware:

```go
r := chi.NewRouter()
r.Use(middleware.RequestID, middleware.Logger, middleware.Recoverer)
r.Route("/api/v1", func(r chi.Router) {
    r.Use(authMiddleware)
    r.Get("/users/{id}", func(w http.ResponseWriter, r *http.Request) {
        id := chi.URLParam(r, "id")
        render.JSON(w, r, getUser(id))
    })
})
http.ListenAndServe(":8080", r)
```

Все сигнатуры здесь стандартные, и любой `func(http.Handler) http.Handler` работает как middleware без адаптеров. После выхода Go 1.22 отличие chi от `ServeMux` свелось к группам (`Route`/`Group`), синтаксическому сахару и коллекции готовых middleware.

### gin

gin — самый популярный фреймворк, и устроен он иначе. Вместо пары `w, r` хендлер получает собственный `*gin.Context`, а в комплекте идут биндинг и валидация запросов:

```go
r := gin.New()
r.Use(gin.Logger(), gin.Recovery())
api := r.Group("/api", authRequired())
api.POST("/users", func(c *gin.Context) {
    var in struct {
        Email string `json:"email" binding:"required,email"`
    }
    if err := c.ShouldBindJSON(&in); err != nil {
        c.JSON(http.StatusBadRequest, gin.H{"error": err.Error()})
        return
    }
    c.JSON(http.StatusCreated, gin.H{"id": 1})
})
r.Run(":8080") // без таймаутов! лучше http.Server{Handler: r, ...}
```

Про `r.Run` вы уже знаете из первого урока: внутри он вызывает сервер без таймаутов, поэтому в продакшене gin передают в `http.Server` как обычный Handler.

С `*gin.Context` связана одна тонкость. Он переиспользуется через пул, поэтому **нельзя** передавать его в горутину, которая живёт дольше запроса: к тому моменту контекст может уже обслуживать совсем другой запрос. Для этого существует `c.Copy()`. Цепочкой middleware управляют вызовы `c.Next()` и `c.Abort()`.

### echo

echo внешне похож на gin, но в его основе лежит одна важная идея:

```go
e := echo.New()
e.HTTPErrorHandler = customHandler
e.GET("/users/:id", func(c echo.Context) error {
    u, err := find(c.Param("id"))
    if err != nil {
        return echo.NewHTTPError(http.StatusNotFound, "not found")
    }
    return c.JSON(http.StatusOK, u)
})
```

Хендлер возвращает `error`. Благодаря этому ошибки превращаются в ответы в одном месте, а класс багов с забытым `return` после `http.Error` просто исчезает. Этот же приём мы видели в третьем уроке, когда писали функцию `handle`.

### fiber (fasthttp)

fiber выглядит как Express.js и построен вовсе не на `net/http`, а на fasthttp:

```go
app := fiber.New()
app.Get("/users/:id", func(c *fiber.Ctx) error {
    return c.JSON(fiber.Map{"id": c.Params("id")})
})
app.Listen(":8080")
```

fasthttp переиспользует буферы и объекты запросов и за счёт этого почти не делает аллокаций. Платить за скорость приходится дорого. Прежде всего, fiber **несовместим** с `net/http`: стандартные middleware, `httptest`, otelhttp и всё остальное, что работает с `http.Handler`, здесь не подойдёт. Кроме того, значения из `c.Params()` и `c.Body()` валидны только до конца хендлера, потому что их буферы затем переиспользуются. Сохраните такую строку в map, и через один запрос там окажется мусор, так что значения нужно копировать. Наконец, HTTP/2 fasthttp не поддерживает. Выигрыш в скорости хорошо виден на микробенчмарках, но в реальном сервисе узким местом обычно оказываются база данных и сеть, а не HTTP-слой.

### gorilla/mux

gorilla/mux — старейший из популярных роутеров:

```go
r := mux.NewRouter()
r.HandleFunc("/articles/{category}/{id:[0-9]+}", handler).Methods("GET").Host("{sub}.example.com")
vars := mux.Vars(r)
```

Он поддерживает регулярные выражения в параметрах и сопоставление по заголовкам и хосту. Для новых проектов его выбирают редко: обычно берут chi или стандартную библиотеку.

## Что уже умеет stdlib (Go 1.22+)

Прежде чем тянуть зависимость, стоит трезво оценить, чего не хватает в стандартной библиотеке. Начиная с Go 1.22 `ServeMux` понимает методы и параметры в паттернах, wildcard `{path...}` и `{$}`, сам отвечает 405 с заголовком `Allow` и разрешает приоритеты паттернов. Рядом есть `http.StripPrefix`, `http.TimeoutHandler`, `http.MaxBytesReader` и `http.ResponseController`, а для остального — `log/slog` для структурных логов, `encoding/json`, `html/template` и `embed`.

Не хватает по сути трёх вещей: групп маршрутов со своими middleware, биндинга с валидацией по тегам и регулярок в параметрах. Группы, впрочем, решаются вложенными `ServeMux` со `StripPrefix` или пятьюдесятью строками собственного кода.

Отсюда и практическое правило. Стандартной библиотеки хватает для небольших и средних API, внутренних сервисов и библиотек, которым не стоит навязывать пользователям лишнюю зависимость. Фреймворк оправдан, когда команда уже хорошо его знает, когда нужна богатая экосистема (валидация, генерация swagger, готовые middleware) или когда в проекте много однотипных CRUD-эндпоинтов. Обычно выбор идёт по нарастающей: сначала stdlib или chi, потому что они совместимы со всем остальным; затем gin или echo, если важнее удобство; и fiber только тогда, когда вы действительно упираетесь в CPU на HTTP-слое и готовы смириться с несовместимостью.

## Как устроен роутер внутри

Как роутер находит нужный маршрут среди сотен? Подходов по сути три.

Самый простой — **линейный перебор**: маршруты проверяются по очереди, и поиск занимает $O(R)$, где $R$ — число маршрутов. Так работает gorilla/mux, которому перебор нужен ради регулярных выражений.

httprouter, chi, gin и echo используют **radix-дерево**. Общие префиксы маршрутов хранятся в нём один раз, параметр пути становится особым узлом, а поиск занимает $O(L)$, где $L$ — длина пути, независимо от того, сколько маршрутов зарегистрировано.

`ServeMux` из Go 1.22 строит дерево по сегментам пути и применяет правило «побеждает самый специфичный паттерн», благодаря чему конфликты обнаруживаются ещё при регистрации.

## Свой мини-фреймворк: ключевые решения

В задаче этого урока вы напишете фреймворк сами. Его ядро умещается в несколько строк:

```go
type HandlerFunc func(c *Context) error
type Middleware func(HandlerFunc) HandlerFunc

type Context struct {
    W http.ResponseWriter
    R *http.Request
}
func (c *Context) Param(k string) string { return c.R.PathValue(k) }
func (c *Context) JSON(code int, v any) error { ... }
```

![Путь запроса в мини-фреймворке: ServeMux находит маршрут, адаптер создаёт `Context`, дальше слои middleware — глобальные, группы, маршрута; ошибка хендлера поднимается обратно и превращается в ответ в одном месте](img/miniweb-flow.svg)

Остальное — вопрос нескольких проектных решений.

1. **Сопоставление** маршрутов не нужно писать с нуля: его можно отдать `ServeMux`, регистрируя паттерн `"GET " + prefix + path`.
2. **Группа** — это структура с префиксом и собственной копией списка middleware. Копия здесь принципиальна, потому что `append` к общему срезу приводит к неприятному багу (см. схему ниже).
3. **Порядок middleware**: сначала глобальные, затем middleware группы, затем middleware конкретного маршрута.
4. **Ошибки**: хендлер возвращает `error`. Если это `*HTTPError{Code, Message}`, его показываем клиенту, а всё остальное превращается в 500 без деталей. Если ответ уже начат, ничего не дописываем.
5. **404 и 405** тоже должны проходить через глобальные middleware, чтобы их видели логирование и CORS.

![Ловушка из пункта 2: если у среза middleware группы есть запас `cap`, два `append` к нему пишут в один и тот же элемент, и вторая группа молча подменяет middleware первой](img/group-append.svg)
