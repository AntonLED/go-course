# Урок 2. Роутинг и middleware

## ServeMux в Go 1.22+

Долгое время стандартный мультиплексор умел сопоставлять только префиксы путей. Ни метода, ни параметров в пути он не понимал, поэтому почти каждый проект первым делом подключал gorilla/mux или chi. В Go 1.22 ситуация изменилась: паттерн теперь имеет вид `[METHOD ][HOST]/path`, и для большинства сервисов встроенного роутера достаточно.

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /users", listUsers)            // только GET (и HEAD!)
mux.HandleFunc("POST /users", createUser)
mux.HandleFunc("GET /users/{id}", getUser)         // сегмент-параметр
mux.HandleFunc("GET /files/{path...}", serveFile)  // «хвост» пути, только последним
mux.HandleFunc("GET /{$}", home)                   // ровно "/", не всё дерево
mux.HandleFunc("/static/", static)                 // любой метод, всё поддерево /static/
mux.HandleFunc("api.example.com/", apiHost)        // по Host

func getUser(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id") // строка; парсить и валидировать — ваша задача
}
```

Большая часть поведения интуитивна, но несколько правил стоит проговорить явно. Паттерн с `GET` автоматически обслуживает и `HEAD`. Путь, который заканчивается на `/`, означает целое поддерево: `/static/` совпадёт с `/static/a/b.css`. Если нужен ровно этот путь без поддерева, на конце ставят `{$}`, так что `/{$}` соответствует только корню.

Когда путь совпал, а метод нет, mux сам отвечает **405** и выставляет заголовок `Allow` со списком допустимых методов. Если не совпало ничего, будет 404. Есть и удобная мелочь: запрос `/static` при зарегистрированном `/static/` получит редирект 301 на версию со слэшем. Пути также очищаются, поэтому `/a/../b` приведёт к редиректу на `/b`.

![Как mux разбирает запросы: из совпавших паттернов побеждает самый специфичный; путь совпал, а метод нет — 405 со списком методов в `Allow`; путь не совпал ни с чем — 404](img/mux-match.svg)

### Приоритеты

Что будет, если запрос подходит под несколько паттернов сразу? Правило одно: **побеждает более специфичный паттерн**, то есть тот, что совпадает со строгим подмножеством запросов другого. `/users/new` специфичнее `/users/{id}`, а `GET /x` специфичнее `/x`. Порядок регистрации при этом не играет никакой роли, и это приятное отличие от роутеров, где «кто первый, тот и прав».

Бывает, что два паттерна пересекаются, но ни один не специфичнее другого, например `/users/{id}` и `/{kind}/new`. На запрос `/users/new` подходят оба, и выбрать честно нельзя. В такой ситуации `Handle` **паникует прямо при регистрации**, так что конфликт обнаруживается при старте, а не в продакшене под нагрузкой. Повторная регистрация одного и того же паттерна тоже вызывает панику.

![Специфичность — это вложенность множеств путей: `/users/new` лежит внутри `/users/{id}` и побеждает; `/users/{id}` и `/{kind}/new` лишь пересекаются, поэтому регистрация второго паникует](img/mux-specificity.svg)

Иногда нужно узнать, какой маршрут сработает, не вызывая хендлер. Для этого есть `mux.Handler(r)`: он возвращает хендлер и паттерн. Это пригодится, например, для метрик с меткой маршрута. Начиная с Go 1.23 паттерн к тому же записывается прямо в запрос, в поле `r.Pattern`.

## Middleware

Роутер решает, кто обработает запрос. Но многие вещи нужны всем хендлерам сразу: логирование, восстановление после паники, аутентификация. Писать это в каждом хендлере бессмысленно, и тут на помощь приходит **middleware** — функция, которая принимает Handler и возвращает новый Handler, добавляя поведение до вызова исходного, после него или с обеих сторон.

```go
type Middleware func(http.Handler) http.Handler

func Logging(l *slog.Logger) Middleware {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            start := time.Now()
            next.ServeHTTP(w, r)                       // ← вызов «внутрь»
            l.Info("request", "path", r.URL.Path, "dur", time.Since(start))
        })
    }
}
```

Всё, что стоит до `next.ServeHTTP`, выполняется на пути запроса внутрь, а всё, что после, выполняется, когда ответ уже сформирован.

### Цепочки и порядок

Middleware обычно много, и вручную оборачивать их друг в друга неудобно. Небольшая функция `Chain` делает это за нас:

```go
func Chain(h http.Handler, mws ...Middleware) http.Handler {
    for i := len(mws) - 1; i >= 0; i-- { h = mws[i](h) }
    return h
}
handler := Chain(mux, RequestID, Logging(l), Recover(l), Auth)
// запрос: RequestID → Logging → Recover → Auth → mux → ... и обратно
```

Обратите внимание, что цикл идёт с конца списка. Благодаря этому первый middleware в списке оказывается самым внешним, и список читается в том порядке, в каком через него пройдёт запрос.

Сам порядок имеет значение: слои похожи на луковицу, и у каждого есть своё разумное место. RequestID ставят снаружи всех, чтобы идентификатор попал и в логи, и в ответы об ошибках. Logging должен быть снаружи Recover: тогда после паники логгер увидит итоговый статус 500, а не ничего. Recover размещают как можно ближе к хендлерам, но всё же снаружи всего, что способно паниковать. Auth идёт после логирования, потому что неудачные попытки входа тоже нужно видеть в логах, но перед бизнес-логикой. А CORS должен стоять до Auth: preflight-запрос `OPTIONS` браузер отправляет без авторизации, и Auth его просто отверг бы.

![Запрос проходит слои снаружи внутрь до хендлера, ответ возвращается через те же слои в обратном порядке; `Chain` оборачивает с конца списка, поэтому первый middleware оказывается внешним](img/middleware-onion.svg)

Middleware не обязательно навешивать на весь mux. Его можно применить и к одному маршруту: `mux.Handle("DELETE /users/{id}", RequireRole("admin")(http.HandlerFunc(deleteUser)))`.

## Передача данных: context

Auth-middleware выяснил, кто пришёл. Как сообщить это хендлеру, если сигнатура `ServeHTTP` фиксирована? Через контекст запроса:

```go
type ctxKey struct{} // неэкспортируемый тип — нет коллизий с чужими пакетами

func WithUser(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        u := authenticate(r)
        next.ServeHTTP(w, r.WithContext(context.WithValue(r.Context(), ctxKey{}, u)))
    })
}
func UserFrom(ctx context.Context) (*User, bool) { u, ok := ctx.Value(ctxKey{}).(*User); return u, ok }
```

Ключом служит собственный неэкспортируемый тип, поэтому ни один чужой пакет не сможет случайно перезаписать или прочитать это значение. Отдельная функция `UserFrom` прячет приведение типа и даёт хендлерам удобный API.

Контекстом не стоит злоупотреблять. В него кладут сквозные данные конкретного запроса: пользователя, request-id, трассировку. Зависимости вроде подключения к БД или логгера сервиса туда не относятся — их передают через поля структуры-сервера, где их видно в типах.

## Обёртка ResponseWriter

Логирующему middleware хочется знать статус ответа, но `http.ResponseWriter` его не сообщает. Приходится оборачивать writer своим типом, который запоминает код:

```go
type statusRecorder struct {
    http.ResponseWriter
    status int
}
func (r *statusRecorder) WriteHeader(code int) { r.status = code; r.ResponseWriter.WriteHeader(code) }
func (r *statusRecorder) Unwrap() http.ResponseWriter { return r.ResponseWriter }
```

У такой обёртки есть подвох. Исходный writer реализует дополнительные интерфейсы вроде `http.Flusher` и `http.Hijacker`, а наша структура встраивает только `http.ResponseWriter`, и приведение `w.(http.Flusher)` перестаёт работать. Стриминг ломается незаметно. В Go 1.20 для этого появился **`http.ResponseController`**: он ищет нужную возможность по цепочке методов `Unwrap()`, так что достаточно, чтобы обёртка умела себя разворачивать.

```go
rc := http.NewResponseController(w)
_ = rc.Flush()
_ = rc.SetWriteDeadline(time.Now().Add(time.Minute)) // для долгих стримов
conn, brw, err := rc.Hijack()
```

![`statusRecorder` перехватывает только `WriteHeader`; `Write` уходит к исходному writer через встроенное поле, приведение к `http.Flusher` ломается, а `ResponseController` добирается до `Flush` через `Unwrap`](img/status-recorder.svg)

И ещё одна деталь для рекордера: если хендлер вызвал `Write`, ни разу не вызвав `WriteHeader`, статус ответа равен 200. Начальное значение поля `status` должно это учитывать.

## Типовые middleware

Большинство middleware в реальных сервисах повторяются от проекта к проекту. Коротко о каждом.

**Recover** ставит `defer func(){ if v := recover(); v != nil { ... 500 } }()` и превращает панику в ответ 500. Есть одно исключение — `http.ErrAbortHandler`. Им паникуют намеренно, чтобы оборвать ответ, поэтому такую панику нужно пробросить дальше.

**RequestID** принимает входящий `X-Request-ID` только после проверки длины и алфавита, а если проверка не прошла, генерирует свой. Без валидации вы получите инъекции в логи (перевод строки `\n` внутри ID) и мегабайтные идентификаторы.

**Auth** достаёт учётные данные через `r.BasicAuth()` или из заголовка `Authorization: Bearer ...`. Секреты сравнивают только через `crypto/subtle.ConstantTimeCompare`: обычное сравнение завершается на первом несовпавшем байте, и по времени ответа можно подобрать секрет (timing-атака).

**CORS** нужен, когда к API обращается браузер с другого origin. Для «непростых» запросов браузер сначала сам отправляет preflight `OPTIONS` с заголовками `Access-Control-Request-Method/Headers`, а сервер отвечает заголовками `Access-Control-Allow-*`. Помните, что `Access-Control-Allow-Origin: *` несовместим с credentials, а если сервер возвращает Origin эхом, в ответе обязателен `Vary: Origin`, иначе кэш отдаст чужой ответ другому сайту.

**Timeout** проще всего сделать через `http.TimeoutHandler(h, 2*time.Second, "timeout")`: он отдаёт 503 и отменяет контекст запроса.

Rate limit, gzip и метрики строятся по той же схеме.

![CORS preflight: перед «непростым» запросом браузер сам шлёт `OPTIONS` с `Access-Control-Request-*`, и только если ответ разрешает метод и заголовки, отправляет настоящий запрос](img/cors-preflight.svg)

## http.StripPrefix

Когда хендлер ничего не знает о том, под каким префиксом его смонтировали, префикс нужно отрезать:

```go
mux.Handle("/static/", http.StripPrefix("/static/", http.FileServerFS(assets)))
mux.Handle("/api/v1/", http.StripPrefix("/api/v1", apiV1)) // apiV1 видит /users, а не /api/v1/users
```

`StripPrefix` меняет `r.URL.Path` (и `RawPath`) у копии запроса, так что исходный запрос остаётся нетронутым. Если префикса в пути нет, ответ будет 404.

## Типичные ошибки

1. В `Chain` перепутан порядок: Recover оказался снаружи Logging, и лог видит 200 вместо 500.
2. Ключ контекста имеет тип `string`, что ведёт к коллизиям; staticcheck предупреждает об этом правилом SA1029.
3. Middleware забывает вызвать `next.ServeHTTP` или вызывает его дважды.
4. Заголовки выставляются **после** `next.ServeHTTP`, когда ответ уже отправлен, и молча теряются.
5. Обёртка writer'а без `Unwrap`, из-за которой ломаются стриминг и SSE.
