# Урок 4. Шаблоны и статические файлы

## text/template и html/template

В стандартной библиотеке Go есть два пакета шаблонов с одинаковым синтаксисом и совершенно разным отношением к безопасности.

`text/template` вставляет значения как есть. Это правильный выбор для конфигов, генерации кода и писем в plain text, где никакого экранирования не нужно.

`html/template` делает **контекстно-зависимое экранирование**. Он понимает, куда именно попадает вставка — в текст HTML, в атрибут, в URL, в JavaScript или в CSS, — и экранирует значение по правилам этого места. Всё, что в итоге увидит браузер, рендерят только им. Посмотрим, как одно и то же вредоносное значение обрабатывается в разных местах страницы:

```go
t := template.Must(template.New("x").Parse(
    `<a href="{{.URL}}" title="{{.T}}">{{.T}}</a><script>var n = {{.T}};</script>`))
t.Execute(os.Stdout, map[string]string{"URL": "javascript:alert(1)", "T": `"><b>x`})
// <a href="#ZgotmplZ" title="&#34;&gt;&lt;b&gt;x">&#34;&gt;&lt;b&gt;x</a><script>var n = "\"\u003e\u003cb\u003ex";</script>
```

Строка `#ZgotmplZ` в выводе — это маркер: шаблонизатор нашёл небезопасный URL (`javascript:` или `data:` в `href`) и заменил его. Внутри `<script>` значение превратилось в JS-литерал, то есть в строку в кавычках, и выйти из неё уже нельзя.

Если у вас есть HTML, которому вы действительно доверяете, его можно пометить типом `template.HTML` или `template.URL`. Это **явный** обход защиты, и оборачивать в эти типы пользовательский ввод нельзя никогда.

![Одно и то же значение `html/template` экранирует по месту вставки: HTML-сущности в тексте и атрибуте, percent-кодирование в URL, JS-строка в `<script>`, а `javascript:` в `href` заменяет на `#ZgotmplZ`](img/html-escaping.svg)

Смешать пакеты не получится: `html/template` и `text/template` объявляют разные типы, хотя имена функций у них одинаковые. Зато перепутать импорт очень легко, и это классическая XSS-уязвимость, от которой компилятор не спасёт: код соберётся и будет работать, просто без экранирования.

## Синтаксис за минуту

Вся грамматика шаблонов помещается на одном экране:

```
{{.Field}}  {{.Method}}  {{index .Map "key"}}  {{len .Items}}
{{if .User}}…{{else if .Guest}}…{{else}}…{{end}}
{{range $i, $it := .Items}}{{$i}}: {{$it.Title}}{{else}}пусто{{end}}
{{with .Author}}{{.Name}}{{else}}аноним{{end}}   // with меняет «точку»
{{- trim -}}                                     // обрезка пробелов слева/справа
{{/* комментарий */}}
{{.Price | printf "%.2f"}}                       // конвейер: значение — последний аргумент
{{template "name" .}}  {{define "name"}}…{{end}}  {{block "name" .}}по умолчанию{{end}}
```

Главное, что нужно усвоить, — это «точка». Внутри `range` и `with` она означает текущий элемент, а не исходные данные, поэтому до корня приходится добираться через `$`, например `{{$.Title}}`. Пустые значения — `0`, `""`, `nil`, пустой срез или map — в `if` и `with` считаются ложью.

## Layout, define, block

У большинства сайтов есть общий каркас страницы, в который подставляется разное содержимое. В шаблонах Go это делается через именованные шаблоны:

```go
const layout = `{{define "layout"}}<html><head><title>{{.Title}}</title></head>
<body>{{block "content" .}}по умолчанию{{end}}</body></html>{{end}}`
const page = `{{define "content"}}<h1>{{.Title}}</h1>{{end}}`

t := template.Must(template.New("").Parse(layout))
t = template.Must(t.Parse(page))       // переопределение — отдельным Parse
t.ExecuteTemplate(w, "layout", data)
```

`block` — это сокращение для пары `define` плюс `template`: он объявляет шаблон с содержимым по умолчанию и тут же его вызывает. Переопределить шаблон в том же вызове `Parse` нельзя, вы получите ошибку multiple definition, а в последующем `Parse` можно.

Как быть, если страниц много, а layout один? Если просто парсить все `content` в один набор, каждая следующая страница перезапишет предыдущую. Поэтому на каждую страницу делают `base.Clone()` и уже в клоне парсят её `content`.

![Набор шаблонов — словарь по именам: `layout` вызывает `content` по имени во время выполнения, поэтому следующий `Parse` может его заменить; `Clone` даёт каждой странице свой `content` при общем layout](img/template-tree.svg)

## FuncMap

Встроенных функций немного, и собственные подключают через `FuncMap`:

```go
funcs := template.FuncMap{
    "upper": strings.ToUpper,
    "price": func(c int64) (string, error) { ... }, // (T, error): ненулевая error прерывает Execute
}
t := template.New("x").Funcs(funcs) // ДО Parse, иначе "function not defined"
```

Функция может вернуть одно значение или пару «значение, error». Порядок вызовов важен: `Funcs` должен идти до `Parse`, потому что парсер проверяет имена функций сразу. И не увлекайтесь: логике место в Go-коде, а шаблон должен оставаться простым.

## Производительность и ошибки

Парсинг шаблона — операция недешёвая, поэтому шаблоны разбирают **один раз** при старте (`template.Must` плюс `ParseFS`), а не на каждый запрос. Готовый `*Template` безопасен для конкурентного `Execute`, так что один экземпляр спокойно обслуживает все запросы.

С ошибками та же история, что и в прошлом уроке. `Execute` пишет вывод по мере выполнения, и если ошибка случится на середине, клиент получит статус 200 и половину страницы. Выход — рендерить в `bytes.Buffer` (его можно брать из `sync.Pool`) и копировать в `w` только после успеха.

## embed: файлы внутри бинарника

Одно из приятных свойств Go — сервис собирается в один бинарник. Директива `//go:embed` позволяет положить туда же шаблоны и статику:

```go
import "embed"

//go:embed templates/*.html
var tmplFS embed.FS

//go:embed static
var staticFS embed.FS // каталог рекурсивно, кроме файлов на "." и "_" (для них — all:static)

//go:embed version.txt
var version string

t := template.Must(template.ParseFS(tmplFS, "templates/*.html"))
```

Директива ставится перед `var` уровня пакета, а путь указывается относительно файла с исходником, без `..`. Полученный `embed.FS` реализует `fs.FS`, доступен только для чтения и безопасен при конкурентном доступе. Если префикс каталога мешает, его убирают через `fs.Sub(staticFS, "static")`.

Есть одна особенность, которая аукнется при кэшировании: у встроенных файлов нулевое время модификации. Поэтому заголовок `Last-Modified` не выставится, и версию файла придётся сообщать через ETag.

## Отдача статики

Раздать встроенные файлы можно в две строки:

```go
sub, _ := fs.Sub(staticFS, "static")
mux.Handle("GET /static/", http.StripPrefix("/static/", http.FileServerFS(sub))) // Go 1.22
```

![Путь `/static/css/app.css` по шагам: `StripPrefix` срезает `/static/`, `FileServerFS` открывает `css/app.css`, а `fs.Sub` дописывает каталог `static/` — так находится файл внутри `embed.FS`](img/static-path.svg)

`http.FileServer` и `FileServerFS` умеют довольно много: определяют `Content-Type` по расширению, поддерживают Range-запросы и `If-Modified-Since`, отдают `index.html` для каталогов и перенаправляют `/index.html` на `/`. Но у них есть и поведение, которое в продакшене обычно нежелательно. Если в каталоге нет `index.html`, они покажут **листинг каталога**. Заголовки `Cache-Control` и ETag они не ставят. А dot-файлы вроде `.env` или `.git` отдадут без вопросов, если те попали в файловую систему.

Когда нужен свой файловый сервер, строят его на `http.ServeContent(w, r, name, modtime, readSeeker)` — это «ядро» стандартного. Если выставить заголовок `ETag` перед вызовом, `ServeContent` сам обработает `If-None-Match` и `If-Range`.

## HTTP-кэширование

Статика — идеальный кандидат для кэширования, и управляют им несколько заголовков.

Для файлов с хэшем в имени, вроде `app.3f9a1c.js`, ставят `Cache-Control: public, max-age=31536000, immutable`. Такой файл никогда не меняется: когда меняется содержимое, меняется и имя, так что браузер может хранить его год.

Для HTML подходит `Cache-Control: no-cache`. Вопреки названию, он **разрешает** хранить ответ, но требует ревалидировать его перед каждым использованием. Не путайте его с `no-store`, который означает «не хранить вообще» и нужен для приватных данных.

**ETag** — идентификатор версии ресурса. Он бывает сильным, `"abc"`, что означает побайтовое равенство, и слабым, `W/"abc"`, что означает семантическую эквивалентность. Клиент присылает сохранённый ETag в `If-None-Match: "abc"`, и если версия не изменилась, сервер отвечает `304 Not Modified` без тела. Для GET и HEAD сравнение слабое, поэтому `W/"abc"` совпадает с `"abc"`.

Пара `Last-Modified` и `If-Modified-Since` делает то же самое по времени, но с точностью до секунды. Наконец, `Vary: Accept-Encoding, Origin` сообщает кэшам, какие заголовки запроса влияют на ответ.

Для встроенных файлов ETag удобно посчитать из содержимого:

```go
sum := sha256.Sum256(data)
etag := `"` + hex.EncodeToString(sum[:8]) + `"` // считаем один раз при старте
w.Header().Set("ETag", etag)
http.ServeContent(w, r, name, time.Time{}, bytes.NewReader(data)) // 304 — автоматически
```

## Типичные ошибки

1. `text/template` для HTML, а значит XSS.
2. `template.HTML(userInput)`, «чтобы не экранировалось».
3. Парсинг шаблонов прямо в хендлере.
4. Потоковый `Execute` в `w`, где ошибка посередине оставляет клиенту половину страницы.
5. `FileServer(http.Dir("."))`, из-за которого наружу уезжает весь рабочий каталог вместе с `.git`.
6. ETag без кавычек. По RFC 9110 такое значение невалидно, `http.ServeContent` не распознает его в `If-None-Match` и никогда не ответит 304.
