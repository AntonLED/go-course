# Урок 3. Работа с запросами и ответами

## Что есть в *http.Request

Хендлер получает от сервера структуру `*http.Request`, и почти всё, что нужно знать о запросе, лежит в нескольких её полях и методах:

```go
r.Method, r.URL.Path, r.URL.RawQuery, r.Host, r.RemoteAddr
r.Header.Get("Content-Type")
r.URL.Query().Get("page")   // парсит RawQuery при каждом вызове — сохраните в переменную
r.PathValue("id")           // из паттерна ServeMux
r.Body                      // io.ReadCloser; сервер закроет его сам
r.Context()                 // отменяется, когда клиент ушёл или хендлер вернулся
r.ContentLength             // -1, если неизвестно (chunked)
```

Самое интересное и самое опасное здесь — тело запроса. С него и начнём.

## Чтение тела: всегда с лимитом

Вызов `io.ReadAll(r.Body)` без ограничения размера — открытое приглашение к OOM. Клиенту ничего не стоит прислать 10 ГБ, и сервер честно попытается уложить их в память. Поэтому тело всегда читают через ограничитель:

```go
r.Body = http.MaxBytesReader(w, r.Body, 1<<20) // 1 MiB
```

Почему именно `MaxBytesReader`, а не знакомый `io.LimitReader`? У них принципиально разное поведение на границе. `LimitReader`, дойдя до лимита, просто возвращает EOF, как будто тело закончилось. Декодер получит обрезанный JSON и выдаст невнятную синтаксическую ошибку, а вы так и не узнаете, что дело в размере. `MaxBytesReader` в этой ситуации возвращает ошибку `*http.MaxBytesError`, по которой легко ответить 413. Вдобавок он сообщает серверу, что после ответа соединение нужно закрыть, ведь клиент мог ещё не дослать остаток тела.

![На лимите `LimitReader` притворяется концом тела (`io.EOF`), и декодер видит обрывок JSON; `MaxBytesReader` возвращает `*http.MaxBytesError` — по нему отвечают 413, а сервер закрывает соединение](img/maxbytes.svg)

## JSON: строгий декодер

Типичный API принимает JSON, и разбирать его лучше строго: проверить тип содержимого, ограничить размер, запретить неизвестные поля и убедиться, что в теле ровно один объект.

```go
func decodeJSON(w http.ResponseWriter, r *http.Request, dst any) error {
    if mt, _, _ := mime.ParseMediaType(r.Header.Get("Content-Type")); mt != "application/json" {
        return errUnsupportedMedia // 415
    }
    dec := json.NewDecoder(http.MaxBytesReader(w, r.Body, 1<<20))
    dec.DisallowUnknownFields()             // опечатка в поле → 400, а не молчаливый игнор
    if err := dec.Decode(dst); err != nil { // разбираем тип ошибки → 400/413
        return err
    }
    if err := dec.Decode(&struct{}{}); err != io.EOF { // ровно один объект
        return errors.New("лишние данные после JSON")
    }
    return nil
}
```

Ошибка из `Decode` бывает разной природы, и от неё зависит код ответа. Вот что можно встретить на практике:

| Ошибка | Пример | Код |
|---|---|---|
| `io.EOF` | пустое тело | 400 |
| `*json.SyntaxError` (есть `Offset`) | `{"a":}` | 400 |
| `io.ErrUnexpectedEOF` | `{"a":1` | 400 |
| `*json.UnmarshalTypeError` (есть `Field`) | `{"age":"десять"}` | 400 |
| `json: unknown field "x"` (строка!) | лишнее поле | 400 |
| `*http.MaxBytesError` | слишком большое тело | 413 |
| не тот `Content-Type` | `text/plain` | 415 |
| бизнес-валидация | возраст -5 | 422 |

Обратите внимание на строку с неизвестным полем: у этой ошибки нет своего типа, это просто текст, и распознавать её приходится по строке.

Граница между 400 и 422 проходит так: 400 означает «не смог разобрать запрос», а 422 — «разобрал, но по смыслу данные неверны».

Зачем второй вызов `Decode`? `json.Decoder`, в отличие от `json.Unmarshal`, читает поток и не требует держать всё тело в памяти, но **останавливается после первого значения**. Тело `{"a":1}{"b":2}` без дополнительной проверки молча пройдёт, а второй объект будет проигнорирован. Второй `Decode` должен вернуть `io.EOF`; всё остальное означает мусор после JSON.

Отдельный случай — частичное обновление через PATCH. Там нужно отличать «поле не передали» от «передали пустую строку», и для этого поля делают указателями: `Title *string` равен `nil`, если поля в запросе не было, и указывает на `""`, если его передали пустым.

## Query, формы, multipart

JSON не единственный формат. Параметры строки запроса, HTML-формы и загрузка файлов разбираются другими средствами:

```go
q := r.URL.Query()
limit, err := strconv.Atoi(q.Get("limit")) // "" → ошибка; обрабатывайте значение по умолчанию
tags := q["tag"]                            // ?tag=a&tag=b → [a b]

// application/x-www-form-urlencoded
if err := r.ParseForm(); err != nil { ... }
name := r.PostForm.Get("name") // только тело; r.Form — тело + query
// FormValue сам вызывает ParseMultipartForm и игнорирует ошибки — удобно, но опасно

// multipart/form-data (загрузка файлов)
r.Body = http.MaxBytesReader(w, r.Body, 32<<20)
if err := r.ParseMultipartForm(8 << 20); err != nil { ... } // 8 MiB в памяти, остальное — во временные файлы
f, hdr, err := r.FormFile("avatar")
if err != nil { ... } // http.ErrMissingFile, если поля нет
defer f.Close()
// hdr.Filename — от клиента, НЕ используйте как путь (../../etc/passwd)
// тип файла проверяйте по содержимому: http.DetectContentType(первые 512 байт)
```

Комментарии в коде указывают на главные ловушки. `FormValue` удобен, но глотает ошибки разбора. Имя файла приходит от клиента, и использовать его как путь на диске нельзя. Тип файла определяют по содержимому, а не по расширению или заголовку.

Если файлы большие, не стоит разбирать форму целиком. Её читают потоково: `mr, _ := r.MultipartReader(); for { part, err := mr.NextPart() ... }`.

## Порядок записи ответа

С ответом всё немного хитрее, чем кажется. У `ResponseWriter` есть строгий порядок операций:

```
w.Header().Set(...)  →  w.WriteHeader(code)  →  w.Write(body)
```

![Три состояния ответа: пока заголовки открыты, их можно менять; `WriteHeader` или первый `Write` фиксирует статус и заголовки; после сброса буфера всё уже в сокете](img/response-states.svg)

Пока не вызван `WriteHeader` или первый `Write`, заголовки можно свободно менять. После этого они зафиксированы, и всё, что вы выставите позже, будет молча проигнорировано. Если хендлер сразу вызвал `Write`, не вызвав `WriteHeader`, сервер подставит неявный статус `200`.

Повторный вызов `WriteHeader` код не меняет, зато оставляет в логе сервера строку `http: superfluous response.WriteHeader call from ...`. Чаще всего за ней стоит забытый `return` после обработки ошибки:

```go
if err != nil {
    http.Error(w, "bad", 400)
    // return забыт! дальше пойдёт WriteJSON(w, 200, ...) → superfluous
}
```

Несколько заголовков Go выставляет сам. Если вы не указали `Content-Type`, сервер определит его по первым 512 байтам ответа через `DetectContentType`; для JSON лучше указывать тип явно. `Content-Length` появится автоматически, если хендлер завершился, а весь ответ уместился в буфер (около 2 КБ). В противном случае HTTP/1.1 перейдёт на `Transfer-Encoding: chunked`. Функция `http.Error` ставит `text/plain` и `X-Content-Type-Options: nosniff`, а `Content-Length` удаляет.

![Ответ, уместившийся в 2-килобайтный буфер к возврату из хендлера, получает `Content-Length`; если буфер переполнился или был `Flush`, заголовки уходят раньше тела, и HTTP/1.1 переходит на `chunked`](img/response-buffer.svg)

Из всего этого следует простое правило: сначала сериализуйте, потом пишите. Пока байты не ушли, у вас ещё есть возможность сменить код ответа:

```go
b, err := json.Marshal(v)
if err != nil { http.Error(w, "internal", 500); return } // ещё можно сменить код
w.Header().Set("Content-Type", "application/json")
w.WriteHeader(status)
w.Write(b)
```

А как же `json.NewEncoder(w).Encode(v)`? Он тоже сначала сериализует значение целиком во внутренний буфер, но вызывают его обычно уже после `WriteHeader(200)`. Если маршалинг упадёт, поменять код будет поздно, и клиент получит 200 с пустым телом. С шаблонами ещё хуже: `Execute` пишет вывод по мере выполнения, и ошибка посередине оставит клиенту статус 200 и половину страницы. Поэтому шаблоны рендерят в буфер.

## Контекст запроса и отмена клиентом

Пользователь закрыл вкладку, а ваш хендлер продолжает выполнять тяжёлый запрос к базе. Чтобы этого не происходило, у запроса есть контекст. `r.Context()` отменяется, когда клиент закрыл соединение или когда `ServeHTTP` вернул управление. В HTTP/1.1 сервер замечает уход клиента благодаря фоновому чтению из сокета, в HTTP/2 — по кадру RST_STREAM. Передавайте этот контекст во все долгие операции:

```go
rows, err := db.QueryContext(r.Context(), q)
if errors.Is(err, context.Canceled) {
    return // клиент ушёл — отвечать некому; nginx логирует такое как 499
}
```

![Клиент оборвал соединение: фоновое чтение сервера видит EOF и отменяет контекст, запрос к БД прерывается с `context.Canceled`; работа на `context.WithoutCancel` продолжается](img/request-context.svg)

Иногда, наоборот, нужна фоновая работа, которая должна пережить запрос, например отправка письма. Для этого в Go 1.21 появился `context.WithoutCancel(r.Context())`: он сохраняет значения из контекста (тот же request-id), но не наследует отмену.

## Ошибки в едином формате: Problem Details (RFC 9457)

Когда каждый хендлер придумывает свой формат ошибки, клиентам API приходится писать отдельный разбор для каждого эндпоинта. RFC 9457 предлагает общий формат `application/problem+json`:

```http
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json

{
  "type": "https://example.com/probs/validation",
  "title": "Unprocessable Entity",
  "status": 422,
  "detail": "Некорректные поля",
  "instance": "/users",
  "errors": {"email": "некорректный email"}
}
```

Поле `type` содержит URI типа проблемы. По умолчанию это `about:blank`, и тогда `title` совпадает со стандартным текстом статуса. `title` кратко описывает тип проблемы, `detail` рассказывает о конкретном случае, а `instance` указывает, где он произошёл. К стандартным полям можно добавлять свои, как `errors` в примере или `request_id`.

С ошибками 500 правило жёсткое: **никаких внутренних деталей клиенту**. SQL-запросы, стектрейсы и внутренние адреса пишутся только в лог вместе с request-id, а клиент получает лишь этот request-id, по которому поддержка найдёт нужную запись.

Чтобы не повторять обработку ошибок в каждом хендлере, удобно позволить хендлерам возвращать `error` и завести одну функцию, которая превращает ошибку в ответ:

```go
type apiFunc func(w http.ResponseWriter, r *http.Request) error

func (s *Server) handle(fn apiFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        if err := fn(w, r); err != nil {
            s.writeError(w, r, err) // errors.As → Problem, errors.Is(ErrNotFound) → 404, иначе 500
        }
    }
}
```

## Типичные ошибки

1. Тело читается без лимита.
2. После `Decode` не проверяется, что за JSON ничего нет.
3. После `http.Error` забыт `return`.
4. `Header().Set` вызывается после `Write`.
5. JSON или шаблон пишутся потоком прямо в ответ, и ошибка посередине оставляет клиенту половину данных.
6. В ответ 500 утекают внутренние детали.
7. Запросы к БД игнорируют `r.Context()`.
