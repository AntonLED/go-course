# Урок 5. HTTP-клиент в Go

## Устройство: Client → Transport → соединения

Серверы редко живут сами по себе: они ходят в другие сервисы, платёжные шлюзы, внешние API. Клиентская сторона `net/http` устроена в три слоя, и у каждого своя ответственность:

```
http.Client          политика: Timeout, редиректы (CheckRedirect), cookies (Jar)
   └─ Transport      RoundTripper: пул соединений, TLS, прокси, HTTP/2, keep-alive
        └─ net.Conn  TCP/TLS соединения
```

`Client` отвечает за политику: сколько ждать, следовать ли редиректам, где хранить cookies. `Transport` занимается механикой: держит пул соединений, делает TLS-рукопожатие, ходит через прокси. А под ним лежат обычные TCP- и TLS-соединения.

Самый короткий способ сделать запрос, `http.Get(url)`, на деле означает `http.DefaultClient.Get(url)`. И вот здесь кроется ловушка: у `DefaultClient` **нет таймаута**. Если сервер принял соединение и замолчал, горутина будет ждать ответа вечно. Поэтому в продакшене всегда создают свой клиент:

```go
var client = &http.Client{
    Timeout: 10 * time.Second, // весь запрос: соединение + редиректы + чтение тела ответа
    Transport: &http.Transport{
        Proxy:                 http.ProxyFromEnvironment,
        DialContext:           (&net.Dialer{Timeout: 3 * time.Second, KeepAlive: 30 * time.Second}).DialContext,
        TLSHandshakeTimeout:   3 * time.Second,
        ResponseHeaderTimeout: 5 * time.Second,
        MaxIdleConns:          100,
        MaxIdleConnsPerHost:   20, // по умолчанию 2! при высокой нагрузке на один хост — постоянные реконнекты
        IdleConnTimeout:       90 * time.Second,
        ForceAttemptHTTP2:     true,
    },
}
```

`Client` и `Transport` безопасны для конкурентного использования и должны **переиспользоваться** на протяжении всей жизни программы. Если создавать новый `Transport` на каждый запрос, вместе с ним каждый раз создаётся новый пул: keep-alive перестаёт работать, а соединения утекают. Писать транспорт с нуля тоже не обязательно — удобно начать с `http.DefaultTransport.(*http.Transport).Clone()` и поменять только нужные поля.

Обратите внимание, что `Client.Timeout` покрывает в том числе чтение тела ответа. Для скачивания больших файлов это неудобно: десятисекундный лимит оборвёт загрузку на середине. В таких случаях общий `Timeout` не ставят, а ограничивают запрос контекстом и `ResponseHeaderTimeout`.

![Что ограничивает каждый таймаут: `Dialer.Timeout` — TCP-подключение, `TLSHandshakeTimeout` — рукопожатие, `ResponseHeaderTimeout` — ожидание заголовков после отправки запроса, а `Client.Timeout` и контекст — весь запрос, включая чтение тела после возврата `Do`](img/client-timeouts.svg)

## Тело ответа: закрыть и дочитать

Получив ответ, с его телом нужно обойтись аккуратно, иначе пул соединений перестанет работать так, как вы рассчитываете:

```go
resp, err := client.Do(req)
if err != nil {
    return err // resp == nil, закрывать нечего
}
defer resp.Body.Close() // всегда, даже если статус не 200

if resp.StatusCode != http.StatusOK {
    _, _ = io.Copy(io.Discard, io.LimitReader(resp.Body, 64<<10)) // дочитать немного
    return fmt.Errorf("unexpected status %d", resp.StatusCode)
}
return json.NewDecoder(io.LimitReader(resp.Body, 10<<20)).Decode(&out)
```

Если тело не закрыть, утекут и соединение, и горутины транспорта. Но и простого закрытия мало. Если закрыть тело, не дочитав его, соединение **не вернётся в пул**: в HTTP/1.1 соединение нельзя переиспользовать, пока в сокете лежат байты старого ответа. Следующий запрос заплатит за новое TCP- и TLS-рукопожатие. Поэтому в примере остаток тела вычитывается в `io.Discard`, но с ограничением, чтобы не качать мегабайты мусора.

Две вещи, о которых часто спрашивают. При `err == nil` поле `resp.Body` никогда не бывает `nil`; даже у ответа 204 это просто пустое тело. А статус не из диапазона 2xx, будь то 404 или 500, **не считается ошибкой** `Do`: проверять `StatusCode` вы должны сами.

![Жизненный цикл соединения в `http.Transport`: в idle-пул хоста оно возвращается, только если тело дочитано до EOF и закрыто; иначе соединение закрывается или утекает, и следующий запрос платит за новое рукопожатие](img/conn-lifecycle.svg)

## Контекст

Таймаут клиента одинаков для всех запросов, но часто нужен лимит на конкретный вызов. Его задают контекстом:

```go
ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
defer cancel()
req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
```

Отмена контекста прерывает запрос на любой стадии: при подключении, во время TLS-рукопожатия, в ожидании заголовков или при чтении тела. Ошибка приходит обёрнутой в `*url.Error`, поэтому проверяют её через `errors.Is(err, context.DeadlineExceeded)`.

У контекста есть ещё одно важное преимущество перед `Client.Timeout`. Он задаётся на каждый запрос и наследует дедлайн входящего запроса, который обрабатывает ваш сервер. Так таймауты каскадируются по цепочке сервисов: если у пользователя осталось 300 мс, нижестоящие вызовы не будут ждать по 10 секунд.

## Ретраи

Сети ненадёжны, и повторить неудавшийся запрос кажется очевидной идеей. Но повторять можно далеко не всё, и прежде чем писать цикл, стоит ответить на несколько вопросов.

**Какие ошибки повторять?** Сетевые (connection reset, connection refused), а также ответы `429`, `502`, `503`, `504` и иногда `500`. Остальные 4xx, кроме 429, повторять бессмысленно: сервер ответит то же самое.

**Какие запросы?** Только идемпотентные: GET, HEAD, PUT, DELETE, OPTIONS. POST допустимо повторять, лишь если он несёт `Idempotency-Key`, по которому сервер отбрасывает дубликаты.

**Что делать с телом?** `req.Body` — это поток, и прочитать его можно только один раз. К счастью, когда тело создаётся из `bytes.Reader`, `strings.Reader` или `bytes.Buffer`, `http.NewRequest` заполняет `req.GetBody`, и через него можно получить свежую копию для каждой попытки.

**Сколько ждать между попытками?** Здесь используют экспоненциальный backoff с потолком. Пауза перед попыткой $n$ растёт так:

$$
d_n = \min\left(d_{\max},\ \text{base} \cdot 2^n\right)
$$

Одного роста мало. Если тысячи клиентов упали одновременно, они и повторять будут одновременно, снова и снова ударяя по серверу залпами. Поэтому к паузе добавляют **jitter**, случайный разброс; в самом распространённом варианте реальный сон выбирают равномерно из интервала от нуля до $d_n$:

$$
t_n \sim \mathcal{U}[0,\ d_n]
$$

Если сервер прислал `Retry-After` (в секундах или в виде HTTP-даты), его нужно уважать: он важнее вашего собственного расчёта.

**Когда остановиться?** Нужен лимит попыток и общий дедлайн контекста. Сама пауза тоже должна прерываться отменой, поэтому вместо `Sleep` пишут `select` по `timer.C` и `ctx.Done()`.

![Ретраи: пауза растёт как `base·2ⁿ` до потолка, а реальный сон выбирается случайно из `[0, d]`; `Retry-After` от сервера важнее собственного backoff; без jitter клиенты после сбоя бьют залпами](img/retry-backoff.svg)

Кое-что Transport повторяет сам, без вашего участия. Если переиспользованное соединение из пула оказалось уже закрытым сервером, запрос будет отправлен заново. Для этого тело должно быть «перематываемым» (тела нет или есть `GetBody`), и вдобавок должно выполняться одно из двух: либо метод `GET`/`HEAD`/`OPTIONS`/`TRACE` (или в запросе есть заголовок `Idempotency-Key`/`X-Idempotency-Key`), либо в соединение ещё ничего не успели записать. `PUT` и `DELETE` без ключа после начала отправки Transport сам повторять не станет.

## RoundTripper как middleware

На сервере сквозную логику выносят в middleware вокруг `Handler`. На клиенте для этого есть свой интерфейс с одним методом, `RoundTripper`, и обёртки строятся точно так же:

```go
type RoundTripper interface {
    RoundTrip(*Request) (*Response, error)
}

type authTransport struct {
    base  http.RoundTripper
    token string
}

func (t *authTransport) RoundTrip(req *http.Request) (*http.Response, error) {
    r := req.Clone(req.Context()) // контракт: исходный запрос менять нельзя
    r.Header.Set("Authorization", "Bearer "+t.token)
    return t.base.RoundTrip(r)
}

client := &http.Client{Transport: &authTransport{base: http.DefaultTransport, token: tok}}
```

Так реализуют логирование, метрики, трейсинг (например, otelhttp), авторизацию, ретраи и circuit breaker. При этом у `RoundTripper` есть контракт, который нужно соблюдать. Он не должен интерпретировать ответ — редиректы и аутентификация остаются делом `Client`. Он возвращает либо ответ, либо ошибку, и всегда закрывает `req.Body`. И он не имеет права менять исходный запрос, поэтому в примере сначала делается `req.Clone`.

![RoundTripper-обёртки вкладываются друг в друга, как серверные middleware: запрос проходит логирование и авторизацию до настоящего `http.Transport`, ответ возвращается тем же путём; `logRT` — условный логирующий транспорт](img/roundtripper-chain.svg)

По аналогии с `HandlerFunc` удобно завести функциональный адаптер:

```go
type RoundTripFunc func(*http.Request) (*http.Response, error)
func (f RoundTripFunc) RoundTrip(r *http.Request) (*http.Response, error) { return f(r) }
```

Заодно это самый простой способ подменить сеть в unit-тесте.

## Тестирование клиента: httptest.Server

Если хочется проверить клиент целиком, а не только логику вокруг него, пригодится `httptest.Server`:

```go
srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    if r.URL.Path != "/v1/items" { t.Errorf("path %s", r.URL.Path) }
    w.Header().Set("Content-Type", "application/json")
    fmt.Fprint(w, `{"items":[]}`)
}))
defer srv.Close()

c := NewAPIClient(srv.URL, srv.Client())
```

`httptest.NewServer` поднимает настоящий сервер на `127.0.0.1` со случайным портом, так что проверяются и сериализация, и заголовки, и таймауты. Для TLS есть `NewTLSServer`; в паре с `srv.Client()` вы получаете клиент, который уже доверяет тестовому сертификату.

## Редиректы и cookies

По умолчанию `Client` следует максимум за 10 редиректами. Чтобы не следовать вовсе, функция `CheckRedirect` должна вернуть `http.ErrUseLastResponse`. При редиректе на другой домен заголовок `Authorization` не пересылается, чтобы токен не утёк чужому сайту. Cookies хранит `Jar` из пакета `net/http/cookiejar`, но по умолчанию его у клиента нет, и cookies между запросами не сохраняются.

## Типичные ошибки

1. `http.Get` или `DefaultClient` без таймаута.
2. Нет `defer resp.Body.Close()`, или он стоит **до** проверки `err`.
3. Создание `http.Client{Transport: &http.Transport{}}` на каждый запрос.
4. Ретраи POST без ключа идемпотентности или ретраи без backoff.
5. Изменение исходного `req` внутри RoundTripper.
6. `MaxIdleConnsPerHost = 2` при большом RPS к одному сервису, что оборачивается лавиной соединений в TIME_WAIT.
