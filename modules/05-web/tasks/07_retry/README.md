# 07. HTTP-клиент с ретраями и RoundTripper-middleware

Пакет `retry`. Урок: [HTTP-клиент в Go](../../lessons/05-http-client.md).

Сеть ненадёжна: соседний сервис перезапускается, балансировщик на секунду отдаёт 503, соединение рвётся посреди ответа. Повторить запрос кажется очевидным решением, но наивный ретрай легко превращает мелкий сбой в крупную аварию. Он может дважды списать деньги или добить и без того перегруженный сервис. Мы напишем клиент, который повторяет запросы аккуратно: только безопасные, только при временных ошибках и с растущей паузой между попытками.

Структуры `Client` и `Transport` описаны в `types.go`, там же указаны их поля и значения по умолчанию.

## Часть 1. `(*Client).Do`

```go
func (c *Client) Do(req *http.Request) (*http.Response, error)
```

Логику удобно разобрать по вопросам, которые клиент задаёт себе перед каждой попыткой.

1. Можно ли вообще повторять этот запрос? Только если метод идемпотентный (`GET HEAD OPTIONS TRACE PUT DELETE`) или в запросе есть заголовок `Idempotency-Key`. Кроме того, тело должно быть перечитываемым: `Body == nil`, `http.NoBody` или задан `req.GetBody` (его выставляет `http.NewRequest` для `*bytes.Reader`, `*strings.Reader` и `*bytes.Buffer`). Если хотя бы одно условие не выполнено, делается ровно одна попытка.
2. Когда повторять? При сетевой ошибке, кроме отмены или дедлайна `ctx` (тогда нужно сразу вернуть `ctx.Err()`), и при кодах `429, 500, 502, 503, 504`. Все остальные ответы, включая `501` и прочие `4xx`, возвращаются сразу.
3. Сколько ждать перед попыткой $n+1$, если $n$ попыток уже неудачны? Для `429` и `503` с корректным `Retry-After` берётся его значение, но не больше `MaxDelay`. `Retry-After` может содержать число секунд или HTTP-дату, которая отсчитывается от `c.Now()`; дата в прошлом означает паузу 0. В остальных случаях пауза растёт экспоненциально, `BaseDelay << (n-1)`, то есть $d_n = \min\left(\text{BaseDelay} \cdot 2^{n-1},\ \text{MaxDelay}\right)$: 100ms, 200ms, 400ms и так далее. Ждать нужно через `c.Sleep(ctx, d)`, и если `Sleep` вернул ошибку (отмена), её надо вернуть.
4. Что делать с телами? Тело неудачного ответа нужно дочитать (`io.Copy(io.Discard, io.LimitReader(...))`) и закрыть, иначе соединение не вернётся в пул. Для повторной попытки берётся свежее тело запроса из `req.GetBody()`.
5. Что вернуть в итоге? Если последняя попытка закончилась ретраибельным кодом, возвращается `(resp, nil)` как есть. Если последняя попытка закончилась сетевой ошибкой, возвращается ошибка, оборачивающая исходную через `%w`.

## Часть 2. `(*Transport).RoundTrip`

Вторая часть — RoundTripper-middleware, то есть обёртка на уровне транспорта. Она клонирует запрос через `req.Clone` (контракт `RoundTripper` запрещает менять исходный), добавляет заголовки из `t.Header`, но только те, которых ещё нет в запросе, вызывает `Base` (если он `nil`, используется `http.DefaultTransport`) и пишет в `Logf` одну строку на запрос:

```
GET http://host/items?id=1 -> 202 (3ms)
DELETE http://down.local/x -> error: connection reset by peer
```

## Подвохи

У `http.DefaultClient` нет таймаута, и зависший сервер подвесит вашу горутину навсегда.

Ретрай POST без ключа идемпотентности — прямой путь к двойному списанию денег.

Ретраи без backoff (и без jitter) добивают и без того лежащий сервис. У этого явления даже есть имя — retry storm.
