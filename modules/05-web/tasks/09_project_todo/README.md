# Задание 5. REST API задач (todo) на стандартной библиотеке

Пакет `todoapi`. Это итоговая задача модуля: собрать всё, что было в уроках 1–6, в один сервис.

Todo-список — учебный пример, но требования к нему вполне взрослые. Нужны пагинация, частичное обновление через `PATCH`, единый формат ошибок, строгая валидация входных данных и middleware, которые не дают сервису упасть от паники и позволяют найти запрос в логах. Если вы сделали предыдущие задачи модуля, почти все детали у вас уже есть, и осталось аккуратно собрать их вместе.

Готово: `store.go` содержит модель `Todo`, интерфейс `Store`, `ErrNotFound` и потокобезопасный `MemStore`. Написать нужно HTTP-слой:

```go
func NewServer(store Store, logger *slog.Logger) http.Handler
```

`NewServer` не запускает сервер, а возвращает `http.Handler`. В бою его кладут в `http.Server` с таймаутами и graceful shutdown (как в задаче 01), а в тестах его легко проверить через `httptest`.

## Эндпоинты

| Метод и путь | Успех | Особенности |
|---|---|---|
| `GET /healthz` | `200 {"status":"ok"}` | |
| `POST /todos` | `201` + `Location: /todos/{id}` + JSON задачи | тело `{"title": string, "done"?: bool}` |
| `GET /todos?limit=&offset=` | `200 {"items":[...],"total":N,"limit":L,"offset":O}` | `limit` по умолчанию 20, допустимо от 1 до 100; `offset` не меньше 0 (по умолчанию 0); `items` — всегда массив, не `null` |
| `GET /todos/{id}` | `200` + JSON | |
| `PATCH /todos/{id}` | `200` + обновлённая задача | тело `{"title"?: string, "done"?: bool}`; отсутствующие поля не меняются (используйте `*string`, `*bool`) |
| `DELETE /todos/{id}` | `204` | |

Задача в JSON выглядит так: `{"id":1,"title":"...","done":false,"created_at":"2024-03-01T10:00:00Z"}`.

## Ошибки — `application/problem+json`

Все ошибки отдаются в одном формате, с телом `{"title": http.StatusText(code), "status": code, "detail"?: "...", "errors"?: {"поле": "описание"}}`.

| Ситуация | Код |
|---|---|
| `id` не положительное целое | 400 |
| некорректные `limit`/`offset` (в `errors` — ключ параметра) | 400 |
| тело: не `application/json` | 415 |
| тело: битый JSON, неизвестное поле, неверный тип, больше одного объекта | 400 |
| тело больше 1 MiB | 413 |
| `title` после `TrimSpace` не от 1 до 200 рун (`errors.title`) | 422 |
| `PATCH` без полей (`{}`) | 422 |
| задачи нет (`ErrNotFound`) | 404 |
| любая другая ошибка хранилища — без деталей в ответе, детали в лог | 500 |
| паника в обработчике — Recover, лог `ERROR "panic"` | 500 |

На неподходящий метод (например, `PUT /todos/1`) сервис отвечает 405, и для этого достаточно штатного поведения `ServeMux`.

## Middleware

Нужны три middleware, знакомые по задаче 02.

- RequestID использует входящий `X-Request-ID`, если он валиден (от 1 до 64 символов из `[A-Za-z0-9_-]`), а иначе генерирует новый. ID возвращается в заголовке ответа, в том числе когда обработчик запаниковал.
- Logging на каждый запрос вызывает `logger.Info("request", "method", ..., "path", ..., "status", ..., "request_id", ...)`.
- Recover превращает панику в ответ 500 в формате problem+json, пишет `logger.Error("panic", ...)`, и сервер продолжает работать.

Порядок имеет значение. Подумайте, где должен стоять Logging, чтобы увидеть код 500 после паники.

## Подсказки

Заведите обёртку `handle(func(w, r) error) http.HandlerFunc`. Тогда во всём сервисе будет одно место, где ошибка превращается в ответ: `errors.As` для «своих» ошибок, `errors.Is(err, ErrNotFound)` для 404.

Не забудьте второй вызов `dec.Decode`, который проверяет, что в теле ровно один объект.

Тесты используют `httptest.NewServer` и фейковое хранилище, которое умеет возвращать ошибки и паниковать, так что эти ветки кода будут проверены.
