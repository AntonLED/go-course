# 04. Циклический барьер на `sync.Cond` (`barrier`)

Урок: [Синхронизация данных](../../lessons/03-sync.md)

Барьер — это точка синхронизации: `n` горутин вызывают `Wait()`, и ни одна не идёт дальше, пока не пришли все. Типичное применение — пошаговые симуляции. Все воркеры считают шаг `k`, ждут друг друга и только потом переходят к шагу `k+1`.

```go
func New(n int) *Barrier      // паника при n <= 0
func (b *Barrier) Wait() bool // true — ровно у одной (последней пришедшей) горутины фазы
```

Требования:

- Барьер многоразовый: когда фаза завершилась, те же горутины могут снова вызвать `Wait()`. Тест гоняет 200 фаз по 8 горутин.
- Пока пришло меньше `n` участников, никто не проходит.
- Реализация строится на `sync.Mutex` и `sync.Cond` (`Wait`/`Broadcast`), без каналов и без `sync.WaitGroup`.

## Подвох

Наивная реализация выглядит так: ждём, пока `count == n`, а потом последний пришедший обнуляет `count`. При повторном использовании она либо зависает, либо пропускает участников. Быстрая горутина успевает войти в следующую фазу и изменить `count` раньше, чем медленная проснётся и проверит условие.

Решение — счётчик поколений (generation). Горутина запоминает номер текущей фазы и ждёт, пока он не сменится.

Не забывайте о правилах работы с `sync.Cond`:

```go
c.L.Lock()
for !condition() { // всегда в цикле
	c.Wait()       // атомарно: Unlock + сон; при пробуждении снова Lock
}
c.L.Unlock()
```
