# 08. Свой errgroup (`errgroup`)

Урок: [Concurrency в Go: errgroup, singleflight](../../lessons/06-errgroup-singleflight.md)

Запустить несколько горутин, дождаться всех и вернуть первую ошибку, отменив остальных, — настолько частая задача, что для неё есть готовый пакет. Внешние зависимости в курсе недоступны, поэтому мы реализуем аналог
[`golang.org/x/sync/errgroup`](https://pkg.go.dev/golang.org/x/sync/errgroup) с тем же API:

```go
type Group struct{ /* ... */ }

func WithContext(ctx context.Context) (*Group, context.Context)
func (g *Group) Go(f func() error)
func (g *Group) TryGo(f func() error) bool
func (g *Group) SetLimit(n int)
func (g *Group) Wait() error
```

Поведение такое же, как в оригинале:

- Нулевое значение `Group{}` работоспособно: без лимита и без контекста.
- `Wait` ждёт все горутины и возвращает первую ненулевую ошибку, остальные отбрасываются.
- `WithContext` создаёт производный контекст через `context.WithCancelCause`:
  - при первой ошибке он отменяется, и причиной становится эта ошибка (`context.Cause(ctx) == err`);
  - после возврата из `Wait` он отменяется всегда, даже при успехе, но причина при этом не меняется.
- `SetLimit(n)` ограничивает число одновременно активных горутин значением `n`; при `n < 0` лимит снимается. Если вызвать `SetLimit(n)` с `n >= 0`, пока заняты слоты ранее установленного лимита (`len(sem) != 0`), произойдёт паника. Так же ведёт себя x/sync; если лимита не было, активные горутины не отслеживаются, и паники не будет.
- `Go` при достигнутом лимите блокируется, пока не освободится слот.
- `TryGo` при достигнутом лимите сразу возвращает `false` и не запускает `f`.

## Подсказки

Лимит проще всего сделать семафором на буферизованном канале: `sem <- struct{}{}` занимает слот, `<-sem` освобождает, а `len(sem)` показывает число занятых слотов.

`wg.Add(1)` вызывайте до `go`, а не внутри горутины.

Слот семафора освобождайте до `wg.Done()`, как это сделано в x/sync. Тогда после возврата из `Wait` все слоты гарантированно свободны, а тест как раз вызывает `TryGo` сразу после `Wait`.

Панику в `f` здесь перехватывать не нужно — это классическое поведение x/sync. В новых версиях x/sync она пере-бросается из `Wait`, подробнее об этом в уроке 6.

Первую ошибку удобно фиксировать через `sync.Once`.

Типичное использование выглядит так же, как с настоящим `x/sync/errgroup`:

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(8)
for _, url := range urls {
	g.Go(func() error { return fetch(ctx, url) })
}
if err := g.Wait(); err != nil { ... }
```
