# 09. Свой singleflight (`singleflight`)

Урок: [Concurrency в Go: errgroup, singleflight](../../lessons/06-errgroup-singleflight.md)

Представьте популярный ключ в кэше, у которого только что истёк срок жизни. В ту же секунду сотни запросов обнаруживают промах и одновременно идут в базу данных за одним и тем же значением. Это называется **cache stampede**, или «эффект толпы». Singleflight решает проблему так: в базу уходит один запрос, а остальные ждут и получают его результат.

Мы напишем аналог [`golang.org/x/sync/singleflight`](https://pkg.go.dev/golang.org/x/sync/singleflight),
но обобщённый: в оригинале ключ — `string`, а значение — `interface{}`. `Result` и `ErrPanicked`
уже объявлены в `types.go`.

```go
type Group[K comparable, V any] struct{ /* ... */ }

func (g *Group[K, V]) Do(key K, fn func() (V, error)) (v V, err error, shared bool)
func (g *Group[K, V]) DoChan(key K, fn func() (V, error)) <-chan Result[V]
func (g *Group[K, V]) Forget(key K)
```

Требования:

- Нулевое значение `Group` готово к работе.
- Пока для `key` выполняется `fn`, новые вызовы `Do` и `DoChan` с тем же ключом не вызывают `fn`, а ждут и получают тот же результат. Тест запускает 100 горутин и ожидает ровно 1 вызов.
- Если получателей было больше одного (считая исполнителя), у всех `shared == true`; у одиночного вызова — `false`.
- Результаты не кэшируются: после завершения вызова следующий `Do` снова вызывает `fn`.
- `DoChan` регистрирует вызов синхронно, до возврата, а канал результата буферизован (ёмкость 1).
- После `Forget(key)` следующий вызов стартует заново, не дожидаясь текущего, а те, кто уже ждёт, получают результат текущего. Здесь есть подвох: когда «старый» вызов завершится, он не должен удалить из карты запись «нового» вызова с тем же ключом.
- Паника в `fn`:
  - в `Do` она распространяется в горутину-исполнителя, ключ освобождается, а ожидающие получают ошибку, оборачивающую `ErrPanicked`, и не зависают навсегда;
  - в `DoChan` она не роняет процесс, и все получатели получают ошибку `ErrPanicked`.

## Подсказки

Внутреннее состояние одного вызова можно устроить так:

```go
type call[V any] struct {
	wg    sync.WaitGroup // ожидающие Do делают wg.Wait()
	val   V
	err   error
	dups  int
	chans []chan<- Result[V]
}
```

Под мьютексом группы проверьте карту и либо присоединитесь к уже идущему вызову (`dups++`), либо создайте новый `call`. Сам `fn` выполняйте вне мьютекса, иначе вызовы с разными ключами будут ждать друг друга.

Очистку делайте в `defer` с `recover()`, чтобы она выполнилась и при панике.
