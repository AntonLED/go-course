# 06. Worker pool с результатами и отменой (`workerpool`)

Урок: [Concurrency в Go: каналы и паттерны](../../lessons/04-channels-patterns.md)

Пул воркеров — рабочая лошадка любого бэкенда: скачать тысячу страниц, обработать очередь сообщений, пересчитать отчёты. Важно не только запустить N горутин, но и корректно их остановить, когда клиент ушёл или истёк таймаут. Тип `Result` уже объявлен в `types.go`. Реализуйте:

```go
func Run[T, R any](ctx context.Context, workers int, in <-chan T,
	f func(context.Context, T) (R, error)) <-chan Result[T, R]
```

Требования:

- Запускается ровно `workers` горутин-воркеров (при `workers <= 0` — одна). Каждая читает задачи из общего канала `in` и вызывает `f(ctx, v)`. Одновременно выполняется не больше `workers` вызовов `f`, и если задачи есть, эти вызовы действительно идут параллельно.
- Каждый результат отправляется в выходной канал, в том числе ошибочный: ошибка кладётся в `Result.Err`, и пул при этом не останавливается. Порядок результатов произвольный.
- Выходной канал закрывается, когда `in` закрыт и все задачи обработаны, либо когда отменён `ctx`.
- После отмены:
  - воркеры не берут новые задачи, даже если в `in` они есть. Помните, что `select` выбирает случайную из готовых веток, поэтому проверяйте `ctx.Err()` явно;
  - воркеры не блокируются навсегда на отправке результата, если потребитель ушёл;
  - все горутины пула завершаются (тест проверяет это через `runtime.NumGoroutine`).
- `f` получает тот же `ctx`, чтобы долгие задачи тоже могли прерваться.

Пример:

```go
in := make(chan string)
go func() { defer close(in); for _, u := range urls { in <- u } }()
for r := range workerpool.Run(ctx, 8, in, fetch) {
	if r.Err != nil { log.Printf("%s: %v", r.In, r.Err); continue }
	fmt.Println(r.In, len(r.Out))
}
```

## Подвох

Кто закрывает `out`? Точно не воркер: их несколько, и второй `close` вызовет панику. Закрывать канал должна отдельная горутина после `wg.Wait()`.
