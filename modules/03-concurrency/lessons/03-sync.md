# Урок 3. Синхронизация данных

## Data race

Как только две горутины начинают работать с общими данными, появляется вопрос, что каждая из них увидит. Самый неприятный ответ на него — гонка данных.

**Гонка данных (data race)** — это два обращения к одной переменной из разных горутин, из которых хотя бы одно является записью, и между которыми нет отношения happens-before. В Go гонка означает **неопределённое поведение** в широком смысле слова. Многословные значения — интерфейсы, срезы, строки — могут оказаться «порванными», когда половина полей новая, а половина старая. Цикл может крутиться вечно, потому что компилятор держит значение в регистре и не перечитывает его из памяти. А для map всё заканчивается `fatal error: concurrent map writes`.

Даже безобидный на вид инкремент — это гонка, потому что `counter++` состоит из трёх операций: прочитать, прибавить, записать.

```go
var counter int
for range 1000 {
	go func() { counter++ }() // read-modify-write: 3 операции, не атомарно
}
```

![Потерянное обновление: `counter++` — это load, add, store; при таком чередовании обе горутины прочитали 0 и обе записали 1](img/data-race.svg)

### Race detector

Искать гонки глазами бесполезно, для этого есть детектор гонок. Он включается флагом `-race` у всех основных команд:

```bash
go test -race ./...     go run -race main.go     go build -race
```

Детектор основан на ThreadSanitizer: компилятор инструментирует каждое обращение к памяти, а рантайм отслеживает порядок событий с помощью векторных часов. Важно понимать, что он находит только гонки, которые **реально случились** в данном прогоне. Ложных срабатываний у него нет, а вот пропуски возможны, поэтому гоняйте тесты под настоящей конкурентной нагрузкой.

Цена у детектора заметная: программа замедляется в 2–20 раз и потребляет в 5–10 раз больше памяти. Поэтому в проде его обычно не включают, а в CI он обязателен. На большинстве платформ ему нужен cgo (`CGO_ENABLED=1`).

## Модель памяти Go

Правила о том, какие записи какая горутина обязана увидеть, описаны в документе [go.dev/ref/mem](https://go.dev/ref/mem), редакция 2022 года. Его главный принцип называется DRF-SC: программа без гонок данных ведёт себя **последовательно согласованно**, как если бы все операции выполнялись в одном общем порядке. Гарантии видимости при этом даёт только отношение **happens-before**, и создают его вполне конкретные события:

| Событие A | happens-before B |
|---|---|
| `go f()` | начало выполнения `f` |
| отправка в канал | завершение соответствующего приёма |
| `close(ch)` | приём, вернувший нулевое значение из-за закрытия |
| приём из **небуферизованного** канала | завершение соответствующей отправки |
| $k$-й приём из канала ёмкости $C$ | завершение $(k+C)$-й отправки (так работает семафор) |
| `mu.Unlock()` ($n$-й) | возврат из `mu.Lock()` ($(n+1)$-й) |
| `once.Do(f)`: завершение `f` | возврат из любого `once.Do` |
| `wg.Done()` | возврат из `wg.Wait()`, который он разблокировал |
| атомарная операция A, значение которой видит атомарная B | B (атомики в Go — sequentially consistent) |

![Три ребра happens-before из таблицы. Вместе с порядком внутри горутины они транзитивно гарантируют, что запись `x = 1` видна в `print(x)`](img/happens-before.svg)

Обратите внимание, чего в таблице нет: завершение горутины **ни с чем не синхронизировано**. Без канала или `WaitGroup` главная горутина может так и не увидеть записей, сделанных дочерней. Пример ниже выглядит невинно, но содержит гонку: цикл может крутиться вечно, если `done` закешировано в регистре, или увидеть `done == true`, но ещё пустую `a`.

```go
var a string
var done bool
func setup() { a = "hello"; done = true }
func main() {
	go setup()
	for !done {} // гонка: может крутиться вечно (done в регистре) или увидеть done без a
	print(a)
}
```

## sync.Mutex и sync.RWMutex

Мьютекс — самый прямой способ защитить общее состояние. По соглашению его ставят в структуре прямо над полями, которые он защищает:

```go
type Cache struct {
	mu sync.RWMutex // защищает m; мьютекс принято ставить над защищаемыми полями
	m  map[string]string
}
func (c *Cache) Get(k string) (string, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.m[k]
	return v, ok
}
```

Нулевое значение мьютекса — это незаблокированный мьютекс, инициализировать его не нужно. Мьютекс в Go **не реентерабелен**: если горутина, уже держащая его, снова вызовет `Lock`, она заблокируется навсегда. Формально разблокировать мьютекс можно из другой горутины, но так никто не делает. А `Unlock` незаблокированного мьютекса приводит к `fatal error: sync: unlock of unlocked mutex`.

Внутри мьютекс устроен в несколько ступеней. Быстрый путь — одна операция CAS; если захватить не удалось, горутина недолго крутится в спин-цикле, а затем засыпает на семафоре рантайма. Чтобы ожидающие не голодали, у мьютекса есть **режим голодания** (starvation): если кто-то ждёт дольше 1 мс, мьютекс начинает передаваться ожидающим напрямую, в порядке FIFO.

`RWMutex` пускает внутрь либо много читателей, либо одного писателя. Чтобы писатель не голодал, новые `RLock` блокируются, как только писатель встал в очередь на `Lock`. Из этого вытекает неочевидная опасность: **рекурсивный `RLock` может привести к deadlock**. Горутина держит блокировку на чтение, в этот момент приходит писатель, и повторный `RLock` той же горутины ждёт писателя, который ждёт её саму. Выгоден `RWMutex` только при заметном преобладании чтений и нетривиальной критической секции; на коротких секциях обычный `Mutex` часто оказывается быстрее.

С версии 1.18 у мьютексов есть `TryLock`, но его использование почти всегда говорит о плохом дизайне. И общее правило для любых блокировок: держите критическую секцию короткой и не делайте под мьютексом никакого I/O.

![`RWMutex`: читатели R1 и R2 работают одновременно; писатель W ждёт, пока выйдут все читатели; R3, пришедший после W, ждёт уже писателя — отсюда deadlock при рекурсивном `RLock`](img/rwmutex.svg)

### Копирование мьютекса

Мьютекс хранит своё состояние в полях структуры, поэтому его копия — это отдельный, никак не связанный замок. Классическая ошибка — метод с получателем по значению:

```go
type Counter struct { mu sync.Mutex; n int }
func (c Counter) Inc() { c.mu.Lock(); c.n++; c.mu.Unlock() } // value receiver: копия мьютекса и n
```

`go vet` с анализатором **copylocks** сообщит `Inc passes lock by value`. Структуры, содержащие `sync.Mutex`, `WaitGroup`, `Once`, `Cond`, `atomic.Int64` и тому подобное, передавайте только по указателю. Как vet понимает, что копировать нельзя? Он считает «замком» любой тип с методами `Lock` и `Unlock`. Это сами `Mutex` и `RWMutex`, а также маркер `noCopy`, встроенный в `WaitGroup`, `Cond`, `Pool`, `atomic.Int64` и другие типы; `Once` же попадает под проверку потому, что содержит `Mutex`.

## sync.Once, OnceFunc, OnceValue

Ленивую инициализацию, которая должна выполниться ровно один раз, делают через `sync.Once`. С Go 1.21 появились обёртки `OnceFunc`, `OnceValue` и `OnceValues`, которые избавляют от пары глобальных переменных:

```go
var (
	cfgOnce sync.Once
	cfg     *Config
)
func Get() *Config {
	cfgOnce.Do(func() { cfg = load() }) // ровно один раз; остальные ждут завершения
	return cfg
}

// Go 1.21+: короче и без глобальных переменных
var getConfig = sync.OnceValue(func() *Config { return load() })
var getDB = sync.OnceValues(func() (*sql.DB, error) { return sql.Open("pgx", dsn) })
```

Поведение при панике у них различается. Если функция в `Do` паникует, `Once` всё равно считается выполненным, и повторных попыток не будет. `OnceFunc` и `OnceValue`, напротив, при каждом последующем вызове **повторяют ту же панику**. Вызов `once.Do` изнутри `f` того же `Once` приводит к deadlock.

Внутри `Once` сочетает атомарный флаг `done` для быстрого пути и мьютекс для медленного. Почему нельзя обойтись одним атомиком? Наивная реализация «`if atomic.Load == 0 { atomic.Store(1); f() }`» неверна: второй вызывающий увидит единицу и вернётся раньше, чем `f` закончит работу, то есть получит неинициализированные данные.

## sync/atomic

Для одиночных счётчиков и флагов мьютекс избыточен — хватит атомарных операций. С Go 1.19 в пакете есть типизированные атомики, которыми пользоваться намного приятнее, чем старыми функциями:

```go
var hits atomic.Int64       // Go 1.19+: типизированные атомики
hits.Add(1); hits.Load(); hits.Store(0)
hits.CompareAndSwap(old, new); hits.Swap(v)

var cfg atomic.Pointer[Config] // lock-free горячая замена конфигурации
cfg.Store(newCfg)
c := cfg.Load()

var v atomic.Value // любое значение, но всегда одного конкретного типа
```

У типов `atomic.Int64` и `atomic.Uint64` есть и менее заметное преимущество: они гарантированно выровнены на 8 байт. Функции вроде `atomic.AddInt64` на 32-битных платформах требуют ручного выравнивания, и забытое выравнивание — классический баг.

Атомики хороши, пока речь идёт об **одной** переменной. Инвариант, связывающий два поля (например, «`a+b == 100`»), атомиками не защитить: между двумя атомарными операциями другая горутина увидит промежуточное состояние. Здесь нужен мьютекс.

Для более сложных обновлений используют CAS-цикл. Вот как атомарно поддерживать максимум:

  ```go
  for { m := max.Load(); if v <= m || max.CompareAndSwap(m, v) { break } }
  ```

## sync.Cond

Условная переменная решает задачу «подождать, пока некоторое условие над защищённым состоянием станет истинным». Обратите внимание на цикл вокруг `Wait`: он обязателен, потому что между `Broadcast` и пробуждением условие могли снова изменить.

```go
c := sync.NewCond(&mu)
// ожидающий
mu.Lock()
for !ready {   // всегда в цикле: условие могли изменить между Broadcast и пробуждением
	c.Wait()   // атомарно: mu.Unlock + сон; перед возвратом снова mu.Lock
}
mu.Unlock()
// сигналящий
mu.Lock(); ready = true; mu.Unlock()
c.Broadcast()  // разбудить всех (Signal — одного)
```

![`sync.Cond`: `Wait` ставит горутину в очередь, отпускает `mu` и усыпляет её; `Broadcast` будит всех, но каждый снова захватывает `mu` и перепроверяет условие в цикле](img/cond.svg)

В Go `Cond` встречается редко, потому что обычно хватает каналов: `close(ch)` работает как broadcast. Но когда ждущих нужно будить многократно, не пересоздавая каналы (очереди, барьеры), `Cond` незаменим. Его главный минус — `Wait` нельзя прервать контекстом.

## sync.Pool

`sync.Pool` хранит временные объекты для повторного использования и тем самым снижает нагрузку на сборщик мусора. Типичные кандидаты — буферы и энкодеры:

```go
var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}
buf := bufPool.Get().(*bytes.Buffer)
buf.Reset()               // объект может быть «грязным»
defer bufPool.Put(buf)
```

Главное, что нужно понимать про пул: это **не кэш** и не пул соединений. Его содержимое может быть очищено на любой сборке мусора; начиная с Go 1.13 объекты переживают один цикл благодаря victim cache, но не больше. Храните в пуле указатели (`*bytes.Buffer`, `*[]byte`), иначе `Put` будет аллоцировать при упаковке значения в `any`. И не возвращайте в пул огромные буферы — ограничивайте `cap`, иначе память «залипнет» в пуле. Внутри пул устроен как набор списков на каждый P, работающих без блокировок, с возможностью подворовывать объекты у других P.

## sync.Map

`sync.Map` — потокобезопасная map с методами `Load/Store/LoadOrStore/LoadAndDelete/Delete/Range/Swap/CompareAndSwap`, а с 1.23 ещё и `Clear`. Соблазн использовать её везде велик, но выигрывает она у связки `map` и `RWMutex` только в двух случаях: когда ключ пишется один раз и много раз читается (кэши, которые только растут) и когда горутины работают с непересекающимися наборами ключей. В остальных случаях обычная `map` под `Mutex` проще, типобезопаснее и часто быстрее. Нулевое значение `sync.Map` готово к работе, а копировать её нельзя.

## Deadlock

Взаимная блокировка возможна, только когда одновременно выполняются четыре условия Коффмана: взаимное исключение, удержание ресурса во время ожидания другого, отсутствие вытеснения и **циклическое ожидание**. На практике разрывают обычно последнее. Классический пример — два мьютекса, которые захватываются в разном порядке:

```go
// g1: a.Lock(); b.Lock()     g2: b.Lock(); a.Lock()   → взаимная блокировка
```

Лечится это единым порядком захвата (например, по id объекта) и правилом не вызывать чужой код под своим мьютексом.

Рантайм умеет обнаруживать только **глобальный** deadlock, когда спят вообще все горутины: `fatal error: all goroutines are asleep - deadlock!`. Если жива хоть одна горутина — HTTP-сервер или даже таймер, — частичный deadlock останется незамеченным, и искать его придётся по дампу стеков (`SIGQUIT`, `pprof goroutine`).

У deadlock есть два родственника. При livelock горутины активны, но прогресса нет, потому что они бесконечно уступают друг другу. При starvation одна горутина систематически не получает ресурс, хотя остальные работают.
