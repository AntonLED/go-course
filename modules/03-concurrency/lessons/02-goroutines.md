# Урок 2. Горутины

## Запуск

Горутину запускает ключевое слово `go` перед вызовом функции. Обратите внимание на комментарии: аргументы и получатель метода вычисляются сразу, в текущей горутине, а в новой выполняется уже сам вызов.

```go
go f(x, y)            // аргументы вычисляются сейчас, в текущей горутине
go func() { ... }()   // анонимная функция
go obj.Method()       // значение получателя тоже вычисляется сразу
```

Привыкшим к потокам в других языках здесь многого не хватает. `go` не возвращает значения и не даёт «хэндла» горутины: нет join, нет идентификатора, нет способа убить горутину снаружи. Узнать о завершении или получить результат можно только через каналы, пакет `sync` или `context`. Это осознанное решение: горутина сама отвечает за то, когда ей закончиться.

Второе, что удивляет новичков: когда `main` возвращается, программа завершается **немедленно**. Остальные горутины никто не ждёт, и их `defer` не выполнятся.

```go
func main() {
	go fmt.Println("hello") // скорее всего ничего не напечатает
}
```

## Замыкания и переменная цикла

Классическая ловушка связана с тем, как замыкание захватывает переменную цикла. До Go 1.22 переменная `for i := ...` была **одна на весь цикл**, и все горутины, запущенные в теле, видели её последнее значение:

```go
for i := 0; i < 3; i++ {
	go func() { fmt.Print(i) }() // до 1.22: чаще всего "333"; с 1.22: 0,1,2 в произвольном порядке
}
```

![До Go 1.22 все замыкания захватывали одну переменную `i`, которую меняет `i++`; с Go 1.22 у каждой итерации своя `i`](img/loopvar.svg)

Начиная с Go 1.22 (если в go.mod указано `go 1.22` или новее), каждая итерация получает **свою** переменную. Старые обходные пути — `i := i` в теле цикла или передача аргументом `go func(i int){...}(i)` — больше не нужны, но вы ещё долго будете встречать их в чужом коде и на собеседованиях. Раньше об этой ошибке предупреждал `go vet` через анализатор `loopclosure`.

Новая семантика спасает только от общей переменной цикла. Если несколько горутин захватывают одну и ту же внешнюю переменную и пишут в неё, это по-прежнему гонка:

```go
sum := 0
for _, v := range nums {
	go func() { sum += v }() // DATA RACE
}
```

## sync.WaitGroup

Самый простой способ дождаться группы горутин — `sync.WaitGroup`. Это счётчик: `Add` увеличивает его, `Done` уменьшает, `Wait` блокируется, пока он не упадёт до нуля.

```go
var wg sync.WaitGroup
for _, u := range urls {
	wg.Add(1)          // ДО запуска горутины
	go func() {
		defer wg.Done() // defer — выполнится даже при панике/раннем return
		fetch(u)
	}()
}
wg.Wait()
```

Ошибиться с `WaitGroup` легко, и ошибки эти типовые. Если вызвать `wg.Add(1)` **внутри** горутины, `Wait` может выполниться раньше, чем хоть одна горутина успеет стартовать, увидеть ноль и сразу вернуться. Если передать `WaitGroup` **по значению** (`func worker(wg sync.WaitGroup)`), `Done` будет уменьшать копию, а `Wait` повиснет навсегда, и рантайм сообщит `all goroutines are asleep - deadlock!`; к счастью, это ловит `go vet` анализатором copylocks.

Если счётчик уйдёт в минус, получите `panic: sync: negative WaitGroup counter`. А повторное использование `WaitGroup` до того, как вернулся предыдущий `Wait`, приводит к панике или гонке. Наконец, в Go 1.25 появился метод `wg.Go(f)`, который сам делает `Add` и `Done`, но в Go 1.23 его ещё нет.

![`WaitGroup` во времени: `Wait` возвращается, когда счётчик падает до 0. Если `Add` вызывается внутри горутины, `Wait` может увидеть 0 раньше, чем горутины стартуют, и вернуться сразу](img/waitgroup.svg)

## Утечки горутин

Горутина, которая никогда не завершится, держит свой стек и всё, на что он ссылается, а сборщик мусора её не соберёт. Такие утечки копятся незаметно, пока сервис не начнёт пухнуть в памяти. Вот три типичные причины:

```go
// 1. Отправка, которую никто не прочитает
func first(urls []string) string {
	ch := make(chan string) // небуферизованный!
	for _, u := range urls {
		go func() { ch <- fetch(u) }()
	}
	return <-ch // остальные len(urls)-1 горутин висят на отправке навсегда
}
// Исправление: make(chan string, len(urls)) или select с ctx.Done().

// 2. Чтение из канала, который никто не закроет
go func() {
	for v := range in { ... } // если in не закрыт — висит вечно
}()

// 3. Бесконечный цикл без условия выхода / без ctx
go func() {
	for { poll(); time.Sleep(time.Second) }
}()
```

![Утечка в `first()`: main забирает первый результат и уходит, а две другие горутины навсегда остаются в `sendq` небуферизованного канала. Буфер на `len(urls)` позволяет всем отправкам завершиться](img/goroutine-leak.svg)

Отсюда главное правило этого урока: **запуская горутину, знайте, когда и как она завершится.** Если ответа нет, скорее всего, вы только что написали утечку. Искать их помогают `runtime.NumGoroutine()`, `pprof` (эндпоинт `/debug/pprof/goroutine?debug=2`) и библиотека `go.uber.org/goleak` в тестах. В задачах этого курса тесты сравнивают `NumGoroutine` до и после работы, делая несколько попыток, чтобы дать горутинам время завершиться.

## Паника в горутине роняет процесс

`recover` работает только в `defer` **той же** горутины, в которой случилась паника. Поэтому паника в дочерней горутине, не перехваченная в ней самой, завершает всю программу, даже если в `main` стоит `recover`:

```go
func main() {
	defer func() { recover() }() // НЕ поможет
	go func() { panic("boom") }()
	time.Sleep(time.Second)
}
// panic: boom  goroutine 6 [running]: ... exit status 2
```

![Паника раскручивает только стек своей горутины: `recover` в `main` её не видит, и рантайм завершает весь процесс](img/panic-goroutine.svg)

Поэтому в серверах и пулах воркеров тело каждой горутины оборачивают защитным `defer`:

```go
go func() {
	defer func() {
		if r := recover(); r != nil {
			log.Printf("panic: %v\n%s", r, debug.Stack())
		}
	}()
	work()
}()
```

Так, например, поступает `net/http` для каждого запроса: паника в хендлере рвёт соединение, но сервер продолжает работать. Помните, однако, что некоторые ошибки рантайма — `fatal error` вроде concurrent map writes, stack overflow или deadlock — `recover` не ловит вообще.

## runtime: полезные функции

Пакет `runtime` даёт несколько функций для наблюдения за горутинами и управления ими. Большинство из них нужны редко, но на собеседованиях про них спрашивают.

| Функция | Что делает |
|---|---|
| `runtime.NumGoroutine()` | число существующих горутин (включая main) |
| `runtime.Gosched()` | уступить P другим горутинам; текущая уходит в **глобальную** очередь и продолжится позже. С асинхронным вытеснением нужна редко |
| `runtime.Goexit()` | завершить текущую горутину, выполнив её `defer`ы. В `main` — остальные горутины продолжают работать, потом deadlock |
| `runtime.GOMAXPROCS(0)` | прочитать число P |
| `runtime.LockOSThread()` | привязать горутину к потоку (для C-библиотек, OpenGL, namespaces) |
| `runtime.Stack(buf, true)` | дамп стеков всех горутин |

С `Gosched` связан популярный вопрос на порядок вывода. В примере ниже на одном P вы почти всегда увидите сначала `B`, потом `A`, но это наблюдение, а не гарантия, и строить на нём синхронизацию нельзя:

```go
runtime.GOMAXPROCS(1)
go fmt.Println("B")
runtime.Gosched()
fmt.Println("A") // почти всегда "B", затем "A" — но это НЕ гарантия, не синхронизируйтесь так
```

## Сколько стоит горутина

Горутина дешёвая, но не бесплатная. Она занимает около 2 КБ стека плюс структуру `g` примерно на 400 байт, а создаётся за 0,3–1 мкс. Переключение между горутинами обходится в 100–200 нс, потому что происходит в user space без перехода в ядро; переключение потоков ОС измеряется уже микросекундами.

Дешевизна самой горутины не делает дешёвой работу, которую она держит. Миллион горутин, ждущих HTTP-ответа, — это миллион открытых соединений, и упрётесь вы в них, а не в память под стеки. Поэтому параллелизм ограничивают пулом воркеров или семафором; оба приёма разобраны в уроке 4.

## Паттерн «горутина с результатом»

Раз `go` не возвращает значения, результат передают через канал. Удобная обёртка выглядит так; буфер размером 1 важен, потому что без него горутина зависнет навсегда, если результат так и не прочитают.

```go
func async[T any](f func() T) <-chan T {
	ch := make(chan T, 1) // буфер 1: горутина не зависнет, если результат не прочитают
	go func() { ch <- f() }()
	return ch
}
```
