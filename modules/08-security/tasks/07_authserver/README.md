# 07. Мини authorization server

Задача к уроку [«Аутентификация и авторизация (OAuth 2.0)»](../../lessons/05-oauth2.md).

В предыдущей задаче вы писали OAuth-клиента. Теперь посмотрим на протокол с другой стороны. Сервер авторизации — самое чувствительное место всей схемы: он выдаёт одноразовые коды, проверяет PKCE, аутентифицирует клиентов и отвечает на introspection. Малейшая небрежность здесь, например нестрогое сравнение `redirect_uri`, превращает его в инструмент для фишинга.

## Что сделать

Код пишется в `authserver.go`. `Client`, `Options` и `UserHeader` уже есть в `types.go`.

```go
func New(clients []Client, opts Options) *Server
func (s *Server) ServeHTTP(w http.ResponseWriter, r *http.Request)
```

### GET /authorize

Проверки выполняются сверху вниз. Первые две ошибки показываются прямо на странице сервера, остальные возвращаются клиенту через редирект:

| Проверка | При провале |
|---|---|
| `client_id` известен | 400, без редиректа |
| `redirect_uri` точно совпадает с зарегистрированным (не передан и зарегистрирован один — берём его) | 400, без редиректа |
| `response_type=code` | 302 `…?error=unsupported_response_type&state=…` |
| `code_challenge_method=S256`, `code_challenge` из 43 символов | 302 `error=invalid_request` |
| scopes ⊆ `Client.Scopes` (пустой — все разрешённые) | 302 `error=invalid_scope` |
| пользователь «вошёл» (заголовок `X-User`) | 302 `error=access_denied` |

При успехе сервер отвечает `302 redirect_uri?code=<32 случайных байта>&state=<state>`, сохраняя query, который уже был в `redirect_uri`.

Код живёт `CodeTTL` и действителен, пока

$$
t_\text{now} < t_\text{выдан} + \text{CodeTTL},
$$

то есть ровно в момент $t_\text{выдан} + \text{CodeTTL}$ он уже просрочен. Access token с `TokenTTL` ведёт себя так же — как `exp` в JWT.

### POST /token

Сначала сервер аутентифицирует клиента. Конфиденциальный клиент может аутентифицироваться только через HTTP Basic: id и secret раскодируются через `url.QueryUnescape`, а secret сравнивается за постоянное время. Публичный клиент передаёт `client_id` в форме. Если аутентификация не удалась, ответ — `401 {"error":"invalid_client"}` с заголовком `WWW-Authenticate`.

Для `grant_type=authorization_code` код должен существовать, быть не истёкшим и выданным именно этому клиенту; `redirect_uri` должен совпадать с переданным в `/authorize`; наконец, должно выполняться `BASE64URL(SHA256(code_verifier)) == code_challenge`. Любое нарушение даёт `400 invalid_grant`.

Код одноразовый. При повторном предъявлении сервер отвечает `invalid_grant` и вдобавок отзывает все токены, выданные по этому коду (RFC 6749 §4.1.2): раз код предъявили дважды, его, скорее всего, украли, и уже выданному токену доверять нельзя.

`grant_type=client_credentials` доступен только конфиденциальным клиентам; публичный получает `unauthorized_client`. В выданном токене `sub = client_id`.

Любой другой `grant_type` даёт `unsupported_grant_type`.

Успешный ответ выглядит как `{"access_token","token_type":"Bearer","expires_in","scope"}` и сопровождается заголовком `Cache-Control: no-store`.

### POST /introspect (RFC 7662)

Эндпоинт доступен только клиенту с Basic-аутентификацией. Для действующего токена он отвечает `{"active":true,"sub","client_id","scope","exp","token_type"}`, для любого другого — просто `{"active":false}`.

## Подвохи

Главная опасность — open redirect. Если клиент неизвестен или `redirect_uri` чужой, редиректить нельзя даже ради того, чтобы сообщить об ошибке, иначе ваш сервер авторизации превращается в доверенный редиректор на фишинговую страницу. Сравнение только точное: никаких префиксов, `/..`, завершающего `/` или лишнего query.

Метод PKCE `plain` мы не принимаем: в нём challenge совпадает с verifier, и защищает он только от части атак.

Одноразовость кода должна выдерживать конкуренцию. В тестах 20 параллельных обменов одного и того же кода, и успешным должен оказаться ровно один.

Время берите только из `Options.Now`.
