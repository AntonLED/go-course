# 08. Задание 8: защищённый API

Финальная задача модуля «Вопросы безопасности».

Соберём всё вместе. Сервис `items` должен ответить на четыре вопроса о каждом запросе: какой сервис звонит, от имени какого пользователя, не слишком ли часто и что этому пользователю можно. Сервис принимает запросы только от доверенных сервисов (mTLS), действует от имени пользователя из JWT, ограничивает частоту запросов и отвечает правильными кодами — 401, 403 и 429.

```
orders (сертификат spiffe://shop.local/orders) ──mTLS──▶ items API
          Authorization: Bearer <JWT пользователя>          │
                                                            ├─ 1. кто звонит? (сертификат → AllowedServices)   401/403
                                                            ├─ 2. от чьего имени? (JWT HS256, kid, exp, iss, aud) 401
                                                            ├─ 3. не слишком ли часто? (token bucket по sub)     429
                                                            └─ 4. что ему можно? (scope / роль)                  403
```

## Что сделать

Код пишется в `secureapi.go`. `Config`, `Item` и константы прав уже есть в `types.go`.

```go
func ServerTLSConfig(certPEM, keyPEM, clientCAPEM []byte) (*tls.Config, error)
func NewAPI(cfg Config) http.Handler
```

| Маршрут | Требование | Ответ |
|---|---|---|
| `GET /healthz` | — | `200 ok` |
| `GET /v1/items` | scope `items:read` | `200 [...]` (пустой — `[]`) |
| `POST /v1/items {"name"}` | scope `items:write` | `201 Item` (ID `"1"`, `"2"`…), плохое тело → `400` |
| `DELETE /v1/items/{id}` | роль `admin` (claim `roles`) | `204` / `404` |

Для маршрутов `/v1/*` проверки выполняются строго в таком порядке.

1. **mTLS.** Идентичность сервиса берётся из проверенного сертификата: SPIFFE URI SAN, а если его нет — CN. Нет сертификата — `401`, сервиса нет в `AllowedServices` — `403`.
2. **JWT.** Токен берётся из `Authorization: Bearer …`. Допускается только `HS256`, ключ выбирается по `kid` из `JWTKeys`, `exp` обязателен; также проверяются `nbf`, `iss`, `aud` (строка или массив) и непустой `sub`, всё с учётом `Leeway`.
   - Если заголовка нет, ответ — `401` с `WWW-Authenticate: Bearer realm="api"`, без параметра `error` (RFC 6750 §3.1).
   - Любой невалидный токен даёт `401` с `WWW-Authenticate: Bearer realm="api", error="invalid_token"`.
3. **Rate limit.** На каждый `sub` заводится token bucket ёмкостью `Burst`, который пополняется со скоростью `RatePerSecond`; время берётся из `cfg.Now`. Если корзина пуста — `429` и заголовок `Retry-After` в целых секундах, минимум 1.
4. **Права.** Если нет нужного scope — `403` с `WWW-Authenticate: Bearer realm="api", error="insufficient_scope", scope="items:write"`; если нет роли — просто `403`.

Все ошибки возвращаются в JSON: `{"error": "..."}`.

## Подвохи

Разница между 401 и 403 — не формальность. 401 означает «не знаю, кто ты»: учётных данных нет или они битые. 403 означает «знаю, кто ты, но нельзя». Сервис с валидным сертификатом, которого нет в списке разрешённых, получает 403, а не 401.

`scope` — это список, разделённый пробелами, и `items:readonly` не даёт права `items:read`. Поэтому проверять через `strings.Contains` нельзя, нужно разбить строку и искать точное совпадение.

`alg: none` и неизвестный `kid` отклоняются. Подпись проверяется до разбора claims и сравнивается через `hmac.Equal`.

Корзина rate limit не должна копить больше `Burst` токенов, даже если сервис простаивал час. Иначе после простоя клиент получит внезапный залп запросов.

Место rate limit в цепочке выбрано не случайно. Он стоит после аутентификации, потому что иначе не по чему считать, и до авторизации — так что запросы без нужных прав тоже тратят лимит, и подбирать права перебором не выйдет.

В `ServerTLSConfig` не игнорируйте результат `AppendCertsFromPEM`: если он вернул `false`, возвращайте ошибку. С пустым пулом сервер молча отвергнет всех клиентов, и искать причину придётся долго.
