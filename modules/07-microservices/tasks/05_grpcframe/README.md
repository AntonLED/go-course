# 05. gRPC-фрейминг и мини-RPC с мультиплексированием

Задача к уроку [«gRPC + protobuf»](../../lessons/03-grpc-protobuf.md).

Если снять с gRPC всю обвязку, останется довольно простая конструкция. Каждый вызов — это поток HTTP/2, в DATA-фреймах которого лежат сообщения с 5-байтным префиксом, а статус вызова приходит в трейлерах. Много вызовов идут по одному TCP-соединению одновременно и не мешают друг другу. В этой задаче вы соберёте то же самое в миниатюре поверх одного `net.Conn` (в тестах это `net.Pipe`) и заодно наступите на все грабли мультиплексирования.

## Часть 1. Фрейминг сообщений (`frame.go`)

```go
func WriteMessage(w io.Writer, msg []byte, compressed bool) error
func ReadMessage(r io.Reader, maxSize int) (msg []byte, compressed bool, err error)
```

Формат gRPC Length-Prefixed-Message: `[flag: 1 байт 0|1][длина: 4 байта big-endian][сообщение]`. Например, `"hi"` кодируется как `00 00 00 00 02 68 69`.

`ReadMessage` по-разному сообщает о разных проблемах:

| Ситуация | Результат `ReadMessage` |
|---|---|
| поток пуст | `io.EOF` |
| оборван заголовок или тело | `io.ErrUnexpectedEOF` |
| флаг не 0/1 | `ErrInvalidFlag` |
| длина > `maxSize` | `ErrMessageTooLarge` — до выделения памяти |

Последняя строка важна: если сначала выделить буфер под заявленную длину, злоумышленник одним заголовком заставит вас аллоцировать 4 ГБ.

`WriteMessage` делает ровно один вызов `Write`.

## Часть 2. Мини-RPC (`rpc.go`)

```go
func NewServer() *Server
func (s *Server) HandleUnary(method string, h UnaryHandler)
func (s *Server) HandleStream(method string, h StreamHandler)
func (s *Server) Serve(conn net.Conn) error

func NewClient(conn net.Conn) *Client
func (c *Client) Call(ctx context.Context, method string, req []byte) ([]byte, error)
func (c *Client) Stream(ctx context.Context, method string, req []byte) (*ClientStream, error)
func (s *ClientStream) Recv() ([]byte, error)
func (c *Client) Close() error
```

Транспортный фрейм устроен так: `[stream id: 4][тип: 1][длина: 4][payload]`, все числа big-endian. Константы типов лежат в `types.go`. Обмен выглядит так:

```
клиент                                   сервер
HEADERS(id=1, таймаут_нс, "/svc/Method") ─▶
DATA(id=1, 00 00 00 00 03 'abc')          ─▶   обработчик в своей горутине
                                          ◀─ DATA(id=1, ...)     × N (стриминг)
                                          ◀─ TRAILERS(id=1, code, message)
CANCEL(id=1)  — если клиенту результат больше не нужен
```

Требования:

- **Мультиплексирование.** По одному соединению одновременно идёт много вызовов, и медленный вызов не блокирует быстрые. Ответы раскладываются по stream id; клиентские id нечётные: 1, 3, 5…
- **Статусы.** Если обработчик вернул ошибку, в трейлеры уходят `CodeOf(err)` и текст ошибки; `*Status` передаётся со своим кодом и сообщением. Неизвестный метод даёт `Unimplemented`, паника — `Internal`, запрос больше `MaxRecvMsgSize` — `ResourceExhausted`, причём соединение после этого продолжает работать. Клиент возвращает ошибки как `*Status`.
- **Дедлайны.** Клиент передаёт в HEADERS остаток времени до дедлайна своего ctx, а сервер создаёт контекст с этим таймаутом — так же, как работает заголовок `grpc-timeout`.
- **Отмена.** Если ctx клиента отменён или истёк, клиент возвращает `Canceled` или `DeadlineExceeded` соответственно и отправляет CANCEL, а сервер отменяет контекст обработчика.
- **Стриминг.** `Recv` возвращает сообщения по порядку, а затем `io.EOF`, если статус OK, или `*Status`.
- **Обрыв соединения.** Все висящие и все последующие вызовы получают `Unavailable`.
- `Serve` возвращает `nil`, когда клиент закрыл соединение, и перед выходом дожидается всех своих горутин.

## Подвохи

Писать в `net.Conn` из разных горутин можно только под mutex и только целыми фреймами, иначе байты двух фреймов перемешаются.

Горутина-читатель на клиенте не должна блокироваться, если кто-то не вычитывает свой поток. Иначе один нерасторопный потребитель остановит все потоки сразу — это классическая head-of-line blocking. Хорошо работает неограниченная очередь на каждый поток плюс канал-уведомление с буфером 1.

Помните, что `net.Pipe` синхронный: `Write` ждёт, пока на другой стороне сделают `Read`. Поэтому сервер не должен писать из горутины-читателя, если эта запись может заблокироваться, — получите взаимную блокировку.

Unary-ответ считается успешным только после того, как пришли трейлеры со статусом OK. Сам по себе DATA-фрейм ещё ничего не гарантирует.
