# 02. Retry + Idempotency-Key

Задача к уроку [«Введение в микросервисы»](../../lessons/01-intro.md).

Сеть ненадёжна, и самый неприятный её сбой выглядит безобидно: запрос дошёл до сервера и выполнился, а ответ потерялся по дороге. Клиент видит таймаут и повторяет запрос — и деньги списываются второй раз. Поэтому повторять можно только те запросы, дубли которых сервер умеет распознать. В этой задаче вы реализуете обе стороны: клиентские повторы с экспоненциальной паузой и серверную идемпотентность по заголовку `Idempotency-Key`.

## Что сделать

Код пишется в `retry.go`. Типы `Policy`, `RetryAfterer`, ошибка `ErrExhausted` и имена заголовков уже есть в `types.go`.

```go
func Permanent(err error) error
func Backoff(p Policy, attempt int) time.Duration
func Do(ctx context.Context, p Policy, fn func(ctx context.Context, attempt int) error) error
func NewKey() string
func Idempotency(next http.Handler) http.Handler
```

### Do

Номер попытки `attempt` начинается с 1. Если `MaxAttempts <= 0`, выполняется ровно одна попытка.

После неудачной попытки с номером $n$ функция ждёт `Backoff(p, n)`:

$$
\text{Backoff}(p, n) = \min\left(\text{BaseDelay} \cdot \text{Multiplier}^{\,n-1},\ \text{MaxDelay}\right)
$$

Ограничение сверху действует, только когда `MaxDelay` задан. К результату затем применяется `Jitter`, если он задан. Исключение — ошибка, реализующая `RetryAfterer` с положительным значением: сервер сам подсказал, сколько ждать, и мы ждём ровно столько.

Не каждую ошибку имеет смысл повторять:

- если ошибка обёрнута в `Permanent(err)`, `Do` немедленно возвращает исходную `err`, без обёртки `Permanent`;
- если `Retryable` вернул false, ошибка тоже возвращается как есть;
- по умолчанию не повторяются `context.Canceled` и `context.DeadlineExceeded`.

Когда попытки кончились, `Do` возвращает ошибку, для которой одновременно выполняются `errors.Is(err, ErrExhausted)` и `errors.Is(err, последняя)`, — вызывающему полезно знать и то, что мы сдались, и почему.

Отмена контекста прерывает паузу между попытками. Результат в этом случае удовлетворяет и `Is(ctx.Err())`, и `Is(последняя ошибка)`.

### Idempotency (middleware)

Middleware запоминает ответы по ключу и ведёт себя так:

| Ситуация | Ответ |
|---|---|
| нет `Idempotency-Key` | просто `next` |
| новый ключ | выполнить `next`, запомнить статус, заголовки, тело |
| тот же ключ + тот же запрос (метод, URI, тело) | сохранённый ответ + `Idempotent-Replayed: true`, `next` не вызывается |
| тот же ключ + другой запрос | `422 Unprocessable Entity` |
| тот же ключ, первый запрос ещё выполняется | `409 Conflict` |
| `next` ответил 5xx | не запоминать — повтор должен выполниться заново |

## Подвохи

Тело запроса можно прочитать только один раз. Прочитав его для хеша, положите обратно в `r.Body` через `io.NopCloser(bytes.NewReader(b))`, иначе `next` получит пустое тело.

Ключ нужно «застолбить» под mutex до вызова `next`. Если сначала выполнить обработчик, а потом записать ключ, два параллельных дубля успеют выполниться оба.

На стороне клиента один и тот же ключ используется для всех попыток одной операции — в этом весь смысл. А вот тело запроса придётся создавать заново на каждую попытку: прочитанный `io.Reader` второй раз не отправить.

И проверьте `Backoff` на больших `attempt`: экспонента быстро растёт, и пауза не должна переполниться в отрицательное значение.
