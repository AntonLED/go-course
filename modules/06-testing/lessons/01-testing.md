# Урок 1. Тестирование в Go

## go test: соглашения

В Go нет отдельного тестового фреймворка, который нужно выбирать и настраивать: всё необходимое уже лежит в стандартной библиотеке и в команде `go test`. Взамен язык требует соблюдать несколько соглашений, и их стоит знать наизусть.

Тесты живут в файлах с суффиксом `*_test.go`. Такие файлы компилируются только командой `go test` и в обычную сборку не попадают, поэтому тестовые хелперы и фейки никак не раздувают итоговый бинарник. Тестом считается функция вида `func TestXxx(t *testing.T)`, причём после слова `Test` должна идти не строчная буква: `TestFoo`, `Test_foo` и `Test1` подойдут, а `Testfoo` будет молча проигнорирована, что порой стоит часа недоумения.

Чаще всего вы будете запускать `go test ./...`, то есть тесты всех пакетов модуля. Дальше в ход идут флаги. `-run 'Regexp/Подтест'` отбирает тесты и подтесты по регулярному выражению, `-v` включает подробный вывод, `-count=1` запрещает брать результат из кэша, `-failfast` останавливает прогон на первом упавшем тесте. Флаг `-timeout 30s` ограничивает время работы; по умолчанию лимит составляет 10 минут, и если тест его превысит, бинарник запаникует и напечатает дамп всех горутин, что само по себе полезно для поиска зависаний.

Кэш результатов заслуживает отдельного разговора, потому что он регулярно сбивает с толку. Успешные результаты кэшируются только в режиме списка пакетов, то есть когда вы явно перечисляете пакеты (`go test ./...`, `go test .`). Просто `go test` без аргументов кэш не использует. Кроме того, все переданные флаги должны входить в «кэшируемый» набор: `-run`, `-v`, `-short`, `-timeout`, `-failfast`, `-cpu`, `-parallel`, `-benchtime`, `-list`, `-fullpath`. Тест перезапустится, если изменился сам тестовый бинарник (исходники или build-флаги) либо переменные окружения и файлы, которые тест читал. Любой флаг вне этого набора отключает кэш, и идиоматичный способ сделать это нарочно — `-count=1`.

![Для каждого пакета `go test` собирает отдельный бинарник `foo.test`; при повторном запуске результат берётся из кэша, если не изменились бинарник, флаги, прочитанные переменные окружения и файлы. Упавшие прогоны в кэш не попадают](img/go-test-pipeline.svg)

```go
func TestAbs(t *testing.T) {
    if got := Abs(-2); got != 2 {
        t.Errorf("Abs(-2) = %d, want 2", got) // продолжает тест
    }
}
```

Сообщить о провале можно двумя способами. `t.Error` и `t.Errorf` помечают тест упавшим, но дают ему доработать до конца, и это удобно, когда проверок несколько и хочется увидеть все расхождения сразу. `t.Fatal` и `t.Fatalf` устроены как `Error` плюс `FailNow`: тест прерывается немедленно. Здесь кроется частая ловушка. `FailNow` вызывает `runtime.Goexit()`, а значит, **работает только в горутине самого теста**. Если вызвать `t.Fatal` из горутины, которую тест запустил, завершится лишь эта горутина, а тест продолжит выполняться как ни в чём не бывало. Анализатор `testinggoroutine` из `go vet` такие места находит; в порождённых горутинах используйте `t.Error` и обычный `return`.

## Табличные тесты и подтесты

Большинство функций приходится проверять на множестве входов: обычный случай, пустая строка, переполнение, некорректный формат. Писать для каждого случая отдельную функцию утомительно, поэтому в Go сложилась идиома табличного теста: кейсы описываются срезом структур, а проверка пишется один раз в цикле.

```go
func TestParseSize(t *testing.T) {
    tests := []struct {
        name    string
        in      string
        want    int64
        wantErr bool
    }{
        {"bytes", "10", 10, false},
        {"kilo", "2K", 2048, false},
        {"empty", "", 0, true},
        {"overflow", "99999999999P", 0, true},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := ParseSize(tt.in)
            if (err != nil) != tt.wantErr {
                t.Fatalf("err = %v, wantErr %v", err, tt.wantErr)
            }
            if got != tt.want {
                t.Errorf("ParseSize(%q) = %d, want %d", tt.in, got, tt.want)
            }
        })
    }
}
```

Новый кейс здесь добавляется одной строкой. Но настоящую силу приёму придаёт `t.Run`, который превращает каждую строку таблицы в именованный подтест. У подтеста есть имя, так что его можно запустить отдельно (`-run 'TestParseSize/kilo'`). `Fatal` внутри подтеста прерывает только его, а соседние кейсы продолжают выполняться. И наконец, подтесты можно запускать параллельно.

### t.Parallel и переменная цикла

```go
for _, tt := range tests {
    t.Run(tt.name, func(t *testing.T) {
        t.Parallel() // подтест ставится на паузу до завершения родительской функции
        check(t, tt)
    })
}
```

Чтобы понять, что здесь происходит, важно знать порядок выполнения. Подтест, вызвавший `t.Parallel()`, сразу возвращает управление родителю и ждёт. Цикл в `TestX` продолжается, регистрирует остальные подтесты, и лишь когда функция `TestX` вернулась, все параллельные подтесты стартуют вместе.

![Подтест с `t.Parallel()` сразу возвращает управление родителю и ждёт. Когда функция `TestX` вернулась, параллельные подтесты выполняются вместе, а сам `TestX` завершается (Cleanup, PASS) только после них](img/parallel-subtests.svg)

Из этого порядка и вырастала знаменитая ошибка. До Go 1.22 переменная `tt` была одна на весь цикл, и к моменту, когда параллельные подтесты наконец запускались, цикл уже закончился, а `tt` указывала на **последний** элемент таблицы. Все подтесты дружно проверяли один и тот же кейс, и тест зеленел, ничего толком не проверив. Лечилось это строчкой `tt := tt` в начале тела цикла. Начиная с Go 1.22 (если в go.mod указано `go 1.22` или новее) переменная цикла создаётся заново на каждой итерации, и проблема исчезла сама собой. В старом коде вы ещё долго будете встречать `tt := tt`, так что полезно понимать, откуда она взялась.

Число одновременно работающих параллельных тестов ограничено флагом `-parallel`, который по умолчанию равен GOMAXPROCS. И учтите, что `t.Setenv` (а с Go 1.24 и `t.Chdir`) несовместимы с `t.Parallel`: они меняют состояние всего процесса, поэтому такое сочетание приводит к панике.

## Хелперы и ресурсы

Как только тестов становится больше десятка, в них появляются повторяющиеся куски: открыть файл, создать временный каталог, поднять фейковый сервер. Такие куски выносят в хелперы, и `testing` даёт для этого два важных инструмента.

```go
func mustOpen(t *testing.T, path string) *os.File {
    t.Helper() // строка ошибки укажет на вызывающего, а не на эту функцию
    f, err := os.Open(path)
    if err != nil {
        t.Fatalf("open %s: %v", path, err)
    }
    t.Cleanup(func() { f.Close() }) // выполнится после теста (и подтестов), LIFO
    return f
}

dir := t.TempDir()           // уникальный каталог, удаляется автоматически
t.Setenv("APP_MODE", "test") // восстановится после теста
```

Первый инструмент — `t.Helper()`. Без него сообщение об ошибке указывало бы на строку внутри `mustOpen`, и из двадцати вызовов хелпера было бы непонятно, какой именно упал. С `t.Helper()` фреймворк пропускает кадр хелпера и показывает место вызова.

Второй — `t.Cleanup`. Он регистрирует функцию, которая выполнится после завершения теста и всех его подтестов; если таких функций несколько, они вызываются в обратном порядке регистрации (LIFO). Чем это лучше `defer`? Тем, что `defer` срабатывает при выходе из функции теста, то есть ещё до того, как запустятся параллельные подтесты, и ресурс закроется у них из-под носа. К тому же `defer` нельзя поставить изнутри хелпера так, чтобы он сработал в конце теста. На `t.Cleanup` построены и готовые удобства: `t.TempDir()` создаёт уникальный каталог и сам его удаляет, а `t.Setenv` восстанавливает прежнее значение переменной окружения.

![`defer` срабатывает при возврате из функции теста, ещё до параллельных подтестов; `t.Cleanup` вызывается после теста и всех подтестов, в обратном порядке регистрации (LIFO)](img/cleanup-order.svg)

Если хелпер принимает не `*testing.T`, а интерфейс `testing.TB`, он работает и в тестах, и в бенчмарках. Есть и неочевидный бонус: такой хелпер можно протестировать, подсунув ему фейковый `TB`. Именно этим вы займётесь в задачах 01 и 08.

## testdata и golden-файлы

Тестам часто нужны входные файлы: примеры конфигов, JSON-ответы, эталонный вывод. Для них предусмотрен каталог `testdata/`, который `go build` и `go vet` игнорируют. Тест всегда запускается с рабочим каталогом, равным каталогу пакета, поэтому относительный путь вида `testdata/x.json` работает независимо от того, откуда вы вызвали `go test`.

Особенно удобен этот каталог для **golden-файлов**. Golden-файл — это эталонный вывод, который лежит рядом с тестом. Когда функция выдаёт большой HTML, JSON или текстовый отчёт, сравнивать его с файлом гораздо приятнее, чем держать многострочный литерал прямо в коде теста. Обновляют эталон специальным флагом:

```go
var update = flag.Bool("update", false, "update golden files")

if *update { os.WriteFile(golden, got, 0o644) }
want, _ := os.ReadFile(golden)
if !bytes.Equal(got, want) { t.Errorf(...) }
// go test ./pkg -run TestRender -args -update   ← и обязательно посмотреть git diff!
```

После обновления эталонов обязательно просмотрите `git diff`: флаг `-update` честно запишет в файл и ошибочный вывод, а тест после этого, разумеется, пройдёт. Второе требование — детерминированность. Если вывод зависит от порядка обхода map, текущего времени или адресов в памяти, golden-тест будет падать через раз, поэтому ключи map сортируйте, а время и адреса в вывод не пускайте.

## Black-box: пакет `xxx_test`

Файл `foo_test.go` может объявить не `package foo`, а `package foo_test`. Это отдельный пакет, который лежит в том же каталоге, но видит только экспортированное API пакета `foo`, в точности как его настоящий пользователь. Такой приём полезен в двух ситуациях. Во-первых, он заставляет тестировать публичный контракт, а не детали реализации, и тесты перестают ломаться при каждом внутреннем рефакторинге. Во-вторых, он разрывает циклы импорта: если тесту пакета `a` нужен пакет `b`, а `b` сам импортирует `a`, из `package a` такой импорт невозможен, а из `package a_test` вполне.

Иногда black-box тесту всё же нужен доступ к какой-то внутренности. Для этого заводят файл `export_test.go` в `package foo` и выставляют наружу нужное только на время тестов: `var ParseInternal = parseInternal`.

![В каталоге `foo/` живут два пакета: тесты в `package foo` видят всё, а `package foo_test` импортирует `foo` как обычный пользователь и потому может импортировать пакет `b`, который сам зависит от `foo`](img/whitebox-blackbox.svg)

## Example-функции

```go
func ExampleReverse() {
    fmt.Println(Reverse("abc"))
    // Output: cba
}
```

Example-функции решают сразу две задачи: это и тест, и документация. При запуске `go test` они выполняются, а напечатанное в stdout сравнивается с комментарием `// Output:`. Если порядок строк не определён, как при обходе map, используйте `// Unordered output:`. Те же функции показываются в документации на pkg.go.dev как готовые примеры использования. Если комментария `Output` нет, пример только компилируется, но не запускается; это всё равно полезно, потому что гарантирует, что пример не устарел относительно API.

Имена подчиняются правилу: `Example` для пакета целиком, `ExampleF` для функции, `ExampleT` для типа, `ExampleT_M` для метода, а суффикс `_xxx` позволяет завести несколько вариантов одного примера.

## Покрытие

```
go test -cover ./...
go test -coverprofile=cover.out ./... && go tool cover -html=cover.out
go test -covermode=atomic -coverpkg=./... ./...   # atomic — для -race; coverpkg — учесть другие пакеты
```

Покрытие показывает, какие строки **выполнялись** во время тестов. Но оно ничего не говорит о том, проверялся ли их результат. Можно написать тесты, которые вызывают каждую функцию и печатают результат через `t.Log`, получить 100% покрытия и не поймать ни одной ошибки. Поэтому к покрытию стоит относиться как к карте неисследованных мест, а не как к оценке качества.

Качество тестов измеряют иначе, с помощью мутационного тестирования. Идея простая: в код намеренно вносят ошибки (мутантов) и смотрят, упадут ли тесты. Хороший набор тестов «убивает» каждого мутанта, а выжившие мутанты указывают на непроверенное поведение. В задачах 01 и 08 ваши тесты будут оцениваться именно так.

## Фаззинг (Go 1.18+)

Табличный тест проверяет те входы, которые вы догадались придумать. Фаззер придумывает их сам: он генерирует и мутирует входные данные, ориентируясь на покрытие, и ищет такие, на которых код падает. С Go 1.18 фаззинг встроен прямо в `go test`.

```go
func FuzzParse(f *testing.F) {
    f.Add("key=value")           // seed corpus
    f.Fuzz(func(t *testing.T, s string) {
        v, err := Parse(s)
        if err != nil { return }
        v2, err := Parse(Format(v))
        if err != nil || v2 != v { t.Fatalf("round trip %q", s) } // проверяем свойство
    })
}
```

Обычный `go test` без дополнительных флагов прогоняет фаззер как обычный тест, только на известных входах: на seed-корпусе, добавленном через `f.Add`, и на файлах из `testdata/fuzz/FuzzParse/*`. Настоящий фаззинг включается флагом: `go test -fuzz=FuzzParse -fuzztime=30s` генерирует новые входы с учётом покрытия. Найденный падающий вход сохраняется в `testdata/fuzz/…`, и с этого момента он становится регрессионным тестом, который будет прогоняться при каждом обычном `go test`. Есть пара ограничений: с `-fuzz` можно указать только один пакет, а регулярное выражение должно совпадать ровно с одним фаззером. Если не задать `-fuzztime`, фаззинг будет идти до первой ошибки или до Ctrl+C.

Аргументы фаззируемой функции могут иметь только простые типы: `string, []byte, int*, uint*, float*, bool, rune, byte`.

Самое трудное в фаззинге — решить, что проверять, ведь правильный ответ для случайного входа заранее неизвестен. Поэтому проверяют не конкретные значения, а свойства. Самое простое свойство — отсутствие паник. Очень продуктивен round-trip: `Decode(Encode(x)) == x`, как в примере выше. Можно сравнивать результат с эталонной, пусть медленной, реализацией или проверять инварианты вроде «результат сортировки упорядочен и содержит те же элементы».

![Без `-fuzz` корпус прогоняется как обычные тесты. С `-fuzz` входы мутируются, интересные (давшие новое покрытие) пополняют корпус в кэше, а падающий вход минимизируется и сохраняется в `testdata/fuzz`](img/fuzz-flow.svg)

## -race и -shuffle

Флаг `go test -race` включает детектор гонок данных. Он инструментирует каждый доступ к памяти, из-за чего программа замедляется примерно в $2$–$20$ раз. Детектор динамический: он находит только те гонки, которые **действительно случились** в данном прогоне. Если конкурентный участок кода не выполнился или горутины разошлись во времени удачно, гонка останется незамеченной. Поэтому тесты с конкурентностью гоняют с `-race -count=N`, давая планировщику больше шансов на неудачное чередование.

Флаг `-shuffle=on` перемешивает порядок тестов. Seed перемешивания печатается в выводе, и `-shuffle=<seed>` воспроизводит тот же порядок. Так ловят тесты, которые незаметно зависят друг от друга через глобальное состояние: один тест что-то записал, другой на это рассчитывает, и всё работает, пока порядок не изменится.

## Build-теги для интеграционных тестов

Тесты с настоящей базой данных или внешним сервисом медленные и требуют окружения, которого нет на машине каждого разработчика. Их принято отделять от быстрых юнит-тестов, и самый явный способ — build-тег:

```go
//go:build integration

package store_test   // тесты с настоящей БД
```

Такие тесты запускаются только командой `go test -tags integration ./...`. Есть и более мягкие альтернативы: пропускать медленные тесты при `go test -short` с помощью `if testing.Short() { t.Skip(...) }` или проверять, задана ли нужная переменная окружения (`if os.Getenv("DB_DSN") == "" { t.Skip() }`).

## TestMain

Если пакету нужна общая подготовка перед всеми тестами, например поднять контейнер с базой или прогреть кэш, объявите `TestMain`. Тогда `go test` вызовет её вместо того, чтобы сразу запускать тесты, а сами тесты выполнятся внутри `m.Run()`.

```go
func TestMain(m *testing.M) {
    setup()           // поднять контейнер, прогреть кэш
    code := m.Run()
    teardown()
    os.Exit(code)     // с Go 1.15 можно просто вернуться из TestMain
}
```

## testify (обзор)

Самая популярная внешняя библиотека для тестов — testify. Её `assert.Equal(t, want, got)` при несовпадении помечает провал и продолжает тест, а `require.NoError(t, err)` прерывает его. Кроме того, в ней есть `suite` для наборов тестов с setup/teardown и `mock` для моков. Testify экономит строки и при несовпадении печатает наглядный дифф. Минусы тоже есть: это ещё одна зависимость, а порядок аргументов (сначала want, потом got) путают постоянно, и сообщения об ошибках становятся перевёрнутыми. Идиоматичная альтернатива — стандартная библиотека в сочетании с `cmp.Diff` из go-cmp.
