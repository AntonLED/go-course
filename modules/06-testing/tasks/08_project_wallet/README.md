# Задание 6. Кошелёк: фейки, тесты против мутантов, горячий путь без аллокаций

Пакет `wallet`. Итоговая задача модуля.

Знакомая ситуация: вам достался рабочий, но совершенно не покрытый тестами сервис, и в нём есть деньги. Трогать такой код страшно, пока нет тестов, которые поймают регрессию. В этом задании вы пройдёте весь путь: напишете фейки для зависимостей, соберёте проверку, которая ловит тонкие баги, и оптимизируете горячий путь, не сломав вывод.

В `service.go` лежит «боевой» сервис кошелька `Wallet`: баланс, пополнение, списание с дневным лимитом и уведомлениями. Он зависит от `Store`, `Clock` и `Notifier`. Код корректен, но тестов у него нет. Ваша задача — довести его до ума в `wallet.go`, и работа делится на три части.

## Часть 1. Фейки

```go
func NewFakeClock(t time.Time) *FakeClock    // Now, Set, Advance — потокобезопасно
func NewMemStore(accounts ...Account) *MemStore
    // Get (копия; нет счёта → ошибка с errors.Is(err, ErrNotFound)), Put,
    // поле PutErr (если задано — Put возвращает его и ничего не сохраняет),
    // PutCount() — число успешных Put
type SpyNotifier struct{ Err error; ... }    // Notify записывает каждый вызов и возвращает Err;
                                             // Sent() — копия списка вызовов
```

Все фейки должны быть безопасны для конкурентного использования: тесты гоняются под `-race`.

## Часть 2. Тесты, которые ловят мутантов

```go
func CheckService(t testing.TB, newService func(Deps) Service)
```

Эта функция проверяет спецификацию из комментариев в `service.go` с помощью ваших фейков. Приёмочный тест запустит её на настоящем `Wallet`, где она не должна найти ни одной ошибки, и на 22 мутантах — копиях сервиса, в каждую из которых внесён один тонкий баг. Поймать нужно всех. Вот некоторые из них:

- граница лимита проверяется через `>=` вместо `>`, или запрещено списание всего баланса (`<=` вместо `<`);
- лимит не накапливается за день, не сбрасывается в новый день, или `DailyLimit == 0` считается нулевым лимитом;
- проверки идут в неверном порядке: баланс проверяется раньше лимита, а заморозка — позже;
- день считается в часовом поясе значения `Clock.Now()` (например, в локальном), а не в UTC — подумайте, каким временем инициализировать `FakeClock`, чтобы этот мутант себя выдал;
- ошибка уведомления проваливает операцию; уведомление отправляется при неудаче; уведомление уходит до сохранения; ошибка `Put` проглатывается; `Put` не вызывается вовсе; текст уведомления неверный;
- `Balance` несуществующего счёта возвращает `0, nil`.

Полный список лежит в `wallet_test.go` в переменной `bugs`, а запуск с `-v` покажет, кто из мутантов выжил.

Несколько советов. Для каждого сценария создавайте свежий набор фейков: `newService` можно вызывать сколько угодно раз. После ошибки проверяйте не только саму ошибку (`errors.Is`), но и отсутствие побочных эффектов: счёт не изменился, `PutCount() == 0`, уведомлений нет. И не забывайте про граничные значения: ровно лимит, ровно баланс, 0, отрицательные суммы.

## Часть 3. Горячий путь

```go
func AppendStatement(dst []byte, e Entry) []byte
// 2024-03-05T10:00:00Z withdraw alice -12.34\n
```

Выписка формируется для миллионов операций, поэтому при достаточной ёмкости `dst` функция должна делать 0 аллокаций (это проверяется через `testing.AllocsPerRun`). Вывод при этом должен совпадать байт в байт с текущей версией на `fmt.Sprintf`, включая случай `math.MinInt64`. Пригодятся `time.Time.AppendFormat` и `strconv.AppendUint`.
