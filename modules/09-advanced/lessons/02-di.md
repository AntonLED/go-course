# Внедрение зависимостей (DI)

Идея **внедрения зависимостей** (dependency injection) проста: компонент не создаёт свои зависимости сам, а получает их снаружи. Сервис пользователей не открывает соединение с базой, а получает готовый репозиторий; HTTP-обработчик не конструирует логгер, а принимает его аргументом. В Java и C# под DI обычно подразумевают фреймворк с аннотациями, а в Go это почти всегда делается **без фреймворка**, обычными конструкторами и интерфейсами.

## Constructor injection

Посмотрим, как выглядит проблема и её решение:

```go
// Плохо: зависимость создаётся внутри — не подменить в тестах, не переиспользовать пул.
type UserService struct{}
func (s *UserService) Get(id int) (*User, error) {
    db, _ := sql.Open("postgres", os.Getenv("DSN")) // скрытая зависимость от env и сети
    ...
}

// Хорошо: всё приходит через конструктор.
type UserService struct {
    repo  UserRepo
    log   *slog.Logger
    clock func() time.Time
}

func NewUserService(repo UserRepo, log *slog.Logger) *UserService {
    return &UserService{repo: repo, log: log, clock: time.Now}
}
```

Первый вариант неудобен сразу по нескольким причинам. В тесте базу не подменить, пул соединений создаётся заново на каждый вызов, а о том, что сервису нужна переменная окружения `DSN` и доступ к сети, можно узнать, только прочитав его код. Во втором варианте все зависимости видны в сигнатуре конструктора. Даже время приходит снаружи через поле `clock`, поэтому в тесте его можно заморозить.

Отсюда вытекают три правила. Зависимости должны быть явными, то есть видны в сигнатуре конструктора. Глобальных синглтонов вроде `var db *sql.DB` на уровне пакета и `init()` с побочными эффектами быть не должно. И наконец, конструктор не делает тяжёлой работы вроде похода в сеть или на диск: это задача методов `Start` или `Run`. Если без такой работы действительно не обойтись, конструктор возвращает `(T, error)`.

## Интерфейсы объявляются у потребителя

Вторая половина DI в Go — место, где объявлен интерфейс. В отличие от Java, где интерфейс обычно лежит рядом с реализацией, в Go его объявляет тот, кто им пользуется:

```go
// package users (потребитель)
type UserRepo interface {           // ровно то, что нужно сервису
    ByID(ctx context.Context, id int) (*User, error)
}

// package postgres (поставщик) — возвращает конкретный тип
func NewRepo(db *sql.DB) *Repo { ... }
func (r *Repo) ByID(ctx context.Context, id int) (*User, error) { ... }
func (r *Repo) Migrate(ctx context.Context) error { ... }
```

Этот принцип известен как «accept interfaces, return structs». Интерфейс получается маленьким, в один-три метода, ровно под нужды потребителя. Поставщик о нём ничего не знает: благодаря утиной типизации `*postgres.Repo` удовлетворяет `users.UserRepo` просто потому, что у него есть нужный метод. В тестах такой интерфейс подменяется фейком из пяти строк. А если хочется, чтобы компилятор проверил соответствие заранее, достаточно одной строки: `var _ users.UserRepo = (*postgres.Repo)(nil)`.

## Composition root

Если каждый компонент получает зависимости снаружи, кто-то должен их всё-таки создать. Это единственное место в программе, где конкретные реализации связываются вместе, и называется оно **composition root**. В Go это `main` или функция `run`/`New`, которую вызывает `main`:

```go
func run(ctx context.Context) error {
    cfg, err := config.Load(os.Args[1:], os.LookupEnv)
    if err != nil { return err }
    log := slog.New(slog.NewJSONHandler(os.Stdout, nil))
    db, err := sql.Open("pgx", cfg.DSN)
    if err != nil { return err }
    defer db.Close()

    repo := postgres.NewRepo(db)
    svc := users.NewService(repo, log)
    api := httpapi.New(svc, log)
    return httpapi.Serve(ctx, cfg.Addr, api)
}
```

![Граф зависимостей из `run`: каждый конструктор получает готовые зависимости аргументами, а `*postgres.Repo` передаётся в сервис как интерфейс `users.UserRepo`, объявленный у потребителя](img/di-composition-root.svg)

Для приложения из 5–30 компонентов ручная сборка — лучший вариант. Всё читается глазами, ошибки ловит компилятор, а порядок инициализации очевиден из порядка строк.

## Functional options

У конструкторов есть своя болезнь: необязательные параметры. Конструктор с десятью аргументами неудобен, а структура `Config` плохо отличает «не задано» от нулевого значения. В Go для этого прижился паттерн functional options:

```go
type Server struct { addr string; timeout time.Duration; log *slog.Logger }
type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func WithLogger(l *slog.Logger) Option   { return func(s *Server) { s.log = l } }

func NewServer(addr string, opts ...Option) *Server {
    s := &Server{addr: addr, timeout: 30 * time.Second, log: slog.Default()} // дефолты
    for _, o := range opts { o(s) }
    return s
}
srv := NewServer(":8080", WithTimeout(5*time.Second))
```

Добавление новой опции не ломает существующие вызовы, опции документируют сами себя, а все значения по умолчанию собраны в одном месте. Если опции нужно валидировать, их делают возвращающими ошибку: `type Option func(*Server) error`. В экосистеме за пределами стандартной библиотеки паттерн встречается повсюду, например в `grpc.NewServer(grpc.UnaryInterceptor(...))` и `zap.New(core, zap.AddCaller())`.

## DI-контейнеры

Когда в графе сотни компонентов, модулей и команд, ручная сборка превращается в сотни строк однообразного кода. Здесь на помощь приходят контейнеры, и в Go есть два принципиально разных подхода к ним.

### google/wire: граф на этапе генерации

```go
//go:build wireinject
func InitApp(cfg Config) (*App, error) {
    wire.Build(NewDB, postgres.NewRepo, wire.Bind(new(users.UserRepo), new(*postgres.Repo)),
        users.NewService, httpapi.New, NewApp)
    return nil, nil
}
```

Wire — генератор кода. По описанию провайдеров он создаёт файл `wire_gen.go` с обычными вызовами конструкторов, ровно такими, какие вы написали бы руками. Ошибки графа, например отсутствующий провайдер или цикл, всплывают **на этапе генерации**, рантайм-оверхеда нет, а сгенерированный код можно прочитать. Сам проект давно в режиме «только поддержка», но подход, то есть DI через кодогенерацию, остаётся актуальным.

### uber-go/fx поверх uber-go/dig: граф во время выполнения

```go
fx.New(
    fx.Provide(NewConfig, NewDB,
        fx.Annotate(postgres.NewRepo, fx.As(new(users.UserRepo))),
        users.NewService, httpapi.New),
    fx.Invoke(func(*http.Server) {}),  // что нужно построить
).Run()                                 // Start → ждём сигнал → Stop
```

Здесь всё происходит при запуске. `dig` смотрит на сигнатуры конструкторов через `reflect`, строит граф и вызывает конструкторы лениво, причём **каждый тип существует в единственном экземпляре**. Ошибки графа проявятся только при старте приложения. Взамен вы получаете модули (`fx.Module`), управление жизненным циклом и группы значений (`group:"routes"`). Расплачиваться приходится «магией», ошибками в рантайме и более сложной навигацией по коду: перейти от вызова к месту, где создан объект, IDE уже не поможет.

![Главное различие — момент построения графа: `wire` проверяет его и генерирует обычный код до компиляции, а `dig` разбирает сигнатуры через `reflect` уже при запуске программы](img/di-wire-vs-fx.svg)

### Жизненный цикл: `fx.Lifecycle`

Компонентам мало быть созданными: их нужно запустить и корректно остановить. В fx для этого конструктор регистрирует хуки:

```go
func NewHTTPServer(lc fx.Lifecycle, cfg Config, h http.Handler) *http.Server {
    srv := &http.Server{Addr: cfg.Addr, Handler: h}
    lc.Append(fx.Hook{
        OnStart: func(ctx context.Context) error {
            ln, err := net.Listen("tcp", srv.Addr)
            if err != nil { return err }
            go srv.Serve(ln)          // OnStart не должен блокироваться
            return nil
        },
        OnStop: func(ctx context.Context) error { return srv.Shutdown(ctx) },
    })
    return srv
}
```

Хуки `OnStart` вызываются в порядке регистрации, а он совпадает с порядком построения, так что зависимости стартуют раньше зависимых. `OnStop` вызываются **в обратном порядке**, иначе HTTP-сервер мог бы пережить базу, которой пользуется. Если какой-то `OnStart` вернул ошибку, fx откатывает старт и останавливает уже запущенные хуки. Весь старт и вся остановка ограничены таймаутом, по умолчанию 15 секунд; его меняют опциями `fx.StartTimeout` и `fx.StopTimeout`, а дедлайн приходит хукам через `ctx`.

![Хуки `OnStart` идут в порядке регистрации, `OnStop` — в обратном, поэтому HTTP-сервер останавливается раньше базы, которой он пользуется. При ошибке старта останавливаются только уже запущенные компоненты](img/di-fx-lifecycle.svg)

## Как устроен runtime-контейнер внутри

Внутри такой контейнер проще, чем кажется, и укладывается в три шага:

1. `Provide(ctor)` проверяет, что передана функция, берёт тип её результата `Type.Out(0)` как ключ и сохраняет конструктор.
2. `Invoke(fn)` для каждого параметра `Type.In(i)` рекурсивно находит провайдер, строит аргументы, вызывает конструктор через `Value.Call` и кэширует результат.
3. Стек типов, которые строятся прямо сейчас, ловит циклы вида $A \to B \to A$.

Всё это вы реализуете сами в задаче 02.

## Типичные ошибки

Самая коварная ошибка — Service Locator, когда бизнес-код сам достаёт зависимости вызовом `container.Get("db")`. Выглядит похоже на DI, но зависимость снова скрыта, и по сигнатуре уже не понять, что компоненту нужно.

Вторая крайность — огромные интерфейсы «на всякий случай» на стороне поставщика, вроде `type Repository interface { 40 методов }`. Их тяжело подменять и невозможно реализовать частично.

Третья — `init()` с подключением к базе. Такой код не тестируется, а порядок инициализации пакетов неочевиден. Похожая проблема у конструктора, который запускает горутины: в тестах они утекают, поэтому запуск должен жить в `Start` или `Run`.

Наконец, циклические зависимости между компонентами обычно говорят о неправильно проведённых границах. Разрывайте их интерфейсом или событием.
