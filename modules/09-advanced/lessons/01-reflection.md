# Рефлексия

Представьте, что вы пишете `json.Marshal`. Функция получает `any` и ничего не знает о том, что ей передали: структуру, срез, map или число. Тем не менее она должна обойти все поля, прочитать их имена и теги и превратить значения в текст. Для этого нужна **рефлексия** — способность программы во время выполнения исследовать и менять собственные значения, о которых на этапе компиляции известно только то, что это `interface{}`.

В Go рефлексия живёт в пакете [`reflect`](https://pkg.go.dev/reflect). На ней построены `encoding/json`, `fmt`, `text/template`, `Scan` в `database/sql`, а также валидаторы, DI-контейнеры и ORM. Даже если вы сами никогда не напишете `reflect.ValueOf`, вы пользуетесь им каждый день, поэтому полезно понимать, как он устроен и чего стоит.

## Два главных типа: `reflect.Type` и `reflect.Value`

Весь пакет вращается вокруг двух сущностей. `reflect.Type` описывает тип, `reflect.Value` хранит конкретное значение вместе с его типом:

```go
x := 3.14
t := reflect.TypeOf(x)   // reflect.Type — описание типа (float64)
v := reflect.ValueOf(x)  // reflect.Value — значение + его тип
fmt.Println(t.Name(), t.Kind(), v.Float()) // float64 float64 3.14
```

`Type` — это интерфейс. Через него вы узнаёте имя и категорию типа (`Name()`, `Kind()`), перебираете поля структуры (`NumField()`, `Field(i)`), добираетесь до типа элемента у указателей, срезов и map (`Elem()`), смотрите на методы (`NumMethod()`, `Implements(u)`) и на раскладку в памяти (`Size()`, `Align()`). `Value`, напротив, структура, и её методы работают со значением: `Kind()`, `Int()`, `String()`, `Field(i)`, `Index(i)`, `Elem()`, семейство `Set*()`, `Call()` и `Interface()`.

Иногда тип нужен, а значения под рукой нет. Особенно неудобно это с интерфейсами: `reflect.TypeOf` от nil-интерфейса вернёт nil. Начиная с Go 1.22 есть `reflect.TypeFor[T]()`, которая строит тип прямо из параметра-типа, например `reflect.TypeFor[error]()`.

### Kind и Type — не одно и то же

`Kind` — это категория: Struct, Pointer, Slice, Map, Int и так далее. `Type` — конкретный тип. Для `type Celsius float64` тип будет `main.Celsius`, а Kind — `Float64`. Разница становится практической, когда вы пишете загрузчик конфигурации: у `time.Duration` Kind равен `Int64`, и если сначала смотреть на Kind, строка `"5s"` попадёт в ветку разбора целых чисел и не распарсится. Поэтому в таких загрузчиках **сначала проверяют конкретный тип**, и только потом переходят к `Kind`.

## Три закона рефлексии

Роб Пайк сформулировал поведение пакета в статье [The Laws of Reflection](https://go.dev/blog/laws-of-reflection) в виде трёх законов:

1. Из интерфейсного значения можно получить объект рефлексии: `reflect.ValueOf(i)`.
2. Из объекта рефлексии можно вернуться обратно к интерфейсу: `v.Interface().(T)`.
3. Изменить объект рефлексии можно, только если значение settable, то есть допускает запись.

![Первые два закона: `reflect.ValueOf` принимает `any`, значение копируется в интерфейс, а `TypeOf` и `ValueOf` читают его `_type` и `data`; `v.Interface()` упаковывает значение обратно](img/reflect-objects.svg)

С первыми двумя всё интуитивно, а третий регулярно становится источником паник:

```go
x := 1
v := reflect.ValueOf(x)
v.SetInt(2)              // panic: reflect.Value.SetInt using unaddressable value

v = reflect.ValueOf(&x).Elem() // Elem() разыменовывает указатель
fmt.Println(v.CanSet())        // true
v.SetInt(2)                    // x == 2
```

Почему первый `SetInt` падает? `ValueOf(x)` получает **копию** `x`, упакованную в интерфейс. Изменить её можно было бы, но результат никто бы не увидел: исходная переменная осталась бы прежней. Чтобы не вводить в заблуждение, Go такую запись просто запрещает. Если же передать указатель и разыменовать его через `Elem()`, мы получим `Value`, которое смотрит прямо на `x`.

![Слева `Value` смотрит на копию `x`, поэтому `SetInt` паникует. Справа `ValueOf(&x)` хранит указатель, а `Elem()` даёт адресуемое `Value`, которое пишет прямо в `x`](img/reflect-settable.svg)

### Адресуемость и `CanSet`

За третьим законом стоят два понятия. Значение **адресуемо** (`CanAddr()`), если оно лежит в памяти, на которую можно взять указатель: это элемент среза, поле адресуемой структуры или результат `Elem()` у указателя. Значение **settable** (`CanSet()`), если оно адресуемо и при этом получено не через неэкспортируемое поле. Второе условие защищает инкапсуляцию: рефлексия не должна давать больше прав, чем обычный код из другого пакета.

Отдельный случай — map. Её элементы не адресуемы, потому что при росте таблицы они переезжают, и `v.MapIndex(k)` возвращает копию. Менять значения в map через рефлексию нужно методом `v.SetMapIndex(k, val)`.

```go
type T struct{ A int; b int }
v := reflect.ValueOf(&T{}).Elem()
v.Field(0).CanSet() // true
v.Field(1).CanSet() // false: неэкспортируемое
v.Field(1).Interface() // panic: cannot return value obtained from unexported field
```

Обратите внимание на последнюю строку: из неэкспортируемого поля нельзя не только писать, но и забрать значение через `Interface()`.

## Обход структуры и теги

Самый частый сценарий рефлексии в прикладном коде — пройти по полям структуры и прочитать их теги. Так работают `encoding/json`, валидаторы и загрузчики конфигурации:

```go
type User struct {
    Name  string `json:"name" validate:"required,min=3"`
    Email string `json:"email,omitempty"`
    age   int
}

func walk(v any) {
    rv := reflect.Indirect(reflect.ValueOf(v)) // разыменует указатель, если есть
    rt := rv.Type()
    for i := 0; i < rt.NumField(); i++ {
        sf := rt.Field(i)          // reflect.StructField: Name, Type, Tag, Offset, Anonymous
        if !sf.IsExported() { continue }
        tag, ok := sf.Tag.Lookup("validate") // Lookup отличает "нет тега" от пустого
        fmt.Println(sf.Name, sf.Type, tag, ok, rv.Field(i))
    }
}
```

![`walk(User{})`: `rt.Field(i)` отдаёт `StructField` со смещением и тегом, `Tag.Lookup` отличает отсутствующий ключ (`"", false`) от заданного, а неэкспортируемое `age` пропускается](img/reflect-struct-walk.svg)

Тег — это обычная строка в формате `key:"value" key2:"value2"`: пары разделяются пробелом, а вокруг двоеточия пробелов быть не должно. Ошибиться здесь легко, а компилятор тег не проверяет, зато проверяет `go vet` своим анализатором `structtag`.

Встроенные поля (у них `Anonymous == true`) для рефлексии выглядят как обычные поля, чьё имя совпадает с именем типа. Их поля «поднимает» уже конкретная библиотека: так делает `encoding/json`. Если вам нужен тот же список полей с учётом встраивания, не пишите обход сами, а возьмите `reflect.VisibleFields(t)`.

## Работа с коллекциями и создание значений

Рефлексия умеет не только читать, но и создавать значения произвольного типа: срезы, map, указатели на новые объекты. Именно так декодер JSON создаёт вложенные структуры, о которых заранее ничего не знает:

```go
s := reflect.MakeSlice(reflect.TypeFor[[]int](), 0, 10)
s = reflect.Append(s, reflect.ValueOf(42))
m := reflect.MakeMap(reflect.TypeFor[map[string]int]())
m.SetMapIndex(reflect.ValueOf("a"), reflect.ValueOf(1))
p := reflect.New(reflect.TypeFor[User]()) // *User, как new(User)
for iter := m.MapRange(); iter.Next(); { fmt.Println(iter.Key(), iter.Value()) }
```

## Вызов функций и методов

Функцию, завёрнутую в `Value`, можно вызвать, передав аргументы тоже в виде `Value`. Методы находятся по имени:

```go
fn := reflect.ValueOf(strings.Repeat)
out := fn.Call([]reflect.Value{reflect.ValueOf("ab"), reflect.ValueOf(3)})
fmt.Println(out[0].String()) // ababab

m := reflect.ValueOf(time.Second).MethodByName("String")
fmt.Println(m.Call(nil)[0]) // 1s
```

У `Type` функции есть методы `NumIn`, `In(i)`, `NumOut`, `Out(i)` и `IsVariadic`, которые описывают сигнатуру. На этом держатся DI-контейнеры: в `c := dig.New(); c.Provide(NewDB)` контейнер смотрит на параметры конструктора и сам понимает, что нужно построить до него.

С методами есть одна тонкость. Метод-набор типа `T` содержит только методы с получателем `T`, а у `*T` к ним добавляются методы с получателем `*T`. Поэтому `reflect.TypeOf(T{}).NumMethod()` не видит методов с указательным получателем, и проверка `Type.Implements(ifaceType)` для `T` и для `*T` может дать разные ответы. Неэкспортируемые методы через `reflect` не видны вовсе.

## `reflect.DeepEqual`

`DeepEqual` сравнивает значения «вглубь»: срезы поэлементно, map по ключам, указатели по значениям, на которые они указывают, причём с защитой от циклических ссылок. Звучит как универсальный инструмент для тестов, но у него есть неочевидная семантика:

```go
reflect.DeepEqual([]int{}, []int(nil))      // false! nil и пустой срез различаются
reflect.DeepEqual(map[int]int{}, map[int]int(nil)) // false
reflect.DeepEqual(math.NaN(), math.NaN())   // false (NaN != NaN)
var e1, e2 error = nil, (*MyErr)(nil)
reflect.DeepEqual(e1, e2)                   // false: разные динамические типы
reflect.DeepEqual(func(){}, func(){})       // false: функции равны только если обе nil
```

Каждая из этих строк по-своему логична: nil-срез и пустой срез действительно разные значения, NaN по стандарту IEEE 754 не равен сам себе, а nil-интерфейс и интерфейс с nil-указателем внутри различаются динамическим типом. Но в тесте такие различия обычно не то, что вы хотели проверить. Поэтому в тестах лучше брать `slices.Equal`, `maps.Equal` или `go-cmp`: у них понятнее семантика и гораздо полезнее диагностика при расхождении.

## Сколько это стоит

Рефлексия медленная, и полезно понимать, откуда берётся цена. Каждый `reflect.ValueOf` упаковывает значение в интерфейс, а это часто означает аллокацию, потому что значение убегает в кучу. `Call` работает в десятки раз медленнее прямого вызова: нужно собрать срез аргументов и проверить их типы. Обход полей с разбором тегов стоит $O(n)$ по числу полей на каждый вызов, если делать его заново каждый раз.

Последнее лечится кэшем по `reflect.Type`: разобрали структуру один раз, сохранили результат, например в `sync.Map` с ключом `reflect.Type` и значением `*typeInfo`, и дальше только читаете. Ровно так поступает `encoding/json`. А вот с ещё одной ценой ничего не поделать: ошибки типов обнаруживаются не компилятором, а паникой во время выполнения.

## Когда рефлексия не нужна

Если задачу решают **дженерики**, используйте их. Компилятор проверит типы, а накладных расходов на упаковку в интерфейс не будет:

```go
// было: func Contains(slice any, x any) bool через reflect
func Contains[T comparable](s []T, x T) bool { return slices.Contains(s, x) }
```

Если набор возможных типов конечен и известен, хватит обычного `type switch`. А если нужна скорость без рантайм-рефлексии, код можно сгенерировать на этапе сборки через `go generate`: так работают `stringer`, `easyjson` и `wire`.

При этом дженерики не заменяют рефлексию там, где структура типа заранее неизвестна. Сериализация произвольных структур, чтение тегов, DI по сигнатурам конструкторов — это по-прежнему территория `reflect`.

## Типичные ошибки

Большинство ошибок с рефлексией заканчиваются паникой, и почти все они сводятся к нескольким сценариям.

- Вызов `reflect.ValueOf(x).SetX` без указателя падает с паникой «unaddressable value».
- После `ValueOf(&x)` забыли `Elem()` и работаете с самим указателем; `NumField` на нём паникует.
- `v.Interface()` на неэкспортируемом поле тоже паникует.
- Проверка `v.Kind() == reflect.Struct` не срабатывает, когда на вход пришёл указатель на структуру.
- `reflect.ValueOf(nil)` возвращает невалидный `Value` (`IsValid() == false`), и по документации на нём паникуют все методы, кроме `IsValid`, `Kind` и `String` (последний вернёт `"<invalid Value>"`).
- `IsNil()` на Kind, который не может быть nil (int, struct), вызывает панику.
