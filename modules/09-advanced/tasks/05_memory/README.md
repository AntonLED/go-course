# 05. Память и аллокации: раскладка, zero-alloc, пул, утечки

Урок: [Управление памятью и аллокациями](../../lessons/04-memory.md)

В пакете `memopt` собраны пять небольших упражнений. Каждое моделирует ситуацию, которая встречается в профилях настоящих сервисов: раздутые структуры, лишние аллокации на горячем пути, пул, который пухнет от одного большого запроса, и срез, который не даёт GC освободить мегабайты. Тесты измеряют память через `unsafe.Sizeof` и `testing.AllocsPerRun`, так что «примерно работает» здесь не пройдёт.

## 1. Порядок полей (`Event`)

В заготовке `Event` повторяет `EventOriginal`, который на amd64 занимает 64 байта: компилятор вставляет между полями выравнивающие «дыры». Переставьте поля так, чтобы `unsafe.Sizeof(Event{})` стал минимально возможным, то есть равным сумме размеров полей, округлённой вверх до максимального выравнивания:

$$
\text{Sizeof} = \left\lceil \frac{\sum_i s_i}{a_{\max}} \right\rceil \cdot a_{\max}
$$

На amd64 это 48 байт. Набор полей и их типы менять нельзя.

## 2. `AppendRecord(dst []byte, r Record) []byte` — 0 аллокаций

Функция дописывает в `dst` строку такого вида:
```
id=42 name="Bob" score=3.50 ok=true\n
```

Поле `name` записывается в Go-кавычках (как делает `strconv.Quote`), `score` — с двумя знаками после точки. Если у `dst` достаточная capacity, функция не должна сделать ни одной аллокации — это проверяет `testing.AllocsPerRun`. Поэтому `fmt` здесь не годится; обойдитесь `strconv.AppendInt`, `AppendQuote`, `AppendFloat` и `AppendBool`.

## 3. `JoinInts(ids []int, sep string) string` — не больше 1 аллокации

Сначала посчитайте точную длину результата, затем один раз вызовите `strings.Builder.Grow` — и единственной аллокацией станет сам буфер. Будьте осторожны с `math.MinInt64`: если считать число цифр через `-x`, получите переполнение.

## 4. `BufferPool`

Нужны `NewBufferPool(maxCap)`, `Get() *bytes.Buffer`, который всегда возвращает пустой буфер, и `Put(b)`, который сбрасывает буфер и возвращает его в `sync.Pool`. `nil` и буферы с `Cap() > maxCap` в пул не возвращаются, а выбрасываются: иначе один гигантский запрос навсегда раздует пул. Пул должен быть потокобезопасным.

## 5. Утечки через срезы

`CloneHead(b, n)` возвращает независимую копию первых `n` байт с `cap == len`. Простой `b[:n]` тут не подходит: он удерживал бы в памяти весь исходный массив, например 10 МБ ради 4 байт.

`RemoveAt[T](s, i)` удаляет элемент, сохраняя порядок остальных, и обнуляет освободившийся хвостовой слот. Указатель, оставшийся за пределами `len`, но внутри `cap`, не даёт GC собрать объект, на который он ссылается. Начиная с Go 1.22 именно так поступает `slices.Delete`.
